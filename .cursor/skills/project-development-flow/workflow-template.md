# AI 辅助开发流程模板

这个文件是 `project-development-flow` skill 的完整填写模板。执行项目规划、版本迭代、验收收口或文档补正时，按需读取并填写相关部分。

## 第一部分：项目级规划

这一部分只在项目开始时完整整理，后续根据实际情况维护。

示例：

```text
项目名称：审美系统

项目一句话定位：
作为墨核的 MVP，用审美偏好作为切口，验证长期记忆、多模态偏好演化和个性化推荐。

对应 Agent 前沿方向：
长期记忆、用户模型、多模态偏好建模、个性化推荐、Skill 沉淀。

它和其他项目的关系：
审美系统是墨核的第一版落地模块，后续服装系统、饮食系统都可以复用这套记忆和偏好建模能力。
```

```text
5. 不做多用户商业化版本。
```

```text

v0.3：初步审美画像生成
v0.4：加入时间维度，分析偏好变化
v0.5：个性化推荐
v1.0：审美变化报告 + Skill 沉淀
```

### 5. MVP 最小闭环

```text
MVP 目标：

MVP 输入：

MVP 处理流程：

MVP 输出：

MVP 验收标准：
```

示例：

```text
MVP 目标：
用户上传图片后，系统能提取审美特征，记录用户反馈，并生成初步审美画像。

MVP 输入：
图片、用户反馈。

MVP 处理流程：
图片上传 → 多模态模型分析 → 结构化审美特征 → 用户反馈 → 偏好记录 → 初步画像。

MVP 输出：
审美特征 JSON、用户偏好记录、初步审美画像。

MVP 验收标准：
连续输入 20-30 张图片后，系统能够生成一份有解释性的审美偏好画像。
```

### 7. 技术风险

```text
技术风险 1：

技术风险 2：

对应缓解方案：
```

示例：

```text
风险 1：多模态模型输出审美标签不稳定。
缓解：强制输出 JSON schema，并建立标签规范。

风险 2：用户反馈太少，难以形成画像。
缓解：第一版用少量人工样例验证，不追求完全自动化。

风险 3：偏好变化难以判断。
缓解：v0.1 不做变化分析，放到 v0.4。
```

## 第二部分：版本级研究与架构闸门

每个大版本开始前，必须先完成版本级研究与拆分。这个阶段不写功能代码，只回答“这个版本为什么存在、推进哪个长期能力、如何拆成子阶段”。

## 2. 版本级调研

调研不只围绕页面或 API，而要覆盖本版本涉及的 Agent / Memory / User Model / Retrieval / Evaluation / Governance 等长期能力。

```text
Agent 前沿方向调研：

可以借鉴的模式：

不能照搬的模式：

```

调研分三层：

```text

2. 能力级调研：memory、profile、retrieval、evaluation、governance 等能力模块。
3. 实现级调研：API、UI、分页、测试、数据库实现。
```

## 第三部分：迭代级实现流程

每个版本都按下面这个流程走一遍。进入代码实现前，必须先完成本轮目标、边界、验收、设计和生成计划。

如果当前大版本还没有完成“版本级研究与架构闸门”，不得直接进入迭代级实现。

示例：

```text
模块名称：审美特征抽取模块

模块职责：
调用多模态模型，从图片中抽取结构化审美特征。

上游模块：
图片上传模块。

下游模块：
审美结果存储模块、用户画像模块。

输入：
image_url、user_id。

输出：

异常情况：
图片无法读取、模型返回空、JSON 解析失败、字段缺失。

权限边界：
```

## 最终总流程

以后做每个项目，都按这个顺序：

```text
项目级规划
↓
拆成多个版本
↓
选择一个大版本
↓
执行版本级研究与架构闸门
↓
拆成多个子阶段
↓
对第一个子阶段执行迭代级流程
↓
AI 生成代码
↓
测试和复盘
↓
进入下一个子阶段或下一个版本
↓
继续循环
```

## 极简记忆

> 先把项目拆成版本路线图。
> 再让每个版本按照“问题定义 → 边界 → 契约 → 数据 → 接口 → Prompt/Skill/Workflow → AI生成 → 测试 → 重构 → 复盘”的闭环推进。

这就是最适合当前 AI 辅助开发方式的流程模板。
