# AI 审美形成系统：开发任务拆分与里程碑计划

## 1. 文档职责

这份文档只负责把当前版本拆成可执行开发任务。

它不重新定义版本路线，也不保存历史完成状态：

- 版本目标和版本边界以 `02-版本迭代路线图.md` 为准。
- MVP 产品范围以 `03-MVP功能需求文档.md` 为准。
- V1 工程验收清单以 `16-V1开发收口清单.md` 为准。
- 实际完成情况、测试记录和复盘以 `15-迭代执行记录.md` 和 `archive/` 为准。

使用方式：

```text
先看 02 判断当前版本
↓
再看 03 确认 MVP 产品范围
↓
再看 16 确认 V1 验收清单
↓
最后用本文档拆任务和安排开发顺序
```

## 2. 当前执行版本

当前执行版本：

```text
V1-A 真实审美特征抽取
```

当前核心目标：

```text
在 V1 skeleton 基线上，将 mock feature extraction 升级为可替换的真实审美特征抽取能力。
```

当前不处理：

- V2 的历史报告和轻量画像。
- V3 的 personalized retrieval、RAG 和评估面板。
- V4 的 Agent、MCP、知识图谱和多模态扩展。
- PostgreSQL runtime 持久化。
- ChromaDB runtime 写入。

## 3. 技术选型

当前技术栈：

- 前端：React + TypeScript + Vite
- 后端：FastAPI + Pydantic
- 业务数据库：PostgreSQL
- 向量库：ChromaDB
- 文件存储：本地文件目录，后续可替换对象存储
- AI 能力：V1 先使用 mock AI client 保持 schema 稳定，后续再替换为真实 LLM / vision / embedding API
- 测试：pytest + 前端构建检查，后续补前端组件测试

PostgreSQL 可以使用 Navicat、DBeaver 或 DataGrip 可视化管理。

## 4. V1 子阶段拆分

V1 可以拆成以下子阶段。它们是开发顺序参考，不替代 `16-V1开发收口清单.md`。

### 4.1 V1-A：真实审美特征抽取

核心问题：

```text
系统能否从真实图片 / 文本输入中抽取稳定、结构化、有 evidence 的审美特征？
```

实现能力：

- FeatureExtractor 抽象。
- MockFeatureExtractor 保留。
- LLMFeatureExtractor / VisionFeatureExtractor。
- 图片审美特征 prompt。
- 文本审美特征 prompt。
- 结构化输出 schema validator。
- promptVersion / modelName 记录。
- 基础失败处理。

验收标准：

- 图片输入可以生成结构化底层特征。
- 文本输入可以生成结构化底层特征。
- 输出符合 `InputFeature` schema。
- 每个特征包含 value / confidence / evidence。
- 模型输出非法时能被识别。
- 当前 API 行为保持不变。
- mock workflow 仍可运行。

### 4.2 V1-B：Embedding 与相似性分组

核心问题：

```text
系统能否把多个审美输入组织成可解释的相似性结构？
```

实现能力：

- EmbeddingClient 抽象。
- MockEmbeddingClient 保留。
- 真实 embedding 生成。
- embedding metadata 保存。
- 输入之间相似度计算。
- 小样本相似性分组。
- 异常输入识别。
- group uncertainty 输出。

验收标准：

- 每个 input 能生成 embedding。
- 相似输入能被分到同一组。
- 每组都有 commonFeatures。
- 每组都有 uncertainty。
- 样本不足时能跳过分组。
- 分组结果不被描述为绝对聚类结论。

### 4.3 V1-C：报告生成与反馈闭环

核心问题：

```text
系统能否生成一份有证据、有不确定性、非玄学化的审美报告，并收集用户反馈？
```

实现能力：

- PossibleInterpretation 生成。
- Insight 生成。
- Report 生成。
- ReportResponse 对齐。
- 洞察 evidenceRefs。
- disclaimer。
- 用户反馈接口完善。
- 反馈 rating schema。
- 前端报告页展示真实后端数据。

验收标准：

- 报告包含 summary。
- 报告包含 lowLevelFeatures。
- 报告包含 similarityGroups。
- 报告包含 possibleInterpretations。
- 报告包含 insights。
- 每条 insight 有 evidenceRefs。
- 每条 insight 有 uncertainty。
- 用户可以提交反馈。
- 反馈可以被保存。
- 报告不包含人格诊断和玄学表达。

### 4.4 V1-D：数据持久化与基础日志

核心问题：

```text
系统能否把输入、特征、任务、报告、反馈和基础日志持久化，为长期记忆做准备？
```

实现能力：

- PostgreSQL 连接。
- users / anonymous users。
- aesthetic_inputs。
- input_features。
- analysis_jobs。
- aesthetic_reports。
- possible_interpretations。
- insights。
- insight_feedback。
- analysis_logs。
- repository 从 MemoryStore 切换为数据库实现。
- `.env.example`。
- 数据库初始化脚本。

可选能力：

- ChromaDB collection 初始化。
- embedding_records 表。

验收标准：

- 服务重启后数据不丢失。
- 输入可查询。
- 报告可查询。
- 反馈可查询。
- analysis job 状态可查询。
- 基础日志记录 step / status / modelName / promptVersion / latency / error。

### 4.5 V1-E：稳定版验收

核心问题：

```text
用户能否完成一次真实输入到真实报告再到反馈保存的完整流程？
```

实现能力：

- 前端完整联调。
- 后端完整联调。
- 错误处理。
- 空输入处理。
- 模型失败处理。
- schema 校验失败处理。
- 报告页面打磨。
- 基础测试。
- README 更新。
- V1 完成记录。

验收标准：

- 用户可以提交 3-10 个图片 / 文本样本。
- 系统可以完成分析任务。
- 系统可以生成结构化报告。
- 每条洞察都有 evidence。
- 用户反馈能保存。
- 后端数据能持久化，或明确记录 V1 mock 阶段替代边界。
- 前端能展示真实报告。
- 基础测试通过。
- V1 遗留问题已记录。

## 5. 当前 V1 收口里程碑

### 5.1 Milestone 1：项目骨架与页面闭环

目标：

```text
前端能完成首页 → 上传页 → 分析等待页 → 报告页的基本路径。
```

任务：

- 确认前端页面：`HomePage`、`UploadPage`、`AnalysisJobPage`、`ReportDetailPage`。
- 确认通用组件：按钮、加载态、证据列表。
- 确认业务组件：上传表单、输入预览、分析状态、报告卡片、反馈面板。
- 确认前端不直接写 `fetch`，统一经过 `frontend/src/services`。

验收：

- 用户可以看到完整 V1 页面骨架。
- 页面表达不出现心理测试、玄学或人格诊断气质。
- 页面字段和报告结构与 `06-输出报告模板文档.md` 对齐。

### 5.2 Milestone 2：后端 API Skeleton

目标：

```text
后端暴露 V1 必要 API，并保持 route/service/repository 分层。
```

任务：

- 实现或检查 `GET /api/health`。
- 实现或检查 `POST /api/inputs`。
- 实现或检查 `POST /api/analysis-jobs`。
- 实现或检查 `GET /api/analysis-jobs/{job_id}`。
- 实现或检查 `GET /api/reports/{report_id}`。
- 实现或检查 `POST /api/insights/{insight_id}/feedback`。

验收：

- API route 只处理 HTTP 层。
- 业务逻辑进入 service。
- 数据访问进入 repository。
- API request / response 使用 Pydantic schema。

### 5.3 Milestone 3：数据结构与存储闭环

目标：

```text
V1 的业务事实可以保存，向量 metadata 和业务数据边界清楚。
```

任务：

- 确认 `aesthetic_inputs` 的保存方式。
- 确认 `input_features` 的保存方式。
- 确认 `embedding_records` 或等价 metadata 保存方式。
- 确认 `analysis_jobs` 状态流转。
- 确认 `aesthetic_reports`、`possible_interpretations`、`insights`、`insight_feedback`。
- 确认 `analysis_logs` 能记录 step、状态、模型、耗时和错误。

验收：

- PostgreSQL 或当前 repository mock 是业务事实来源。
- ChromaDB 只保存向量和检索 metadata。
- 不把完整业务对象只存在向量库。

### 5.4 Milestone 4：Mock AI Workflow

目标：

```text
先用 mock AI client 跑通 V1 分析链路，保证 schema 稳定。
```

任务：

- 实现或检查图片底层特征 mock。
- 实现或检查文本底层特征 mock。
- 实现或检查 embedding mock。
- 实现或检查相似性分组。
- 实现或检查 possible interpretations 生成。
- 实现或检查报告生成。
- 实现或检查 prompt output validator。

验收：

- mock 输出和真实模型预期输出使用同一 schema。
- LLM 原始输出不能直接入库。
- 每条洞察至少有一个 evidence ref。
- 相似性分组不能被表达成绝对聚类结论。

### 5.5 Milestone 5：前后端联调

目标：

```text
前端通过真实 API 获取任务状态、报告和反馈结果。
```

任务：

- 上传页调用输入创建 API。
- 分析等待页调用分析任务创建和查询 API。
- 报告页调用报告查询 API。
- 反馈面板调用反馈提交 API。
- 增加必要的 loading、error 和 empty state。

验收：

- 用户可以从上传走到报告。
- 反馈可以提交并得到明确结果。
- 前端类型与后端 schema 对齐。

### 5.6 Milestone 6：V1 验收与归档

按 16 完成 V1 验收，并把实际状态写入 15 和 archive。

- 记录已完成、部分完成、未完成。

## 6. AI 生成代码顺序

每次让 AI 写代码时，按下面顺序拆小任务：

1. Pydantic schema 和 TypeScript type 对齐。
2. Repository 或当前 in-memory store。
3. Service。
4. Workflow step。
5. API route。
6. 前端 service。
7. 前端页面或 feature component。
8. 单元测试或集成测试。
9. 文档状态更新。

每次生成代码前必须提供：

- 本次任务目标。
- 涉及的权威文档。
- 输入 schema。
- 输出 schema。
- 验收标准。
- 不允许 AI 自行决定的边界。

## 7. 每次开发的约束

- 不直接在 API route 中写业务流程。
- 不在 service 中拼接 prompt。
- 不让 LLM 原始输出直接入库。
- 不把 ChromaDB 当业务数据库。
- 不把相似性分组说成绝对聚类结论。
- 不输出人格诊断、玄学判断或无依据高级词。
- 不把 V2/V3/V4 能力提前塞进 V1。
