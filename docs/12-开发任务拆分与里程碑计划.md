- 根目录 `16` / `17` 只作为历史兼容入口保留。
- 实际完成情况、测试记录和复盘以 `15-迭代执行记录.md` 和 `archive/` 为准。

使用方式：


## 5. AI 生成代码顺序

每次让 AI 写代码时，按下面顺序拆小任务：

1. Pydantic schema 和 TypeScript type 对齐。
2. Repository 或当前 in-memory store。
3. Service。
4. Workflow step。
5. API route。
6. 前端 service。
7. 前端页面或 feature component。
8. 单元测试或集成测试。
9. 文档状态更新。

每次生成代码前必须提供：

- 本次任务目标。
- 涉及的权威文档。
- 输入 schema。
- 输出 schema。
- 验收标准。
- 不允许 AI 自行决定的边界。

## 6. 每次开发的约束

- 不直接在 API route 中写业务流程。
- 不在 service 中拼接 prompt。
- 不让 LLM 原始输出直接入库。
- 不把 ChromaDB 当业务数据库。
- 不把相似性分组说成绝对聚类结论。
- 不输出人格诊断、玄学判断或无依据高级词。
- 不把后续版本 runtime 能力提前塞进当前研究或验收阶段。

### 6.1 AI 辅助开发治理约束

本项目允许 AI 辅助生成代码，但不允许用“兜底、兼容、默认值、mock 或跳过逻辑”掩盖错误。

开发期默认规则：

- 核心业务事实失败必须 fail fast，例如输入不存在、报告不存在、feedback 关联不到 insight、schema 校验失败、数据库写入失败。
- 非核心增强能力可以 graceful degradation，但必须记录为显性降级事件，并说明 original error、fallback action、developer message、userVisible 和测试覆盖。
- Mock / heuristic / placeholder / dev-only 行为必须可见，不能在文档、API 或 UI 中暗示为真实 AI 能力。
- 测试失败时先定位根因，不优先修改测试预期；只有当测试不符合权威设计文档时才允许调整测试。
- 一处实现不抽象；只有稳定重复或当前版本明确需要替换实现时，才新增 interface / factory / registry。
- 未来版本能力只能进入文档、边界提示或预留字段，不提前实现未被当前 iteration 验收的 runtime。

### 6.2 Developer Debug Panel 实施边界

Developer Debug Panel 作为 V2 横向基础设施分阶段推进，不阻断 V2-C 主线。

实施顺序：

1. 先记录治理原则和验收标准。
2. 再补 `fallback_events`、`mock_usage`、`schema_validation`、`boundary_warnings` 等最小调试语义。
3. 最后实现最小开发者面板，只展示 workflow trace、fallback events、mock usage、schema validation、boundary warnings。

明确不做：

- 不做复杂 dashboard。
- 不做实时刷新。
- 不接入 Langfuse / LangSmith / OpenTelemetry runtime。
- 不提前实现 RAG、Agent、MCP 或 ChromaDB runtime。
