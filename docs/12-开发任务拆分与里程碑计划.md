# AI 审美形成系统：开发任务拆分与里程碑计划

## 1. 文档职责

这份文档只负责把当前版本拆成可执行开发任务。

它不重新定义版本路线，也不保存历史完成状态：

- 版本目标和版本边界以 `02-版本迭代路线图.md` 为准。
- MVP 产品范围以 `03-MVP功能需求文档.md` 为准。
- V1 工程验收清单以 `16-V1开发收口清单.md` 为准。
- 实际完成情况、测试记录和复盘以 `15-迭代执行记录.md` 和 `archive/` 为准。

使用方式：

```text
先看 02 判断当前版本
↓
再看 03 确认 MVP 产品范围
↓
再看 16 确认 V1 验收清单
↓
最后用本文档拆任务和安排开发顺序
```

## 3. 技术选型

当前技术栈：

- 前端：React + TypeScript + Vite
- 后端：FastAPI + Pydantic
- 业务数据库：PostgreSQL
- 向量库：ChromaDB
- 文件存储：本地文件目录，后续可替换对象存储
- AI 能力：V1 先使用 mock AI client 保持 schema 稳定，后续再替换为真实 LLM / vision / embedding API
- 测试：pytest + 前端构建检查，后续补前端组件测试

PostgreSQL 可以使用 Navicat、DBeaver 或 DataGrip 可视化管理。

## 4. V1 子阶段拆分

V1 可以拆成以下子阶段。它们是开发顺序参考，不替代 `16-V1开发收口清单.md`。

### 4.1 V1-A：真实审美特征抽取

核心问题：

```text
系统能否从真实图片 / 文本输入中抽取稳定、结构化、有 evidence 的审美特征？
```

实现能力：

- FeatureExtractor 抽象。
- MockFeatureExtractor 保留。
- LLMFeatureExtractor / VisionFeatureExtractor。
- 图片审美特征 prompt。
- 文本审美特征 prompt。
- 结构化输出 schema validator。
- promptVersion / modelName 记录。
- 基础失败处理。

验收标准：

- 图片输入可以生成结构化底层特征。
- 文本输入可以生成结构化底层特征。
- 输出符合 `InputFeature` schema。
- 每个特征包含 value / confidence / evidence。
- 模型输出非法时能被识别。
- 当前 API 行为保持不变。
- mock workflow 仍可运行。

### 4.2 V1-B：Embedding 与相似性分组

核心问题：

```text
系统能否把多个审美输入组织成可解释的相似性结构？
```

实现能力：

- EmbeddingClient 抽象。
- MockEmbeddingClient 保留。
- 真实 embedding 生成。
- embedding metadata 保存。
- 输入之间相似度计算。
- 小样本相似性分组。
- 异常输入识别。
- group uncertainty 输出。

验收标准：

- 每个 input 能生成 embedding。
- 相似输入能被分到同一组。
- 每组都有 commonFeatures。
- 每组都有 uncertainty。
- 样本不足时能跳过分组。
- 分组结果不被描述为绝对聚类结论。

### 4.3 V1-C：报告生成与反馈闭环

核心问题：

```text
系统能否生成一份有证据、有不确定性、非玄学化的审美报告，并收集用户反馈？
```

实现能力：

- PossibleInterpretation 生成。
- Insight 生成。
- Report 生成。
- ReportResponse 对齐。
- 洞察 evidenceRefs。
- disclaimer。
- 用户反馈接口完善。
- 反馈 rating schema。
- 前端报告页展示真实后端数据。

验收标准：

- 报告包含 summary。
- 报告包含 lowLevelFeatures。
- 报告包含 similarityGroups。
- 报告包含 possibleInterpretations。
- 报告包含 insights。
- 每条 insight 有 evidenceRefs。
- 每条 insight 有 uncertainty。
- 用户可以提交反馈。
- 反馈可以被保存。
- 报告不包含人格诊断和玄学表达。

### 4.4 V1-D：数据持久化与基础日志

核心问题：

```text
系统能否把输入、特征、任务、报告、反馈和基础日志持久化，为长期记忆做准备？
```

实现能力：

- PostgreSQL 连接。
- users / anonymous users。
- aesthetic_inputs。
- input_features。
- analysis_jobs。
- aesthetic_reports。
- possible_interpretations。
- insights。
- insight_feedback。
- analysis_logs。
- repository 从 MemoryStore 切换为数据库实现。
- `.env.example`。
- 数据库初始化脚本。

可选能力：

- ChromaDB collection 初始化。
- embedding_records 表。

验收标准：

- 服务重启后数据不丢失。
- 输入可查询。
- 报告可查询。
- 反馈可查询。
- analysis job 状态可查询。
- 基础日志记录 step / status / modelName / promptVersion / latency / error。

### 4.5 V1-E：稳定版验收

核心问题：

```text
用户能否完成一次真实输入到真实报告再到反馈保存的完整流程？
```

实现能力：

- 前端完整联调。
- 后端完整联调。
- 错误处理。
- 空输入处理。
- 模型失败处理。
- schema 校验失败处理。
- 报告页面打磨。
- 基础测试。
- README 更新。
- V1 完成记录。

验收标准：

- 用户可以提交 3-10 个图片 / 文本样本。
- 系统可以完成分析任务。
- 系统可以生成结构化报告。
- 每条洞察都有 evidence。
- 用户反馈能保存。
- 后端数据能持久化，或明确记录 V1 mock 阶段替代边界。
- 前端能展示真实报告。
- 基础测试通过。
- V1 遗留问题已记录。

## 5. 当前 V1 收口里程碑

### 5.1 Milestone 1：项目骨架与页面闭环

目标：

```text
前端能完成首页 → 上传页 → 分析等待页 → 报告页的基本路径。
```

任务：

- 确认前端页面：`HomePage`、`UploadPage`、`AnalysisJobPage`、`ReportDetailPage`。
- 确认通用组件：按钮、加载态、证据列表。
- 确认业务组件：上传表单、输入预览、分析状态、报告卡片、反馈面板。
- 确认前端不直接写 `fetch`，统一经过 `frontend/src/services`。

验收：

- 用户可以看到完整 V1 页面骨架。
- 页面表达不出现心理测试、玄学或人格诊断气质。
- 页面字段和报告结构与 `06-输出报告模板文档.md` 对齐。

### 5.2 Milestone 2：后端 API Skeleton

目标：

```text
后端暴露 V1 必要 API，并保持 route/service/repository 分层。
```

任务：

- 实现或检查 `GET /api/health`。
- 实现或检查 `POST /api/inputs`。
- 实现或检查 `POST /api/analysis-jobs`。
- 实现或检查 `GET /api/analysis-jobs/{job_id}`。
- 实现或检查 `GET /api/reports/{report_id}`。
- 实现或检查 `POST /api/insights/{insight_id}/feedback`。

验收：

### 5.3 Milestone 3：数据结构与存储闭环

验收：

- PostgreSQL 或当前 repository mock 是业务事实来源。

- 不把完整业务对象只存在向量库。

- 实现或检查相似性分组。

## 6. AI 生成代码顺序

每次让 AI 写代码时，按下面顺序拆小任务：

1. Pydantic schema 和 TypeScript type 对齐。
2. Repository 或当前 in-memory store。
3. Service。
4. Workflow step。
5. API route。
6. 前端 service。
7. 前端页面或 feature component。
8. 单元测试或集成测试。
9. 文档状态更新。

每次生成代码前必须提供：

- 本次任务目标。
- 涉及的权威文档。
- 输入 schema。
- 输出 schema。
- 验收标准。
- 不允许 AI 自行决定的边界。

## 7. 每次开发的约束

- 不直接在 API route 中写业务流程。
- 不在 service 中拼接 prompt。
- 不让 LLM 原始输出直接入库。
- 不把 ChromaDB 当业务数据库。
- 不把相似性分组说成绝对聚类结论。
- 不输出人格诊断、玄学判断或无依据高级词。
- 不把 V2/V3/V4 能力提前塞进 V1。

### 7.1 AI 辅助开发治理约束

本项目允许 AI 辅助生成代码，但不允许用“兜底、兼容、默认值、mock 或跳过逻辑”掩盖错误。

开发期默认规则：

- 核心业务事实失败必须 fail fast，例如输入不存在、报告不存在、feedback 关联不到 insight、schema 校验失败、数据库写入失败。
- 非核心增强能力可以 graceful degradation，但必须记录为显性降级事件，并说明 original error、fallback action、developer message、userVisible 和测试覆盖。
- Mock / heuristic / placeholder / dev-only 行为必须可见，不能在文档、API 或 UI 中暗示为真实 AI 能力。
- 测试失败时先定位根因，不优先修改测试预期；只有当测试不符合权威设计文档时才允许调整测试。
- 一处实现不抽象；只有稳定重复或当前版本明确需要替换实现时，才新增 interface / factory / registry。
- 未来版本能力只能进入文档、边界提示或预留字段，不提前实现未被当前 iteration 验收的 runtime。

### 7.2 Developer Debug Panel 实施边界

Developer Debug Panel 作为 V2 横向基础设施分阶段推进，不阻断 V2-C 主线。

实施顺序：

1. 先记录治理原则和验收标准。
2. 再补 `fallback_events`、`mock_usage`、`schema_validation`、`boundary_warnings` 等最小调试语义。
3. 最后实现最小开发者面板，只展示 workflow trace、fallback events、mock usage、schema validation、boundary warnings。

明确不做：

- 不做复杂 dashboard。
- 不做实时刷新。
- 不接入 Langfuse / LangSmith / OpenTelemetry runtime。
- 不提前实现 RAG、Agent、MCP 或 ChromaDB runtime。
