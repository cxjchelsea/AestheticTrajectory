# AI 审美形成系统：项目目录结构与代码分层规范

## 1. 文档目的

这份文档定义项目的代码目录结构、分层边界和文件放置规则。

它解决的问题是：

> 让 AI Coding Agent 明确知道代码应该写在哪里，避免 route 巨石化、utils 混乱、prompt 到处散落、schema 不一致。

本项目采用：

- 前端：React + Vite + TypeScript
- 后端：FastAPI
- 业务数据库：PostgreSQL
- 向量库：ChromaDB
- AI 服务：LLM / 多模态模型 API，MVP 可先 mock

当前实现说明：

```text
前端当前使用轻量 state route，没有引入正式路由库。
后端当前同时保留 memory repository 和 database repository，两者通过依赖配置切换。
当前已实现 V1 stable baseline 和 V2-A 历史报告；V2-B profile 模块尚未实现。
```

## 3. 前端目录规范

### 3.1 `frontend/src/app`

负责前端应用初始化。

放置：

- 路由配置
- 全局 provider
- 应用入口配置

不放：

- 业务 API 调用细节
- AI 分析逻辑
- 数据库逻辑

### 3.2 `frontend/src/pages`

负责页面级组件。

建议页面：

```text
pages/
  HomePage.tsx
  UploadPage.tsx
  AnalysisJobPage.tsx
  ReportDetailPage.tsx
  ReportHistoryPage.tsx
```

页面只负责组织 UI 和调用 feature，不直接写复杂业务逻辑。

### 3.3 `frontend/src/components`

负责通用 UI 组件。

示例：

```text
components/
  Button.tsx
  Card.tsx
  LoadingState.tsx
  ErrorMessage.tsx
  EvidenceList.tsx
```

不放：

- 页面专属业务状态
- 后端 API 细节
- prompt 内容

### 3.4 `frontend/src/features`

负责业务功能组件。

建议结构：

```text
features/
  upload/
    UploadForm.tsx
    InputPreviewList.tsx
  analysis/
    JobStatusPanel.tsx
  report/
    ReportSection.tsx
    InsightCard.tsx
    FeedbackPanel.tsx
  history/
    ReportTimeline.tsx
```

feature 可以组合 components、hooks 和 services，但不能直接访问数据库。

### 3.5 `frontend/src/services`

负责调用 FastAPI 后端。

示例：

```text
services/
  apiClient.ts
  inputApi.ts
  analysisJobApi.ts
  reportApi.ts
  feedbackApi.ts
```

规则：

- 所有 HTTP 请求集中在 services。
- 页面和组件不直接写 `fetch`。
- API response 需要经过基础校验或类型约束。

### 3.6 `frontend/src/schemas` 与 `frontend/src/types`

`schemas` 负责前端校验结构，`types` 负责 TypeScript 类型。

规则：

- 类型命名应尽量与后端 Pydantic schema 对齐。
- 如果后端字段变化，前端类型必须同步。
- 不在页面中临时发明 response 结构。

## 4. 后端目录规范

### 4.1 `backend/app/main.py`

FastAPI 应用入口。

只负责：

- 创建 app
- 注册 router
- 注册 middleware
- 启动事件

不放：

- 业务逻辑
- 数据库查询
- AI 调用
- workflow 细节

### 4.2 `backend/app/api`

负责 API 路由。

建议结构：

```text
api/
  routes/
    health.py
    inputs.py
    analysis_jobs.py
    reports.py
    feedback.py
  deps.py
```

API route 只负责：

- 接收 request
- 调用 service
- 返回 response
- 处理 HTTP 层错误

不允许：

- 在 route 中直接调用 LLM。
- 在 route 中直接写复杂 SQL。
- 在 route 中直接写 workflow 全流程。

### 4.3 `backend/app/core`

负责全局配置和基础能力。

示例：

```text
core/
  config.py
  logging.py
  security.py
  errors.py
```

规则：

- 环境变量只在 config 中读取。
- 其他模块通过 settings 对象使用配置。
- 不在业务 service 中直接读取 `.env`。

### 4.4 `backend/app/db`

负责 PostgreSQL 连接和数据库会话。

示例：

```text
db/
  postgres.py
  session.py
  migrations/
```

规则：

- 只处理连接、session、事务。
- 不写具体业务查询。
- 不存放 ChromaDB 逻辑。

### 4.5 `backend/app/models`

负责 PostgreSQL 数据表模型。

示例：

```text
models/
  user.py
  aesthetic_input.py
  analysis_job.py
  input_feature.py
  report.py
  insight.py
  feedback.py
  user_profile.py
  analysis_log.py
```

规则：

- models 表达数据库结构。
- 不写业务流程。
- 不写 prompt。

### 4.6 `backend/app/schemas`

负责 Pydantic schema。

建议结构：

```text
schemas/
  input.py
  analysis_job.py
  feature.py
  embedding.py
  interpretation.py
  report.py
  feedback.py
  profile.py
  common.py
```

规则：

- API request / response 必须使用 schema。
- LLM 输出必须使用 schema 校验。
- workflow step 的输入输出也应定义 schema。

### 4.7 `backend/app/repositories`

负责 PostgreSQL 数据访问。

示例：

```text
repositories/
  input_repository.py
  analysis_job_repository.py
  feature_repository.py
  report_repository.py
  feedback_repository.py
  profile_repository.py
  log_repository.py
```

规则：

- repository 只负责数据库读写。
- 不包含业务判断。
- 不调用 LLM。
- 不调用 ChromaDB，除非是专门的 vector repository。

### 4.8 `backend/app/services`

负责业务逻辑。

示例：

```text
services/
  input_service.py
  analysis_job_service.py
  report_service.py
  feedback_service.py
  profile_service.py
```

规则：

- service 可以调用 repository。
- service 可以调用 workflow。
- service 不直接拼 prompt。
- service 不直接处理底层数据库连接。

### 4.9 `backend/app/ai`

负责 AI 能力封装。

建议结构：

```text
ai/
  prompt_registry.py
  prompt_loader.py
  prompt_renderer.py
  prompts/
    image_features.extract.v1.prompt.md
    text_features.extract.v1.prompt.md
    interpretations.generate.v1.prompt.md
    report.generate.v1.prompt.md
    profile.update.v1.prompt.md
  clients/
    llm_client.py
    vision_client.py
    embedding_client.py
  parsers/
    structured_output_parser.py
  validators/
    prompt_output_validator.py
  mock/
    mock_feature_extractor.py
    mock_embedding.py
    mock_interpretation_generator.py
```

规则：

- `prompt_registry.py` 负责维护 promptId、文件路径、版本、默认模型配置和对应输出 schema。
- `prompt_loader.py` 负责读取 prompt 文件，不负责业务判断。
- `prompt_renderer.py` 负责把 inputData 渲染进 prompt template，不直接调用模型。
- prompt 文件只放在 `ai/prompts`。
- 模型调用统一经过 client。
- LLM 原始输出必须经过 parser 和 validator。
- MVP mock 也要保持与真实输出相同 schema。
- 后续如果加入 Prompt Template 管理，应优先扩展 `prompt_renderer.py`，不要让 service 或 workflow 直接拼接 prompt。
- 后续如果加入 Prompt Versioning 管理，应优先扩展 `prompt_registry.py` 和 observability log，保证每条报告和洞察都能追溯 promptVersion。

### 4.10 `backend/app/workflows`

负责 AI workflow 编排。

示例：

```text
workflows/
  aesthetic_analysis_v1.py
  steps/
    load_inputs.py
    extract_features.py
    generate_embeddings.py
    write_vectors.py
    cluster_inputs.py
    generate_interpretations.py
    generate_report.py
    save_results.py
```

规则：

- workflow 只负责编排，不直接写大量业务细节。
- 每个 step 可以单独测试。
- 每个 step 必须写入 observability log。
- workflow 不直接返回 LLM 原始输出。

### 4.11 `backend/app/vector_store`

负责 ChromaDB。

示例：

```text
vector_store/
  chroma_client.py
  collections.py
  input_vectors.py
  report_vectors.py
  profile_vectors.py
```

规则：

- ChromaDB 只保存向量和检索 metadata。
- PostgreSQL 仍然是业务事实来源。
- 不把完整业务对象只存在 ChromaDB。

### 4.12 `backend/app/storage`

负责文件存储。

示例：

```text
storage/
  local_storage.py
  object_storage.py
```

规则：

- 文件保存和读取统一走 storage service。
- route 不直接操作文件路径。

### 4.13 `backend/app/observability`

负责日志、trace 和指标。

示例：

```text
observability/
  analysis_logger.py
  trace_context.py
  metrics.py
```

规则：

- 每个 workflow step 必须调用 analysis logger。
- promptVersion、modelName、latency、errorType 必须可记录。

## 6. 文件职责边界

### API Route 不做的事

API route 不应该：

- 直接调用 LLM。
- 直接写 SQL。
- 直接操作 ChromaDB。
- 拼接 prompt。
- 编排完整分析流程。

API route 应该：

- 校验 request。
- 调用 service。
- 返回 response。

### Service 不做的事

Service 不应该：

- 直接读取 `.env`。
- 直接维护数据库连接。
- 直接解析 LLM 原始字符串。

Service 应该：

- 组织业务逻辑。
- 调用 repository、workflow、AI client。

### Repository 不做的事

Repository 不应该：

- 写业务判断。
- 调用 AI。
- 调用前端 API。

Repository 应该：

- 封装 PostgreSQL 读写。
- 保持函数职责小而清晰。

### AI Client 不做的事

AI client 不应该：

- 决定业务流程。
- 保存数据库。
- 生成报告结构之外的业务对象。

AI client 应该：

- 调用模型。
- 返回原始或初步结构化结果。
- 交给 parser / validator 处理。

## 7. 命名规范

### Python

- 文件名：`snake_case.py`
- 函数名：`snake_case`
- 类名：`PascalCase`
- Pydantic schema：`CreateAnalysisJobRequest`、`ReportResponse`
- Repository：`ReportRepository`
- Service：`ReportService`

### TypeScript

- 组件名：`PascalCase.tsx`
- hook：`useSomething.ts`
- service：`somethingApi.ts`
- type：`SomethingResponse`

### 数据库

- 表名：复数或清晰实体名，保持统一。
- 字段名：`snake_case`
- JSON 字段：以 `_json` 或明确业务名结尾。

示例：

```text
analysis_jobs
input_features
possible_interpretations
user_profiles
profile_items
profile_evidence
analysis_logs
```

## 8. 环境变量规范

后端：

```text
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_HOST=
POSTGRES_PORT=
POSTGRES_DB=
POSTGRES_DSN=
CHROMA_HOST=
CHROMA_PORT=
UPLOAD_DIR=
LLM_API_KEY=
EMBEDDING_MODEL=
```

前端：

```text
VITE_API_BASE_URL=
```

规则：

- 不提交真实密钥。
- `.env.example` 必须保留字段名。
- 后端密钥不暴露给前端。
- PostgreSQL 可以使用 Navicat、DBeaver 或 DataGrip 可视化连接。

## 9. AI 编码约束

后续让 AI 写代码时，可以使用以下统一约束：

```text
请根据 `08-项目目录结构与代码分层规范.md` 放置代码。

要求：
1. FastAPI route 只处理 HTTP 层，不写复杂业务逻辑。
2. PostgreSQL 访问必须放在 repositories 或 db 层。
3. ChromaDB 访问必须放在 vector_store 层。
4. prompt 文件只能放在 backend/app/ai/prompts。
5. LLM 输出必须通过 schemas 和 validators 校验。
6. workflow step 必须放在 backend/app/workflows/steps。
7. 前端页面不直接 fetch，必须通过 frontend/src/services。
```
