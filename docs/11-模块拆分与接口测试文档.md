# AI 审美形成系统：模块拆分与接口测试文档

## 1. 文档目的

这份文档把 AI 审美形成系统拆分为可开发的工程模块，并定义每个模块的：

- 模块职责
- 输入
- 输出
- 依赖模块
- 测试方式
- 验收标准

说明：

- 本文档是详细模块参考，不是 V1 开发入口。
- V1 具体要做哪些表、API、页面和 mock 输出，以 `16-V1开发收口清单.md` 为准。
- 本文档中 V2 / V3 模块只作为后续扩展参考，不能反向扩大 V1 范围。

整体原则是：

> MVP 先跑通“输入 → 底层特征 → embedding → 相似性分组 → 动态解释 → 报告 → 反馈”的闭环，进阶阶段再加入历史报告、轻量画像、RAG、长期记忆、Function Calling、Observability、知识图谱和 Agent。

## 3. 核心流程

```text
用户创建会话
↓
上传图片 / 文本
↓
保存原始输入
↓
创建分析任务
↓
提取图片 / 文本底层特征
↓
生成 embedding
↓
相似性分组与共性分析
↓
生成动态解释候选
↓
生成审美报告与洞察
↓
用户反馈
↓
保存反馈，V2 再更新用户画像
↓
保存历史报告与日志
```

## 4. MVP 模块定义

## 4.1 用户与会话模块

### 职责

管理用户身份，支持匿名体验和后续登录扩展。

MVP 可以先使用匿名用户 ID，避免登录系统拖慢开发。

### 输入

```json
{
  "clientId": "browser_generated_id",
  "sessionId": "optional_session_id"
}
```

### 输出

```json
{
  "userId": "user_001",
  "isAnonymous": true,
  "createdAt": "2026-05-15T00:00:00Z"
}
```

### 依赖

- 数据库
- 本地 cookie / localStorage

### 测试方式

- 单元测试：无 session 时能创建匿名用户。
- 单元测试：已有 session 时能复用用户。
- 集成测试：上传样本时能正确关联 userId。

### 验收标准

- 同一浏览器多次访问能识别同一匿名用户。
- 不登录也能完成一次完整分析。

## 4.2 审美输入模块

### 职责

接收用户上传的图片和文本，创建审美输入记录。

### 输入

图片输入：

```json
{
  "userId": "user_001",
  "type": "image",
  "file": "binary_file",
  "description": "可选描述"
}
```

文本输入：

```json
{
  "userId": "user_001",
  "type": "text",
  "contentText": "我喜欢的一段文字",
  "description": "可选说明"
}
```

### 输出

```json
{
  "inputId": "input_001",
  "type": "image",
  "fileUrl": "/uploads/input_001.jpg",
  "contentText": null,
  "status": "saved"
}
```

### 依赖

- 文件与内容存储模块
- 用户与会话模块

### 测试方式

- 单元测试：图片类型、大小、格式校验。
- 单元测试：文本为空时拒绝保存。
- 集成测试：批量上传 5-10 个样本后能全部生成 inputId。
- 异常测试：不支持的文件格式返回明确错误。

### 验收标准

- 支持图片和文本输入。
- 每个输入都有唯一 inputId。
- 输入能关联用户和分析任务。

## 4.3 文件与内容存储模块

### 职责

保存图片文件、文本内容和元数据。

### 输入

```json
{
  "inputId": "input_001",
  "type": "image",
  "content": "binary_or_text"
}
```

### 输出

```json
{
  "storagePath": "/uploads/input_001.jpg",
  "contentHash": "sha256_hash",
  "size": 204800
}
```

### 依赖

- 本地文件系统或对象存储
- 数据库

### 测试方式

- 单元测试：同一文件能生成稳定 hash。
- 集成测试：上传后能读取原始文件。
- 异常测试：存储失败时分析任务不应继续。

### 验收标准

- 图片和文本都能持久化。
- 原始输入可追溯。
- 删除输入时能同步处理文件引用。

## 4.4 分析任务模块

### 职责

创建并追踪一次完整分析流程。

### 输入

```json
{
  "userId": "user_001",
  "inputIds": ["input_001", "input_002", "input_003"]
}
```

### 输出

```json
{
  "jobId": "job_001",
  "status": "pending",
  "inputCount": 5
}
```

### 状态

```text
pending
processing
completed
failed
```

### 依赖

- 审美输入模块
- 特征提取模块
- embedding 模块
- 报告生成模块

### 测试方式

- 单元测试：输入数量不足时拒绝创建任务。
- 集成测试：任务能从 pending 流转到 completed。
- 异常测试：任一子模块失败时 job 进入 failed，并记录错误。

### 验收标准

- 能查询任务状态。
- 失败原因可读。
- 任务完成后返回 reportId。

## 4.5 图片底层特征提取模块

### 职责

从图片中提取少量稳定底层特征，不直接生成高层主题。

### 输入

```json
{
  "inputId": "input_001",
  "fileUrl": "/uploads/input_001.jpg"
}
```

### 输出

```json
{
  "inputId": "input_001",
  "type": "image",
  "lowLevelFeatures": {
    "saturation": "low",
    "brightness": "medium_low",
    "colorTemperature": "cool",
    "colorContrast": "low",
    "personPresence": "absent",
    "spatialDensity": "low",
    "compositionComplexity": "medium",
    "textureComplexity": "medium"
  },
  "evidence": [
    "画面主体色彩偏灰蓝",
    "人物缺席",
    "空间元素较少"
  ],
  "modelName": "vision_model_name",
  "confidence": 0.82
}
```

### 依赖

- 文件存储模块
- AI 视觉模型
- 可观测日志模块

### 测试方式

- 单元测试：输出必须符合 JSON schema。
- 固定样本测试：低饱和图片应识别为 low saturation。
- 固定样本测试：人物肖像应识别为 personPresence=center。
- 鲁棒性测试：高饱和二次元、婚礼摄影、meme collage 不应被强行解释成低饱和文艺风。

### 验收标准

- 输出只包含底层特征和证据，不直接输出人格判断。
- 同一图片多次分析结果基本稳定。
- 明显特征识别错误率可接受。

## 4.6 文本底层特征提取模块

### 职责

从文本中提取情绪、叙事和意象等底层结构。

### 输入

```json
{
  "inputId": "input_002",
  "contentText": "一段用户喜欢的文字"
}
```

### 输出

```json
{
  "inputId": "input_002",
  "type": "text",
  "lowLevelFeatures": {
    "sentimentTone": "low",
    "emotionIntensity": "weak",
    "narrativeDensity": "low",
    "concreteness": "mixed",
    "imageryDensity": "medium",
    "perspective": "first_person"
  },
  "evidence": [
    "句子中出现空房间意象",
    "情绪表达克制",
    "没有完整事件链"
  ],
  "modelName": "text_model_name",
  "confidence": 0.78
}
```

### 依赖

- 文本内容存储
- LLM 或文本分类模型

### 测试方式

- 单元测试：空文本、超长文本、乱码文本的处理。
- 固定样本测试：强叙事文本应识别为 high narrativeDensity。
- 固定样本测试：抽象诗性文本应识别为 abstract 或 mixed。
- 一致性测试：同一文本多次输出不应大幅波动。

### 验收标准

- 输出区分底层观察和解释。
- 不直接推断用户人格。
- 每个特征有文本证据。

## 4.7 embedding 模块

### 职责

为图片和文本生成向量表示，构建 latent aesthetic space。

### 输入

```json
{
  "inputId": "input_001",
  "type": "image",
  "content": "fileUrl_or_text"
}
```

### 输出

```json
{
  "inputId": "input_001",
  "embeddingId": "emb_001",
  "modelName": "clip_or_embedding_model",
  "dimension": 768,
  "vector": [0.012, -0.033, 0.218]
}
```

### 依赖

- 输入模块
- 向量存储
- embedding 模型

### 测试方式

- 单元测试：向量维度符合模型定义。
- 单元测试：同一输入重复生成向量稳定。
- 集成测试：向量能被写入并读取。
- 相似度测试：相似样本距离应小于不相似样本。

### 验收标准

- 每个输入都有 embedding。
- embedding 可用于相似度计算和相似性分组。
- 模型版本可追踪。

## 4.8 相似性分组与共性分析模块

### 职责

基于 embedding 和底层特征，发现输入之间的群组、共性和差异。

### 输入

```json
{
  "jobId": "job_001",
  "inputs": [
    {
      "inputId": "input_001",
      "features": {},
      "embeddingId": "emb_001"
    }
  ]
}
```

### 输出

```json
{
  "jobId": "job_001",
  "similarityGroups": [
    {
      "groupId": "group_001",
      "sampleIds": ["input_001", "input_003"],
      "commonFeatures": ["low_saturation", "low_spatial_density"],
      "representativeInputId": "input_001",
      "distanceSummary": {
        "intraClusterDistance": 0.21,
        "nearestClusterDistance": 0.48
      }
    }
  ],
  "globalPatterns": ["low_saturation", "person_absent"],
  "outliers": ["input_005"]
}
```

### 依赖

- 特征提取模块
- embedding 模块

### 测试方式

- 单元测试：输入不足时返回单组或跳过分组。
- 固定样本测试：明显同风格样本应进入同一相似性组。
- 稳定性测试：同一批输入重复相似性分组结果大致稳定。
- 异常测试：离群样本能被识别。

### 验收标准

- 相似性分组结果能解释。
- 每个 similarity group 有共同底层特征。
- 不把分组名称当成固定事实。

## 4.9 动态解释候选模块

### 职责

基于底层特征、相似性分组结果和证据，生成多个 possibleInterpretations。

### 输入

```json
{
  "jobId": "job_001",
  "similarityGroups": [],
  "globalPatterns": [],
  "userHistory": null,
  "knowledgeContext": null
}
```

### 输出

```json
{
  "interpretations": [
    {
      "interpretationId": "interp_001",
      "name": "结构化疏离",
      "target": "group_001",
      "confidence": 0.64,
      "evidence": ["low_saturation", "person_absent", "low_spatial_density"],
      "alternativeNames": ["冷感空间偏好"],
      "uncertainty": "这也可能只是近期对简洁空间的偏好。"
    }
  ]
}
```

### 依赖

- 相似性分组与共性分析模块
- RAG 审美知识库模块，进阶
- 用户历史检索模块，进阶

### 测试方式

- 单元测试：每个解释必须有证据。
- 单元测试：每个解释至少提供一个替代解释。
- 去作者中心化测试：高饱和、二次元、Y2K、meme 样本不能全部被解释成“疏离、克制、留白”。
- 人工评审：解释是否与输入证据匹配。

### 验收标准

- 不把高层解释当事实。
- 输出多个候选解释。
- 每个解释都有 evidence 和 uncertainty。

## 4.10 报告生成模块

### 职责

将结构化分析结果转化为用户可读的审美报告。

### 输入

```json
{
  "jobId": "job_001",
  "features": [],
  "similarityGroups": [],
  "interpretations": [],
  "contradictions": [],
  "reportTemplateVersion": "v1"
}
```

### 输出

```json
{
  "reportId": "report_001",
  "summary": "这组输入呈现出低饱和、人物缺席和空间密度低的倾向。",
  "sections": {
    "lowLevelFeatures": [],
    "similarityGroups": [],
    "possibleInterpretations": [],
    "tensions": [],
    "insights": []
  },
  "markdown": "# 你的近期审美剖析..."
}
```

### 依赖

- 动态解释候选模块
- 输出报告模板
- LLM

### 测试方式

- 单元测试：报告结构符合 schema。
- 单元测试：每条洞察引用已有证据。
- 快照测试：固定输入生成报告结构不应大幅变化。
- 人工评审：输出是否像解释型报告，而不是心理测试。

### 验收标准

- 报告包含底层特征、相似性分组、可能解释、张力、洞察和反馈入口。
- 没有无证据结论。
- 没有人格诊断和玄学表达。

## 4.11 洞察反馈模块

### 职责

收集用户对单条洞察或解释的反馈。

### 输入

```json
{
  "userId": "user_001",
  "insightId": "insight_001",
  "interpretationId": "interp_001",
  "rating": "seen",
  "comment": "这个很像我"
}
```

### 输出

```json
{
  "feedbackId": "feedback_001",
  "saved": true
}
```

### rating 枚举

```text
not_me
interesting
accurate
seen
```

### 依赖

- 报告生成模块
- 用户画像模块

### 测试方式

- 单元测试：非法 rating 被拒绝。
- 集成测试：反馈保存后能查询。
- 集成测试：反馈能影响基础用户画像。

### 验收标准

- 用户能对每条洞察反馈。
- 反馈能关联到 insight 和 interpretation。
- 反馈可用于后续画像更新。

## 4.12 基础用户画像模块

### 职责

根据历史报告和用户反馈维护轻量用户画像。

MVP 只做基础版本，不做复杂推荐。

### 输入

```json
{
  "userId": "user_001",
  "reportId": "report_001",
  "feedback": []
}
```

### 输出

```json
{
  "userId": "user_001",
  "profile": {
    "acceptedInterpretations": ["结构化疏离"],
    "rejectedInterpretations": ["工业化孤独感"],
    "stableLowLevelFeatures": ["low_saturation"],
    "updatedAt": "2026-05-15T00:00:00Z"
  }
}
```

### 依赖

- 洞察反馈模块
- 报告历史模块

### 测试方式

- 单元测试：认可解释进入 acceptedInterpretations。
- 单元测试：否定解释进入 rejectedInterpretations。
- 集成测试：后续报告不应反复强推被否定解释。

### 验收标准

- 能保存用户认可和否定的解释。
- 能记录稳定底层特征。
- 不把单次反馈直接当成永久偏好。

## 4.13 报告历史模块

### 职责

保存并展示用户过往分析报告。

### 输入

```json
{
  "userId": "user_001",
  "reportId": "report_001"
}
```

### 输出

```json
{
  "reports": [
    {
      "reportId": "report_001",
      "createdAt": "2026-05-15T00:00:00Z",
      "summary": "低饱和、人物缺席、空间密度低",
      "inputCount": 8
    }
  ]
}
```

### 依赖

- 报告生成模块
- 用户模块

### 测试方式

- 单元测试：报告按时间倒序返回。
- 集成测试：用户只能看到自己的报告。
- 集成测试：报告详情能完整还原结构化数据。

### 验收标准

- 用户可查看历史报告。
- 历史报告可用于后续 personalized retrieval。

## 4.14 基础可观测日志模块

### 职责

记录一次分析过程中关键中间结果，便于调试和评估。

### 输入

```json
{
  "jobId": "job_001",
  "stage": "feature_extraction",
  "modelName": "vision_model",
  "input": {},
  "output": {},
  "durationMs": 1200,
  "status": "success"
}
```

### 输出

```json
{
  "logId": "log_001",
  "saved": true
}
```

### 依赖

- 所有 AI 子模块

### 测试方式

- 单元测试：每个阶段能写入日志。
- 集成测试：失败任务能查到失败阶段。
- 追踪测试：一条洞察能追溯到输入、特征、解释和 prompt 版本。

### 验收标准

- 每个分析任务都有基础 trace。
- 关键模型版本和 prompt 版本可查。
- 失败原因可定位。

## 4.15 Prompt 管理与模型调用模块

### 职责

统一管理 prompt 文件、prompt metadata、模型调用、结构化输出解析和输出校验。

这个模块不是“让 AI 自动生成提示词”，而是把 `10-Prompt Contract 与结构化输出规范.md` 中定义的 prompt contract 转化为后端可调用的工程能力。

它负责：

- 根据 `promptId` 查找 prompt 文件。
- 读取 prompt 内容。
- 绑定 prompt version。
- 将业务输入渲染进 prompt。
- 调用 LLM / 多模态模型 client。
- 解析模型输出。
- 使用 Pydantic schema 校验输出。
- 检查 evidence、uncertainty、禁止表达和安全边界。
- 返回结构化结果给 workflow step。
- 把 promptVersion、modelName、latency、token usage 写入日志。

### 输入

```json
{
  "promptId": "interpretations.generate.v1",
  "inputData": {
    "jobId": "job_001",
    "similarityGroups": [],
    "globalPatterns": [],
    "recentFeatures": [],
    "userHistory": []
  },
  "modelConfig": {
    "modelName": "mock-llm",
    "temperature": 0.2,
    "maxTokens": 2000
  }
}
```

### 输出

```json
{
  "promptId": "interpretations.generate.v1",
  "promptVersion": "v1",
  "modelName": "mock-llm",
  "status": "success",
  "parsedOutput": {},
  "validationResult": {
    "schemaValid": true,
    "policyValid": true,
    "evidenceValid": true
  },
  "usage": {
    "inputTokens": 1200,
    "outputTokens": 800,
    "latencyMs": 2300
  }
}
```

失败输出：

```json
{
  "promptId": "interpretations.generate.v1",
  "status": "failed",
  "errorType": "INVALID_JSON | SCHEMA_INVALID | POLICY_VIOLATION | MISSING_EVIDENCE | MODEL_ERROR",
  "retryable": true,
  "rawOutputStored": true
}
```

### 依赖

- Prompt 文件：`backend/app/ai/prompts`
- Prompt Contract：`10-Prompt Contract 与结构化输出规范.md`
- Pydantic schema
- LLM client / vision client / embedding client
- 基础可观测日志模块

### 典型内部组件

```text
prompt_registry.py
  维护 promptId、文件路径、版本、适用 schema、默认模型配置。

prompt_loader.py
  根据 promptId 读取 prompt 文件。

prompt_renderer.py
  将 inputData 注入 prompt 模板。

llm_client.py
  统一调用 LLM 或多模态模型。

structured_output_parser.py
  解析模型返回的 JSON 或结构化输出。

prompt_output_validator.py
  校验 schema、evidence、uncertainty 和禁止表达。
```

### 测试方式

- 单元测试：`promptId` 能正确映射到 prompt 文件。
- 单元测试：prompt loader 能读取指定版本 prompt。
- 单元测试：renderer 能把输入 JSON 注入模板。
- 单元测试：parser 能处理合法 JSON、非法 JSON 和模型包裹文本。
- 单元测试：validator 能拦截人格诊断、玄学表达、缺少 evidence 的输出。
- 集成测试：mock LLM 输出能通过完整调用链并返回结构化结果。
- 日志测试：每次调用都记录 promptVersion、modelName、latency 和 token usage。

### 验收标准

- workflow step 不直接拼 prompt。
- workflow step 不直接解析 LLM 原始输出。
- 所有 prompt 调用都经过统一 loader、client、parser、validator。
- 所有 AI 输出在保存到 PostgreSQL 前必须通过 schema 校验。
- 失败时返回结构化错误，并写入 `analysis_logs`。

### 进阶扩展

MVP 阶段只需要“Prompt 管理 / 加载模块”，不需要复杂后台管理。

后续可以继续扩展为：

1. Prompt Template 管理
   - 把 prompt 拆成 system、developer、user、examples、output_schema 等片段。
   - 支持不同模型使用不同模板。
   - 支持同一 prompt 在不同语言或报告风格下渲染。

2. Prompt Versioning 管理
   - 记录每次 prompt 修改的版本。
   - 把 report、insight、interpretation 与 promptVersion 绑定。
   - 支持对比不同 prompt 版本的输出质量。
   - 支持回滚到旧 prompt。

3. Prompt Evaluation
   - 使用固定样本集测试 prompt 输出稳定性。
   - 检查 JSON 通过率、evidence 覆盖率、越界表达率和用户反馈认可率。

## 5. 进阶模块定义

## 5.1 Function Calling / Workflow 编排模块

### 职责

将固定流程拆成可调用工具，让系统更稳定、可调试。

### 输入

```json
{
  "jobId": "job_001",
  "workflow": "aesthetic_analysis_v1",
  "inputIds": []
}
```

### 输出

```json
{
  "jobId": "job_001",
  "steps": [
    "analyze_image_features",
    "generate_embedding",
    "group_inputs",
    "generate_report"
  ],
  "status": "completed"
}
```

### 测试方式

- 单元测试：每个 function 入参和出参符合 schema。
- 集成测试：workflow 能按顺序执行。
- 异常测试：某一步失败后能停止并记录错误。

### 验收标准

- 不依赖单个大 prompt 完成所有分析。
- 每一步可单独测试和重跑。

## 5.2 personalized retrieval 模块

### 职责

检索用户历史输入、报告、解释和反馈，用于长期对比。

### 输入

```json
{
  "userId": "user_001",
  "currentFeatures": ["low_saturation", "person_absent"],
  "topK": 5
}
```

### 输出

```json
{
  "memories": [
    {
      "reportId": "report_001",
      "matchedFeatures": ["low_saturation"],
      "similarity": 0.82,
      "acceptedInterpretations": ["冷感空间偏好"]
    }
  ]
}
```

### 测试方式

- 相似度测试：相似历史报告排序靠前。
- 权限测试：不能检索其他用户历史。
- 反馈测试：被否定解释不应作为正向记忆强推。

### 验收标准

- 能找到相似历史。
- 能区分被认可和被否定的解释。

## 5.3 RAG 审美知识库模块

### 职责

检索审美知识、风格资料和解释语言，增强报告质量。

### 输入

```json
{
  "queryFeatures": ["high_saturation", "dense_composition", "collage"],
  "queryText": "高饱和、拼贴、meme 风格如何解释",
  "topK": 5
}
```

### 输出

```json
{
  "documents": [
    {
      "docId": "doc_001",
      "title": "meme collage 视觉特征",
      "snippet": "拼贴、高密度符号、流行文化引用...",
      "score": 0.76
    }
  ]
}
```

### 测试方式

- 检索相关性测试：查询 meme collage 不应返回工业风为主的资料。
- 引用测试：报告中使用知识库内容时应可追溯。
- 污染测试：不相关知识不能被强行写入报告。

### 验收标准

- 检索结果与当前特征相关。
- RAG 只增强解释，不替代用户输入证据。

## 5.4 Evaluation 指标模块

### 职责

统计系统质量指标。

### 输入

```json
{
  "reportId": "report_001",
  "feedback": [],
  "trace": []
}
```

### 输出

```json
{
  "metrics": {
    "insightHitRate": 0.42,
    "evidenceCoverage": 0.91,
    "alternativeInterpretationCoverage": 0.84,
    "rejectedInterpretationRecurrence": 0.05
  }
}
```

### 测试方式

- 单元测试：指标计算正确。
- 数据测试：空反馈时不产生错误。
- 回归测试：优化后指标不应明显下降。

### 验收标准

- 能统计洞察命中率。
- 能统计证据覆盖率。
- 能发现被否定解释反复出现的问题。

## 5.5 报告对比与审美轨迹模块

### 职责

比较多次报告，生成初步审美变化说明。

### 输入

```json
{
  "userId": "user_001",
  "reportIds": ["report_001", "report_002"]
}
```

### 输出

```json
{
  "changes": [
    {
      "type": "feature_shift",
      "from": "warm_color",
      "to": "cool_color",
      "evidence": ["report_001", "report_002"]
    }
  ],
  "summary": "最近两次输入中，冷色调和人物缺席比例上升。"
}
```

### 测试方式

- 单元测试：两个报告能比较共同特征差异。
- 集成测试：历史报告不足时返回“数据不足”。
- 人工评审：变化说明不能过度解释。

### 验收标准

- 能生成基于证据的变化说明。
- 不把两次输入直接上升为长期人格变化。

## 6. 高级扩展模块

## 8. MVP 开发顺序建议

### 第 1 步：基础输入闭环

开发：

- 用户与会话模块
- 审美输入模块
- 文件与内容存储模块
- 分析任务模块

验收：

- 用户能上传图片和文本。
- 能创建分析任务。

### 第 2 步：特征与 embedding

开发：

- 图片底层特征提取模块
- 文本底层特征提取模块
- embedding 模块

验收：

- 每个输入都有 features 和 embedding。

### 第 3 步：分析与解释

开发：

- 相似性分组与共性分析模块
- 动态解释候选模块

验收：

- 一组输入能生成 similarityGroups 和 possibleInterpretations。

### 第 4 步：报告与反馈

开发：

- 报告生成模块
- 洞察反馈模块
- 报告历史模块，V2

验收：

- 用户能看到报告并反馈。
- V1 报告能保存并可通过报告详情查看；历史列表放入 V2。

### 第 5 步：质量与可观测

开发：

- 基础可观测日志模块
- 基础 Evaluation 指标，V2

验收：

- 洞察有 trace。
- 用户反馈能被保存，V2 再影响画像。
- V1 至少能记录基础分析日志。

## 9. MVP 总体验收标准

MVP 可以认为完成，如果满足：

- 用户能上传 5-10 个图片 / 文本样本。
- 系统能提取少量稳定底层特征。
- 每个输入能生成 embedding。
- 系统能生成可解释的相似性分组，样本不足时能明确跳过分组。
- 系统能生成多个 possibleInterpretations。
- 报告中每条洞察有证据和不确定性。
- 用户能对洞察反馈。
- 报告能保存，历史列表可放入 V2。
- 分析过程有基础日志。
- 至少一组非开发者偏好的样本能得到合理解释。

## 10. 最小可开发边界

如果时间很紧，第一版只做这些模块：

1. 审美输入模块
2. 图片 / 文本底层特征提取模块
3. embedding 模块
4. 相似性分组与共性分析模块
5. 动态解释候选模块
6. 报告生成模块
7. 洞察反馈模块

暂缓：

- 登录系统
- RAG
- Agent
- 知识图谱
- MCP
- 音乐 / 视频
- 高级可视化

第一版最重要的不是功能多，而是证明：

> 系统能从输入中提取稳定结构，并生成用户觉得有依据、有共鸣、不过度玄学的解释。
