# AI 审美形成系统：审美表征体系文档

## 1. 文档目的

这份文档不再把系统定义为一个固定“审美标签库”，而是定义为一个：

> 审美表征体系（Aesthetic Representation System）。

它的目标不是预先穷尽所有审美标签，而是建立一套可中间检查、可调试、可扩展的审美 representation layer。

系统应该先提取相对稳定的底层特征，再通过 embedding、相似性分组和 LLM 动态生成解释语言。

当前实现边界：

```text
V1 / V2-A 已实现：底层特征 schema、embedding 生成、当前 job 内相似性分组、动态解释候选、报告和反馈、历史报告回看。
V2-B planned：轻量画像和 profile evidence。
V2-C / V2-D planned：反馈权重、画像更新、近期变化提示。
V3+ planned：personalized retrieval、RAG、Agent、知识图谱和 MCP。
```

核心转变是：

```text
固定标签库
↓
底层特征 pipeline + 动态解释生成
```

## 2. 为什么不能只做固定标签库

固定标签库容易带来三个问题。

### 2.1 ontology 爆炸

如果不断扩展：

- 更多风格
- 更多主题
- 更多气质
- 更多张力
- 更多审美词

最后会形成一个无限扩张的审美词典，难以维护，也难以验证。

### 2.2 开发者审美污染

如果标签主要来自开发者个人偏好，系统会过拟合某一种审美语言。

例如，当前很多标签倾向于：

- 低饱和
- 工业
- 空旷
- 留白
- 疏离
- 克制
- 未完成

这些偏向文艺、都市、当代视觉文化。

如果用户上传：

- 高饱和二次元
- Y2K
- hyperpop
- 朋克
- 婚礼摄影
- 美式 suburban
- meme collage
- 甜美元气风

固定标签库可能会理解力下降，甚至强行把不适合的解释套上去。

### 2.3 把解释语言误认为真实结构

底层特征可能是相对真实的：

```text
低饱和 + 人物缺席 + 空旷空间
```

但高层主题只是解释：

```text
工业化孤独感
```

系统不能把“工业化孤独感”当成事实。更准确的做法是：

```json
{
  "features": ["低饱和", "人物缺席", "空旷空间"],
  "possibleInterpretations": ["工业化孤独感", "结构化疏离", "冷感空间偏好"]
}
```

## 3. 核心原则

### 3.1 区分 representation 和 interpretation

系统需要明确区分：

- representation：输入中可观察、可比较、可计算的特征。
- interpretation：基于这些特征生成的解释语言。

例如：

| 类型 | 示例 | 稳定性 |
| --- | --- | --- |
| 底层特征 | 饱和度、色温、空间密度、人物比例 | 相对稳定 |
| 中层标签 | 极简、工业、复古、二次元、朋克 | 半主观 |
| 高层解释 | 工业化孤独感、未完成的温柔 | 高度主观 |

### 3.2 底层特征尽量稳定

底层特征应该尽量可观察、可计算、可复用。

它们是系统真正的 representation layer。

### 3.3 高层主题动态生成

高层主题不应该固定成枚举值，而应该由系统根据输入特征动态命名。

系统可以保留历史中生成过的主题，但不能把它们当成唯一合法标签。

### 3.4 允许多种解释并存

同一组特征可以有多个解释。

例如：

```text
高饱和 + 快速切换 + 拼贴 + 流行符号
```

可能解释为：

- meme collage
- hyperpop 视觉
- 网感拼贴
- 高刺激视觉偏好

系统不应该强行只给一个结论。

### 3.5 用户反馈验证解释

高层解释是否成立，最终要看用户反馈。

用户认可的解释可以进入长期画像；用户否定的解释应降低权重。

## 4. 三层表征结构

### 4.1 第一层：底层感知特征

底层特征是最稳定的层。

它描述输入“看起来是什么样”，尽量不解释用户人格或审美意义。

第一版建议只做少量核心特征：

- 色彩
- 饱和度
- 明度
- 色温
- 人物存在
- 空间密度
- 构图复杂度
- 纹理复杂度
- 文本情绪
- 文本叙事密度

### 4.2 第二层：中层风格结构

中层标签用于组织输入，但仍然要保持开放。

例如：

- 极简
- 工业
- 复古
- 自然
- 未来感
- 二次元
- Y2K
- 朋克
- meme collage
- 婚礼摄影
- 甜美元气
- 赛博霓虹

中层标签可以来自模型识别、RAG 知识库、用户自定义或 LLM 动态命名。

### 4.3 第三层：高层解释主题

高层主题是解释语言，不是事实标签。

例如：

- 工业化孤独感
- 结构化疏离
- 未完成的温柔
- 高刺激网感
- 甜美元气叙事
- 夸张自我表达
- 梦幻逃逸感

这些主题应该保存为 possibleInterpretations，而不是固定 theme。

## 5. MVP 底层特征 Schema

为了避免第一版过度复杂，MVP 只做最小可行特征集合。

每个底层特征都必须用统一结构保存：

```json
{
  "value": "低",
  "confidence": 0.82,
  "evidence": ["画面整体以低纯度灰蓝色为主"]
}
```

规则：

- `value` 是分档或分类结果。
- `confidence` 表示模型对该字段的把握程度，范围为 0-1。
- `evidence` 必须指向输入中的可观察内容。
- 没有证据时，该字段应返回 `unknown`，而不是强行判断。

### 5.1 图片底层特征

第一版只提取：

| 特征 | 类型 | 示例 |
| --- | --- | --- |
| saturation | 数值 / 分档 | 低、中、高 |
| brightness | 数值 / 分档 | 低、中、高 |
| color_temperature | 分档 | 冷、暖、中性 |
| color_contrast | 分档 | 弱、中、强 |
| person_presence | 分档 | 缺席、弱存在、中心 |
| spatial_density | 分档 | 空旷、中等、密集 |
| composition_complexity | 分档 | 简洁、中等、复杂 |
| texture_complexity | 分档 | 平滑、中等、复杂 |
| mood_atmosphere | 分档 | 冷静、明快、压抑、柔和、紧张 |

### 5.2 文本底层特征

第一版只提取：

| 特征 | 类型 | 示例 |
| --- | --- | --- |
| sentiment_tone | 分档 | 明亮、中性、低沉 |
| emotion_intensity | 分档 | 弱、中、强 |
| narrative_density | 分档 | 低、中、高 |
| concreteness | 分档 | 抽象、混合、具体 |
| imagery_density | 分档 | 低、中、高 |
| rhythm | 分档 | 短促、平缓、跳跃、铺陈 |
| time_orientation | 分类 | 过去、现在、未来、循环、模糊 |
| spatial_reference | 分档 | 弱、中、强 |
| subject_distance | 分类 | 贴近自我、旁观、去主体 |

### 5.3 embedding 特征

除人工可解释特征外，每个输入还应保存 embedding。

embedding 负责捕捉难以手工命名的潜在结构：

- 视觉相似性
- 情绪相似性
- 风格相似性
- 跨模态接近关系

这部分构成 latent aesthetic space。

## 6. 开放式标签生成

系统不应只从预定义标签中选择，而应采用：

```text
发现结构
↓
动态命名
↓
多解释候选
↓
用户反馈验证
```

### 6.1 标签生成输入

LLM 生成标签时应接收：

- 底层特征
- embedding 相似性分组结果
- 输入证据
- 历史用户反馈
- 可用审美知识
- 禁止人格化规则

### 6.2 标签生成输出

推荐结构：

```json
{
  "groupId": "group_01",
  "observedFeatures": [
    "低饱和",
    "人物缺席",
    "空间密度低"
  ],
  "candidateLabels": [
    {
      "label": "冷感空间",
      "type": "style_structure",
      "confidence": 0.78,
      "evidence": ["image_01", "image_03"]
    }
  ],
  "possibleInterpretations": [
    {
      "interpretation": "结构化疏离",
      "confidence": 0.62,
      "evidence": ["低饱和", "人物缺席", "空间密度低"],
      "uncertainty": "这也可能只是用户近期偏好简洁构图，而不是稳定的疏离主题。"
    }
  ]
}
```

## 7. 高层主题的保存方式

不要这样保存：

```json
{
  "theme": "工业化孤独感"
}
```

应该这样保存：

```json
{
  "featurePattern": {
    "visual": ["低饱和", "空间密度低", "人物缺席"],
    "textual": ["低叙事密度", "低情绪强度"]
  },
  "possibleInterpretations": [
    {
      "name": "工业化孤独感",
      "confidence": 0.64,
      "userFeedback": null
    },
    {
      "name": "结构化疏离",
      "confidence": 0.58,
      "userFeedback": null
    }
  ]
}
```

这样可以避免把解释语言固化为真实结构。

## 8. 张力分析

张力仍然很重要，但也要区分特征和解释。

### 8.1 底层张力

例如：

- 高饱和 vs 低饱和
- 高密度 vs 低密度
- 人物中心 vs 人物缺席
- 强叙事 vs 弱叙事
- 复杂构图 vs 简洁构图

### 8.2 解释型张力

例如：

- 秩序 vs 失控
- 温柔 vs 冷硬
- 亲密 vs 疏离
- 日常 vs 异化
- 甜美 vs 攻击性
- 怀旧 vs 未来

解释型张力必须来自底层特征和用户输入证据。

## 9. 去作者中心化测试

为了避免系统只适合开发者自己的审美，需要建立多样化测试集。

### 9.1 必测风格

至少包含：

- 低饱和文艺风
- 高饱和二次元
- Y2K
- 朋克
- hyperpop
- meme collage
- 婚礼摄影
- 美式 suburban
- 甜美元气风
- 赛博霓虹
- 极简设计
- 自然松弛风

### 9.2 测试目标

观察：

- 哪些底层特征仍然有效
- 哪些中层标签覆盖不足
- 哪些高层解释过于主观
- 系统是否把所有输入都解释成同一套文艺语言
- 用户是否认可动态生成的解释

## 10. 标签与知识图谱的关系

知识图谱不应该从高层解释直接开始。

推荐顺序：

```text
底层特征关系
↓
中层风格关系
↓
高层解释关系
```

示例：

```text
高饱和 → 可能关联 → 高刺激感
高密度构图 → 可能关联 → 信息过载感
拼贴元素 → 可能关联 → meme collage
meme collage + 高饱和 + 快节奏符号 → 可能解释为 → 网感高刺激审美
```

所有关系都应该带：

- 证据
- 来源
- 权重
- 用户反馈

## 11. 禁用规则

禁止：

- 把高层解释当事实
- 把用户审美解释成人格诊断
- 用开发者偏好的词强行解释所有输入
- 只从预定义标签中选择，不允许新标签出现
- 无证据生成主题

推荐：

- 输出多个可能解释
- 标注不确定性
- 让用户反馈验证
- 保留底层特征作为主要结构
- 将高层解释视为可变语言

## 12. 结论

这个系统真正稳定的部分不是“审美词典”，而是：

> 底层特征提取、embedding 审美空间、相似性关系、用户反馈与动态解释生成。

因此，下一步不应该继续扩展 ontology，而应该建立第一版 feature pipeline。

第一版只需要做到：

- 提取少量稳定底层特征
- 跑通 embedding
- 做小样本相似性分组
- 动态生成关键词、1 个张力、2 个可能主题
- 找用户测试哪些解释真正有共鸣

这会比继续增加标签更有价值。
