# AI 审美形成系统：数据结构与系统架构文档

## 1. 文档目的

这份文档定义系统的技术架构、核心模块、数据流和主要数据结构。

它服务于两个目标：

1. 指导 MVP 开发。
2. 为后续长期记忆、审美轨迹和多模态扩展预留结构。

## 2. 系统总体架构

MVP 可以采用简单的 Web 应用架构：

```text
前端应用
↓
FastAPI 后端 API
↓
AI Workflow / Function Calling 层
↓
AI 分析服务
↓
PostgreSQL 数据库 / 文件存储 / ChromaDB 向量库 / 个人记忆
↓
报告生成 / 反馈更新 / 可观测日志
```

推荐技术栈：

- 前端：React
- 样式：Tailwind
- 后端：FastAPI
- 数据库：PostgreSQL
- ORM / 数据访问：SQLAlchemy + psycopg，或 SQLAlchemy + asyncpg
- 文件存储：本地存储 / S3 兼容存储
- 向量存储：ChromaDB
- AI：OpenAI / Gemini / Qwen VL / CLIP / SigLIP
- 进阶 AI 编排：Function Calling / workflow orchestration
- 进阶检索：RAG 审美知识库 / personalized memory retrieval
- 远期扩展：知识图谱 / MCP 外部上下文接入 / 审美观察 Agent

说明：

- React 只负责前端页面与交互。
- FastAPI 负责业务 API、分析任务编排、AI 服务调用和文件处理。
- PostgreSQL 保存业务数据、报告、反馈和日志，是业务事实来源。
- ChromaDB 保存输入向量和检索 metadata，用于相似度检索；MVP 不把报告、洞察或用户画像向量化作为必做项。
- PostgreSQL 可以用 Navicat、DBeaver 或 DataGrip 可视化管理。

### 2.1 为什么选择 PostgreSQL

本项目将 PostgreSQL 作为业务数据库，而不是 MySQL、Oracle 或其他关系型数据库，主要基于以下判断。

项目数据形态并不是纯表单业务数据，而是同时包含结构化字段和 AI 生成的半结构化结果：

```text
输入样本
分析任务
底层特征 feature_json
报告 report_json
解释 evidence_json
洞察 feedback
workflow analysis_logs
```

PostgreSQL 的优势：

- 支持成熟的关系型建模，适合保存 users、inputs、jobs、reports、feedback、logs 等业务事实。
- 原生支持 `JSONB`，适合保存 `feature_json`、`report_json`、`evidence_json` 这类结构会演进的 AI 输出快照。
- 与 Python / FastAPI / SQLAlchemy / Alembic 组合成熟，便于做 schema migration、repository 分层和测试。
- 既能保存稳定业务表，也能容纳后续 V2 / V3 的历史报告、轻量画像、审美轨迹和检索 metadata。
- 开源、部署成本低，适合当前 MVP 到中期产品演进。
- 与 ChromaDB 职责互补：PostgreSQL 保存业务事实，ChromaDB 保存向量和相似度检索 metadata，边界清晰。

不优先选择 MySQL 的原因：

- MySQL 可以胜任常规业务数据保存，但本项目会频繁保存 AI 输出的结构化快照和 evidence 结构；PostgreSQL 的 `JSONB`、索引能力和半结构化数据处理更贴合当前方向。
- 当前项目文档、V1-D 迁移和后端实现已经围绕 PostgreSQL、SQLAlchemy、psycopg、Alembic 建立；改成 MySQL 会增加迁移脚本、驱动、字段类型和验收标准的返工。
- MySQL 不是不能用，而是对本项目“结构化业务数据 + 半结构化 AI 输出 + 后续长期记忆”的组合来说，不是当前最省力的默认选型。

不优先选择 Oracle 的原因：

- Oracle 更适合大型企业级系统、强治理和既有 Oracle 基础设施场景。
- 当前项目处于 MVP / V1 阶段，不需要 Oracle 的企业级能力和运维复杂度。
- Oracle 的本地开发、授权、部署和团队使用成本明显高于 PostgreSQL，不适合作为当前个人/小团队产品验证阶段的默认数据库。

其他数据库的边界：

- SQLite 适合作为自动测试数据库，不作为业务 runtime 数据库。
- ChromaDB 只负责向量存储和相似度检索，不保存业务报告、反馈和任务状态。
- 文档型数据库可以保存 JSON，但本项目仍需要清晰的业务关系、迁移和事务边界，因此不作为 V1 默认业务数据库。

结论：

```text
PostgreSQL 是当前最平衡的选择：
既能承担业务事实来源，又能保存 AI 分析产生的半结构化 JSON 快照，
同时保持开源、低成本、易迁移和与 FastAPI 技术栈的良好兼容。
```

## 3. 核心模块

### 3.1 MVP 必做模块

MVP 先跑通“输入 → 底层特征 → embedding → 相似性分组 → 动态解释 → 报告 → 反馈”的闭环。

本阶段包含：

1. 用户与会话模块
2. 审美输入模块
3. 文件与内容存储模块
4. 分析任务模块
5. 图片底层特征提取模块
6. 文本底层特征提取模块
7. embedding 模块
8. 相似性分组与共性分析模块
9. 动态解释候选模块
10. 报告生成模块
11. 洞察反馈模块
12. 基础可观测日志模块
13. Prompt 管理与模型调用模块

以下模块从 V2 开始实现，不属于精简 MVP 必做项：

- 报告历史模块
- 基础用户画像模块
- 报告对比模块

这些模块的详细职责、输入、输出、依赖、测试方式和验收标准见 `11-模块拆分与接口测试文档.md`。

### 3.2 进阶模块

进阶阶段用于提升系统稳定性、个性化能力和可评估性。

本阶段包含：

1. Function Calling / Workflow 编排模块
2. personalized retrieval 模块
3. RAG 审美知识库模块
4. Evaluation 指标模块
5. 报告对比与审美轨迹模块

其中，RAG 与 personalized retrieval 的职责不同：

- 审美知识库 RAG：检索外部或自建知识，用于增强解释质量。
- personalized retrieval：检索用户自己的历史记录，用于长期对比和个性化。

### 3.3 高级扩展模块

高级扩展模块不属于 MVP 必需项，用于增强长期能力和展示深度。

本阶段包含：

1. 审美知识图谱模块
2. 审美观察 Agent 模块
3. MCP 外部上下文模块
4. 多模态扩展模块

MCP 外部上下文模块可接入：

- Pinterest
- Are.na
- Spotify
- Notion
- 豆瓣
- 小红书收藏
- 本地相册

## 4. 核心数据流

### 4.1 单次分析流程

```text
用户上传样本
↓
保存原始样本
↓
创建分析任务
↓
调用 AI 提取单样本特征
↓
生成 embedding
↓
保存底层特征与向量
↓
对本次样本进行相似性分组
↓
分析共性、差异和动态解释候选
↓
生成审美报告
↓
保存报告与洞察
↓
用户阅读并反馈
```

### 4.2 长期演化流程

```text
多次历史报告
↓
底层特征频率统计
↓
embedding 相似性分组中心比较
↓
解释候选出现与消退分析
↓
用户反馈加权
↓
生成审美变化说明
```

## 5. 数据表设计

### 5.1 users：用户表

保存用户基础信息。

```text
id
name
email
avatar_url
created_at
updated_at
```

MVP 如果不做登录，可以用 anonymous_user_id 替代。

### 5.2 aesthetic_inputs：审美输入表

保存用户上传的原始样本。

```text
id
user_id
type
content_text
file_url
source
title
description
created_at
updated_at
```

字段说明：

- type：image / text / music / video / link
- content_text：文本内容
- file_url：图片或文件地址
- source：用户手动上传、历史导入、第三方平台等

### 5.3 input_features：输入特征表

保存单个样本的结构化分析结果。

```text
id
input_id
model_name
feature_json
summary
confidence
created_at
```

feature_json 示例：

```json
{
  "lowLevelFeatures": {
    "saturation": "low",
    "brightness": "medium_low",
    "colorTemperature": "cool",
    "colorContrast": "low",
    "personPresence": "absent",
    "spatialDensity": "low",
    "compositionComplexity": "medium",
    "textureComplexity": "medium"
  },
  "evidence": ["画面主体色彩偏灰蓝", "人物缺席", "空间元素较少"]
}
```

### 5.4 embeddings：向量表

保存输入样本或报告的 embedding。

```text
id
owner_type
owner_id
model_name
vector
vector_dimension
created_at
```

owner_type 可选：

- input
- report
- insight
- user_profile

### 5.5 analysis_jobs：分析任务表

保存一次分析任务状态。

```text
id
user_id
status
input_count
error_message
started_at
finished_at
created_at
```

status 可选：

- pending
- processing
- completed
- failed

### 5.6 aesthetic_reports：审美报告表

保存一次完整审美报告。

```text
id
user_id
job_id
title
summary
low_level_features_json
similarity_groups_json
interpretations_json
contradictions_json
report_json
markdown
created_at
```

### 5.7 possible_interpretations：动态解释候选表

保存由底层特征和相似性分组结果生成的解释候选。

```text
id
report_id
target_type
target_id
name
confidence
evidence_json
alternative_names_json
uncertainty
created_at
```

target_type 可选：

- report
- similarity_group
- input

### 5.8 insights：洞察表

保存报告中的单条洞察。

```text
id
report_id
interpretation_id
title
observation
evidence_json
interpretation
uncertainty
confidence
created_at
```

### 5.9 insight_feedback：洞察反馈表

保存用户对每条洞察的反馈。

```text
id
user_id
insight_id
interpretation_id
rating
comment
created_at
```

rating 可选：

- not_me
- interesting
- accurate
- seen

### 5.10 user_aesthetic_profiles：用户审美画像表，V2

保存长期用户画像。

```text
id
user_id
profile_json
stable_low_level_features_json
accepted_interpretations_json
rejected_interpretations_json
updated_at
```

V1 不要求创建或更新该表。该表从 V2 开始使用，用于保存历史报告和用户反馈形成的轻量画像。

### 5.11 aesthetic_timeline_events：审美时间轴表

保存长期变化事件。

```text
id
user_id
event_type
title
description
related_report_ids
evidence_json
created_at
```

event_type 可选：

- new_interpretation
- interpretation_decline
- feature_shift
- style_shift
- contradiction_detected
- stable_preference

## 6. 结构化报告数据

报告不应只保存一整段 Markdown，也应该保存结构化 JSON。

示例：

```json
{
  "summary": "这组输入呈现出低饱和、人物缺席和空间密度低的倾向。",
  "lowLevelFeatures": [
    {
      "feature": "saturation",
      "value": "low",
      "evidence": ["image_01", "image_03"],
      "confidence": 0.88
    }
  ],
  "similarityGroups": [
    {
      "groupId": "group_001",
      "name": "冷感低密度组",
      "samples": ["image_01", "text_02"],
      "commonFeatures": ["cool_color", "person_absent", "low_spatial_density"]
    }
  ],
  "possibleInterpretations": [
    {
      "interpretationId": "interp_001",
      "name": "结构化疏离",
      "target": "group_001",
      "confidence": 0.64,
      "evidence": ["low_saturation", "person_absent", "low_spatial_density"],
      "alternativeNames": ["冷感空间偏好"],
      "uncertainty": "这也可能只是近期对简洁空间的偏好。"
    }
  ],
  "insights": [
    {
      "title": "你近期输入中出现冷感低密度特征",
      "evidence": ["low_saturation", "person_absent", "low_spatial_density"],
      "interpretation": "这些特征可能被解释为结构化疏离，也可能只是冷感空间偏好。",
      "uncertainty": "该解释需要通过用户反馈确认。"
    }
  ]
}
```

## 7. API 设计

### 7.1 创建输入

```text
POST /api/inputs
```

用途：

- 上传图片
- 保存文本
- 创建审美输入记录

### 7.2 创建分析任务

```text
POST /api/analysis-jobs
```

用途：

- 选择一组输入
- 创建分析任务
- 启动 AI 分析流程

### 7.3 查询分析状态

```text
GET /api/analysis-jobs/:id
```

用途：

- 获取任务状态
- 返回失败原因
- 返回完成后的 report_id

### 7.4 获取报告

```text
GET /api/reports/:id
```

用途：

- 展示报告详情
- 展示底层特征、相似性分组、可能解释、洞察和依据

### 7.5 提交反馈

```text
POST /api/insights/:id/feedback
```

用途：

- 保存用户对洞察的反馈
- V1 只保存反馈；V2 再基于反馈更新轻量画像

### 7.6 获取历史报告

```text
GET /api/reports
```

用途：

- 展示用户历史分析记录

## 8. AI 服务分层

建议将 AI 分析拆成几个服务函数：

```text
analyzeImageFeatures()
analyzeTextFeatures()
generateEmbedding()
groupInputsBySimilarity()
extractCommonPatterns()
detectContradictions()
generateInterpretationCandidates()
retrieveUserMemory()
retrieveAestheticKnowledge()
generateInsights()
generateReport()
saveUserFeedback()
updateUserProfile()
```

这样可以避免一个超长 prompt 负责所有事情。

进阶阶段，这些服务函数可以通过 Function Calling 暴露给 LLM，由 workflow 层根据当前任务编排调用。MVP 阶段可以先使用固定流程编排，不必直接实现完整 Agent。

## 9. MVP 技术取舍

### 9.1 可以简化的部分

MVP 可以暂时简化：

- 不做复杂登录
- 不做复杂向量数据库
- 不做实时任务队列
- 不做第三方平台导入
- 不做高级可视化
- 不做完整 Agent
- 不做图数据库
- 不做 MCP 外部接入

### 9.2 不能省略的部分

MVP 不建议省略：

- 底层特征保存
- 每条洞察的依据
- 用户反馈
- 报告历史
- 模型版本记录
- prompt 版本记录
- 洞察证据链
- 基础分析日志

这些是项目从“玩具”变成“系统”的关键。

## 10. 后续扩展架构

### 10.1 长期记忆

通过多次报告和用户反馈生成长期 profile：

- 稳定偏好
- 近期变化
- 被否定解释
- 高命中解释

### 10.2 审美轨迹

通过时间序列分析生成：

- 底层特征趋势图
- 风格迁移
- 新旧解释对比
- 阶段性报告

### 10.3 多模态扩展

增加音乐、视频后，仍然遵循同一结构：

```text
原始输入
↓
底层特征
↓
embedding
↓
跨模态聚合
↓
解释型报告
```

### 10.4 Function Calling

当分析流程复杂后，将核心分析能力封装为工具函数：

- analyzeImageFeatures
- analyzeTextFeatures
- generateEmbedding
- groupInputsBySimilarity
- generateInterpretationCandidates
- retrieveAestheticKnowledge
- generateReport
- updateUserProfile

这样可以提升稳定性、可调试性和工程表达。

### 10.5 RAG 与 personalized retrieval

RAG 用于检索审美知识库，增强解释质量。

personalized retrieval 用于检索用户历史输入、报告和反馈，增强个性化分析。

两者都属于检索增强，但职责不同。

### 10.6 审美观察 Agent

当系统具备工具选择、历史状态、定期任务和主动观察能力后，可以升级为审美观察 Agent。

Agent 负责：

- 选择分析工具
- 对比历史审美状态
- 主动发现变化
- 生成周报 / 月报
- 根据用户反馈调整观察重点

### 10.7 审美知识图谱与 MCP

知识图谱用于表达审美概念之间的关系；MCP 用于接入外部上下文源。

这两者属于高级扩展，不是 MVP 必需项。

## 11. 架构核心原则

这个系统的技术架构必须服务于一个目标：

> 让 AI 输出有依据、可追溯、可反馈、可长期演化。

因此，哪怕 MVP 很小，也要保留：

- 数据层
- 特征层
- 向量层
- 报告层
- 反馈层
- 画像层，V2 开始实现

只要这几个层次存在，项目就不再是简单的“上传图片让 GPT 评价”，而是一个真正的个人风格建模系统。
