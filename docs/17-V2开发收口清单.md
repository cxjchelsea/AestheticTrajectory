## 1. 文档目的

这份文档用于收口 V2 的工程验收范围。

它不定义新的产品愿景，也不替代 V2 子阶段任务单，只把 V2 必须验收的工程内容压成一张清单：

- V2 要提供哪些用户可见能力。
- V2 要新增或复用哪些表。
- V2 要提供哪些 API。
- V2 要做哪些前端页面。
- V2 的轻量画像和 feedback 更新规则是什么。
- V2 完成标准是什么。

职责边界：

- V2 版本级研究和能力边界，以 `iterations/v2-0-memory-user-model-research.md` 为准。
- V2 的具体工程验收，以本文档为准。
- V2 实际完成情况、测试结果、遗留问题，以 `15-迭代执行记录.md` 和 `archive/v2/` 为准。
- V2-A / V2-B / V2-C 的过程细节留在各自 iteration 文档，不在本文档展开。
- 如果其他文档里出现 V3 / V4 能力，本文档优先用于判断 V2 是否需要实现。

## 2. V2 一句话目标

> 在 V1 的报告与反馈闭环之上，加入历史报告、轻量画像、可追溯 profile evidence，以及 feedback 对画像的修正能力。

V2 只允许形成：

```text
基于用户输入、报告洞察和用户反馈的轻量审美观察记录。
```

V2 不生成人格画像、心理评估或推荐决策。

## 3. V2 明确不做

V2 不做：

- 完整登录系统。
- 真实图片文件存储。
- 真实图片内容读取。
- 真实 LLM / vision / embedding runtime。
- ChromaDB runtime 写入和查询。
- personalized retrieval。
- RAG / 审美知识库。
- Agent / MCP。
- 知识图谱。
- 音乐 / 视频输入。
- 自动推荐。
- 用户画像的复杂手动编辑、删除和权限工作流。

这些能力从 V3、V4 或后续基础设施任务开始。

## 4. V2 前端页面

### 4.1 首页

必须包含：

- 上传入口。
- 历史报告入口。
- 轻量画像入口。

限制：

- 不暗示系统已经具备人格诊断、心理评估、推荐决策或真实 Agent 能力。

### 4.2 上传 / 分析页

必须包含：

- 提交不少于 3 条文本输入。
- 分析等待状态。
- 分析完成后进入报告页。
- 本地 mock / fallback 状态的明确提示。

限制：

- 真实后端分析失败时，不能把本地 mock 报告伪装成已持久化报告。
- 开发模式下重复挂载不能导致同一轮分析重复写入输入样本。

### 4.3 报告详情页

必须展示：

- 总体摘要。
- 底层特征摘要。
- 相似性分组。
- 可能解释。
- 重点洞察。
- evidence refs。
- disclaimer。
- insight feedback 按钮。

反馈选项：

```text
不像我
不确定
有点像
很像我
```

限制：

- 只有真实后端报告可以写入 feedback。
- 本地 mock / fallback 报告的 feedback 只能保留在界面，不写入画像。
- 开发环境可以显示 Developer Debug Panel，生产环境不能显示。

### 4.4 历史报告页

必须包含：

- 历史报告列表。
- 按创建时间倒序展示。
- 报告摘要卡片。
- 空状态。
- 从历史列表进入报告详情。

报告摘要必须至少包含：

```text
report_id
job_id
title
summary
input_count
created_at
```

### 4.5 轻量画像页

必须展示：

- profile summary。
- profile items。
- profile item 数量和 evidence 数量。
- 每个 profile item 的状态、可信度、证据数量。
- evidence refs 的可读说明。
- feedback evidence 的可读说明。
- rejected / uncertain 条目的单独提示。
- 空状态。

限制：

- 正向倾向只展示 `stable` / `recent` 且 `weight > 0` 的条目。
- `not_me` 反馈不能进入正向画像。
- `unsure` 反馈不能强化正向 summary。
- 页面不能直接把内部字段当作用户文案，例如 `density=low`、`somewhat_me`、`feedback_xxx`。
- 页面不输出人格、心理、能力或命运判断。

## 5. V2 PostgreSQL 表

V2 继承 V1 表，并重点验收以下表。

### 5.1 `aesthetic_reports`

用途：

```text
保存报告主体和 report_json，用于历史报告回看。
```

验收标准：

- `user_id` 可用于按用户查询历史报告。
- `job_id` 可用于从历史报告关联分析任务。
- `report_json` 可以反序列化为 `ReportResponse`。
- 历史报告列表按 `created_at desc, id desc` 返回。
- 历史报告列表不依赖前端 mock data。

### 5.2 `insights`

用途：

```text
保存报告中的可反馈洞察。
```

验收标准：

- 每条 insight 关联 `report_id`。
- 每条 insight 有 `title`、`observation`、`interpretation`、`uncertainty`、`confidence`。
- `evidence_json` 对应 API 中的 `evidenceRefs`。
- 新生成的 mock insight id 必须带 report 作用域，避免历史 mock insight id 重复。
- 不存在的 insight 不能保存 feedback。

### 5.3 `insight_feedback`

用途：

```text
保存用户对 insight 的反馈，并作为 profile evidence 来源。
```

验收标准：

- feedback 保存 `user_id`、`insight_id`、`interpretation_id`、`rating`、`comment`、`created_at`。
- rating 只允许 `not_me`、`unsure`、`somewhat_me`、`very_me`。
- 同一 `user_id + insight_id` 再次反馈时更新原 feedback，不重复累计。
- 当前 feedback 可通过 API 查询。
- feedback 能进入 profile evidence。

### 5.4 `user_profiles`

用途：

```text
保存用户当前轻量画像的摘要版本。
```

验收标准：

- 每个 profile 关联 `user_id`。
- profile 包含 `summary`、`version`、`created_at`、`updated_at`。
- `summary` 只来自已有 profile items 聚合。
- `summary` 不写人格、心理或能力诊断。

### 5.5 `profile_items`

用途：

```text
保存轻量画像中的单个审美倾向或被否定 / 待确认解释。
```

验收标准：

- 每个 item 关联 `profile_id`。
- item 包含 `key`、`label`、`status`、`weight`、`confidence`、`source_count`、`last_seen_at`。
- status 只允许 `stable`、`recent`、`rejected`、`uncertain`、`inactive`、`hidden`、`deleted`。
- `stable` / `recent` 可以进入正向倾向展示。
- `rejected` / `uncertain` 不能进入正向 summary。
- 每个 item 至少有一条 evidence。

### 5.6 `profile_evidence`

用途：

```text
保存 profile item 的证据来源。
```

验收标准：

- 每条 evidence 关联 `profile_item_id`。
- evidence 包含 `evidence_type`、`evidence_id`、`direction`、`weight_delta`、`note`、`created_at`。
- `evidence_type` 支持 `feature`、`report`、`interpretation`、`insight`、`feedback`。
- `direction` 支持 `positive`、`negative`、`uncertain`、`conflict`。
- `not_me` 生成 negative evidence。
- `unsure` 生成 uncertain evidence。
- `somewhat_me` 生成弱 positive evidence。
- `very_me` 生成强 positive evidence。

## 6. V2 API

### 6.1 历史报告列表

```text
GET /api/users/{user_id}/reports
```

验收标准：

- 返回 `ReportHistoryResponse`。
- response 包含 `reports`、`total`、`limit`、`offset`。
- 支持 `limit` / `offset`。
- 按创建时间倒序返回。
- 只返回对应用户的报告。

### 6.2 报告详情

```text
GET /api/reports/{report_id}
```

验收标准：

- 存在报告时返回 `ReportResponse`。
- 不存在报告时返回 404。
- `ReportResponse` 包含 summary、features、groups、interpretations、insights 和 disclaimer。
- 每个 `Insight` 包含可用于 feedback 的 `insightId`。

### 6.3 读取当前反馈

```text
GET /api/insights/{insight_id}/feedback
```

验收标准：

- 已反馈时返回 `InsightFeedbackResponse`。
- 未反馈时返回 `null`。
- 不把其他用户 feedback 当作当前用户 feedback。

### 6.4 提交或修改反馈

```text
POST /api/insights/{insight_id}/feedback
```

验收标准：

- 不存在的 insight 返回 404。
- rating 非法时返回 422。
- 同一 insight 再次反馈时更新当前 feedback，不重复累计。
- 保存后可被画像构建读取。

### 6.5 用户画像

```text
GET /api/users/{user_id}/profile
```

验收标准：

- 返回 `ProfileResponse`。
- 有足够 evidence 时返回 `UserProfile`。
- 无足够 evidence 时返回 `profile: null` 和明确 message。
- 每个 profile item 至少包含一个 evidence。
- feedback evidence 能被前端识别并展示。

### 6.6 分析任务 Debug

```text
GET /api/analysis-jobs/{job_id}/debug
```

验收标准：

- 开发环境可用于查看 workflow trace、schema validation 和 boundary warnings。
- 不作为用户侧正式能力。
- 生产环境前端不展示 Developer Debug Panel。

## 7. V2 Workflow 与服务边界

必须满足：

- API route 只处理 HTTP 层。
- 业务逻辑进入 service。
- 数据访问进入 repository。
- workflow step 负责分析流程，不直接处理前端状态。
- ChromaDB 不作为业务数据源。
- profile builder 从 reports + feedback 构建画像，不凭空生成画像。
- feedback 更新后重新查询 profile 时，画像能反映当前 feedback。
- 本地 mock / fallback 报告不得写入真实 feedback 或 profile evidence。

## 8. V2 画像与反馈规则

必须满足：

- 先 evidence，后 profile。
- 先用户反馈，后模型推断。
- 只描述输入中出现的审美倾向。
- 不把单次输入固化为长期偏好。
- 不把被否定解释作为正向记忆。
- 不把不确定反馈强化为正向画像。
- 每个 profile item 都必须可追溯到 evidence。
- 用户修改反馈时，不重复累计为多条 evidence。
- 画像不用于推荐、消费引导或自动化重大决策。

## 9. 测试与验收要求

正式归档前必须完成：

- 后端自动测试通过。
- 前端 production build 通过。
- Alembic migration 可执行到 head。
- PostgreSQL runtime 路径通过。
- 前端手动路径通过。
- V2 验收核对表已更新。
- V2 遗留问题已更新。
- `15-迭代执行记录.md` 已同步最终状态。

最小手动验收路径：

```text
首页 → 上传 / 分析 → 报告详情 → 提交 feedback → 历史报告 → 轻量画像
```

必须人工确认：

- 真实报告 feedback 可以保存和修改。
- fallback / mock 报告不会写入真实 feedback。
- 画像页显示正向倾向、已否定解释和待确认解释。
- 页面没有人格、心理或能力诊断式表达。
- 一次分析不会重复写入输入样本。

## 10. 归档标准

V2 可以归档的条件：

- 本文档所有 V2 必做项均已通过，或在 `archive/v2/V2-遗留问题.md` 中说明为何可延后。
- `archive/v2/V2-验收核对表.md` 中不存在 blocking issue。
- `archive/v2/V2-归档说明.md` 已记录最终实现快照、测试结果和后续边界。
- `15-迭代执行记录.md` 中 V2 状态已更新为 `accepted / archived`。

V2 不能归档的情况：

- 真实报告 feedback 不能保存。
- 画像缺少 evidence。
- `not_me` 进入正向画像。
- 分析失败被静默包装成真实报告。
- 同一轮分析重复写入业务数据。
- 页面出现人格诊断、心理评估、命运判断或无依据高级词。
