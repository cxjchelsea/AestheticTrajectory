# AI 审美形成系统：开发任务拆分与里程碑计划

## 1. 技术选型建议

### 1.1 前端框架选择

最终技术选择：

> 前端 React，后端 FastAPI，业务数据库 Oracle，向量库 ChromaDB。

原因：

- React 生态成熟，适合做上传页、报告页、历史页、任务状态轮询和数据可视化。
- FastAPI 更适合承接 AI 分析服务、文件上传、任务编排、模型调用和异步后台任务。
- Oracle 作为业务数据库，可以体现传统企业级数据库使用能力，适合保存用户、输入、报告、反馈、画像和日志。
- ChromaDB 专门负责向量存储和相似度检索，职责比把向量塞进业务库更清晰。
- 前后端分离后，系统边界更接近真实工程项目，也更方便后续部署、测试和替换模型。

不再采用 Next.js 全栈方案。React 只做前端，FastAPI 负责后端。

### 1.2 推荐技术栈

MVP 推荐：

- 前端：React + Vite
- 样式：Tailwind CSS
- 后端：FastAPI
- 数据库：Oracle
- 数据访问：SQLAlchemy + python-oracledb，或直接使用 python-oracledb
- 文件存储：本地 uploads，后续可换 S3 / R2
- 向量存储：ChromaDB，MVP 可先 mock collection
- AI：先用 LLM / 多模态模型 API，后续再替换或优化
- 前端测试：Vitest + React Testing Library，后续加 Playwright
- 后端测试：pytest + FastAPI TestClient

### 1.3 MVP 技术原则

第一版不要追求完整复杂，而要追求闭环稳定：

```text
上传输入
↓
保存输入
↓
提取底层特征
↓
生成 embedding
↓
聚类与共性分析
↓
动态解释候选
↓
生成报告
↓
用户反馈
```

第一版可以使用 mock AI 服务，先保证数据流、接口、页面和测试跑通，再替换成真实模型。

## 2. 里程碑总览

开发分为 8 个里程碑：

1. 项目初始化与基础工程结构
2. Oracle 数据库、ChromaDB 与基础 API
3. 输入上传与分析任务闭环
4. 底层特征提取模块
5. embedding、聚类与动态解释候选
6. 报告生成与反馈闭环
7. 历史报告、基础画像与可观测日志
8. 测试、样本集、简历展示和 Demo 打磨

每个里程碑都应该能单独提交、单独测试、单独验收。

## 3. 里程碑 1：项目初始化与基础工程结构

### 目标

搭建可运行的 React 前端和 FastAPI 后端项目骨架。

### 开发任务

1. 初始化 React + Vite 项目。
2. 配置 TypeScript。
3. 配置 Tailwind CSS。
4. 配置 ESLint / Prettier。
5. 初始化 FastAPI 后端项目。
6. 配置 Python 虚拟环境和依赖管理。
7. 创建前端首页、上传页、报告页、历史页占位。
8. 创建后端 API 目录结构。
9. 创建前后端环境变量模板。
10. 配置前端请求后端 API 的基础 client。

### 建议目录

```text
frontend/
  src/
    pages/
    components/
    services/
    types/
    tests/

backend/
  app/
    main.py
    api/
    core/
    models/
    schemas/
    services/
    repositories/
    ai/
    storage/
    tests/
```

### 验收标准

- 本地项目可以启动。
- 首页、上传页、报告页、历史页可以访问。
- TypeScript 无明显错误。
- Tailwind 样式生效。
- FastAPI 后端可以启动。
- 前端能请求后端 health check 接口。

### 可交给 AI 的任务提示

```text
请根据 `10-开发任务拆分与里程碑计划.md` 的里程碑 1，初始化 React + Vite + TypeScript + Tailwind 前端项目，以及 FastAPI 后端项目。创建首页、上传页、报告页、历史页占位，并实现后端 health check API。
```

## 4. 里程碑 2：Oracle 数据库、ChromaDB 与基础 API

### 目标

根据 `05` 和 `09` 定义核心业务数据结构，并建立 Oracle 与 ChromaDB 的连接。

### 开发任务

1. 安装并配置 python-oracledb。
2. 选择并配置 SQLAlchemy 或直接使用 python-oracledb。
3. 配置 Oracle 连接环境变量。
4. 创建用户表。
5. 创建审美输入表。
6. 创建分析任务表。
7. 创建输入特征表。
8. 创建报告表。
9. 创建 possible_interpretations 表。
10. 创建 insights 表。
11. 创建 insight_feedback 表。
12. 创建 user_aesthetic_profiles 表。
13. 创建 analysis_logs 表。
14. 安装并配置 ChromaDB。
15. 创建 ChromaDB collection：inputs、reports、insights、user_profiles。
16. 编写 seed 或基础 mock 数据。
17. 实现数据库 health check 和 ChromaDB health check。

### 验收标准

- Oracle 能正常连接。
- ChromaDB 能正常连接。
- 每张核心表能创建和查询。
- ChromaDB collection 能创建、写入和查询。
- 字段命名与 `05`、`09` 保持一致。

### 可交给 AI 的任务提示

```text
请根据 `05-数据结构与系统架构文档.md` 和 `09-模块拆分与接口测试文档.md`，为 FastAPI 后端创建 Oracle 数据库访问层和 ChromaDB 向量库访问层。Oracle 需要覆盖用户、输入、分析任务、底层特征、报告、possible_interpretations、insights、feedback、profile、analysis_logs 等表；ChromaDB 需要创建 inputs、reports、insights、user_profiles collection。
```

## 5. 里程碑 3：输入上传与分析任务闭环

### 目标

实现用户上传图片 / 文本，并创建分析任务。

### 开发任务

1. 实现匿名用户与会话。
2. 实现图片上传组件。
3. 实现文本输入组件。
4. 实现输入预览和删除。
5. 实现 `/api/inputs`。
6. 实现文件保存。
7. 实现 `/api/analysis-jobs`。
8. 实现任务状态查询 `/api/analysis-jobs/:id`。
9. 上传页接入 API。

### 验收标准

- 用户可以上传 5-10 个样本。
- 图片和文本都能保存。
- 每个输入有 inputId。
- 能创建 analysis job。
- job 状态可以查询。

### 测试重点

- 图片格式和大小校验。
- 空文本校验。
- 输入数量不足时不能创建任务。
- 存储失败时任务不继续。

### 可交给 AI 的任务提示

```text
请实现审美输入模块和分析任务模块：支持图片上传、文本保存、输入预览、创建 analysis job，并提供对应 API 和基础测试。
```

## 6. 里程碑 4：底层特征提取模块

### 目标

实现图片和文本的底层特征提取。

### 开发任务

1. 定义 image feature schema。
2. 定义 text feature schema。
3. 实现 mock 图片特征提取服务。
4. 实现 mock 文本特征提取服务。
5. 后续可接入真实多模态模型。
6. 保存 feature_json 到 input_features。
7. 为每次提取写入 analysis_logs。

### 图片底层特征

- saturation
- brightness
- colorTemperature
- colorContrast
- personPresence
- spatialDensity
- compositionComplexity
- textureComplexity

### 文本底层特征

- sentimentTone
- emotionIntensity
- narrativeDensity
- concreteness
- imageryDensity
- perspective

### 验收标准

- 每个输入能生成 lowLevelFeatures。
- 每个特征有 evidence。
- 输出符合 JSON schema。
- 同一输入重复分析结果基本稳定。

### 可交给 AI 的任务提示

```text
请根据 `04-审美表征体系文档.md` 和 `09-模块拆分与接口测试文档.md`，实现图片和文本底层特征提取模块。第一版可以使用 mock 规则或 LLM mock，但必须输出稳定 JSON schema 并保存到 input_features。
```

## 7. 里程碑 5：embedding、聚类与动态解释候选

### 目标

让系统从一组输入中发现结构，并生成 possibleInterpretations。

### 开发任务

1. 定义 embedding service 接口。
2. 第一版实现 mock embedding。
3. 后续接入真实 embedding 模型。
4. 实现 embedding 保存。
5. 实现简单相似度计算。
6. 实现简单聚类逻辑。
7. 实现 globalPatterns 提取。
8. 实现 outliers 识别。
9. 实现动态解释候选生成。
10. 保存 possible_interpretations。

### 验收标准

- 每个输入都有 embedding。
- 一组输入能生成 clusters。
- 每个 cluster 有 commonFeatures。
- 能生成多个 possibleInterpretations。
- 每个解释有 evidence、alternativeNames、uncertainty。

### 测试重点

- 相似输入距离更近。
- 离群输入能识别。
- 高饱和、Y2K、meme 样本不会被统一解释成“疏离、克制、留白”。

### 可交给 AI 的任务提示

```text
请实现 embedding、聚类与动态解释候选模块。第一版允许 mock embedding，但必须跑通 input_features → embeddings → clusters → possibleInterpretations 的完整数据流。
```

## 8. 里程碑 6：报告生成与反馈闭环

### 目标

生成用户可读报告，并收集用户反馈。

### 开发任务

1. 定义 report JSON schema。
2. 实现报告生成 service。
3. 按 `06` 的模板生成 Markdown。
4. 实现报告详情页。
5. 展示底层特征。
6. 展示聚类。
7. 展示 possibleInterpretations。
8. 展示重点洞察。
9. 实现反馈组件。
10. 实现 `/api/insights/:id/feedback`。
11. 保存用户反馈。

### 验收标准

- 报告页可以完整展示分析结果。
- 每条洞察有 evidence 和 uncertainty。
- 用户可以选择反馈。
- 反馈能保存到数据库。

### 测试重点

- 报告结构符合 schema。
- 无证据洞察不能生成。
- 反馈 rating 枚举合法。
- 反馈能关联 insightId 和 interpretationId。

### 可交给 AI 的任务提示

```text
请根据 `06-输出报告模板文档.md` 实现报告生成模块和报告详情页，并实现洞察反馈 API。报告必须包含底层特征、聚类、可能解释、洞察、证据和不确定性。
```

## 9. 里程碑 7：历史报告、基础画像与可观测日志

### 目标

让系统具备持续记录和调试能力。

### 开发任务

1. 实现历史报告列表页。
2. 实现基础用户画像更新。
3. 保存 acceptedInterpretations。
4. 保存 rejectedInterpretations。
5. 保存 stableLowLevelFeatures。
6. 实现 analysis_logs 查询。
7. 在每个关键阶段写入日志。
8. 实现基础 trace 查看。

### 验收标准

- 用户能查看历史报告。
- 用户反馈能影响基础画像。
- 分析过程能追踪到关键步骤。
- 失败任务能看到失败阶段。

### 测试重点

- 历史报告按时间倒序。
- 用户只能看自己的报告。
- 被否定解释不应在画像中被当作正向偏好。
- 每个 job 至少有基础日志。

### 可交给 AI 的任务提示

```text
请实现历史报告、基础用户画像和分析日志模块。用户反馈后需要更新 acceptedInterpretations、rejectedInterpretations 和 stableLowLevelFeatures，并在历史页展示报告列表。
```

## 11. 推荐开发顺序

最推荐的顺序是：

```text
项目初始化
↓
Oracle 表结构与 ChromaDB collection
↓
输入上传
↓
分析任务
↓
底层特征 mock
↓
embedding mock
↓
聚类与解释
↓
报告生成
↓
反馈保存
↓
历史与画像
↓
替换真实 AI 模型
↓
测试与 Demo
```

这样做的好处是：

- 先跑通工程闭环。
- 先稳定 Oracle 业务表结构和 ChromaDB collection 结构。
- 先用 mock 降低模型不确定性。
- 后续替换真实模型时不会破坏主流程。

## 12. 每次让 AI 编程时的原则

不要一次让 AI 实现整个系统。

每次只给一个小任务：

- 一个页面
- 一个 API
- 一个 service
- 一个 schema 或一张表
- 一个测试文件

每次任务都要包含：

- 参考文档
- 输入输出
- 验收标准
- 不要做什么

推荐格式：

```text
请根据 `09-模块拆分与接口测试文档.md` 的【模块名称】实现该模块。

要求：
1. 输入输出必须符合文档 schema。
2. 不要实现超出 MVP 的功能。
3. 写基础单元测试。
4. 如果需要 mock AI 输出，请保持 schema 稳定。
```

## 13. 第一周目标

第一周不追求真实 AI 效果，只追求完整闭环。

必须完成：

- React + Vite 前端项目初始化
- FastAPI 后端项目初始化
- Oracle 业务表结构
- ChromaDB collection 初始化
- 输入上传
- 分析任务
- mock 特征提取
- mock embedding
- mock 聚类
- mock possibleInterpretations
- 报告页
- 反馈保存

第一周完成后，系统应该已经可以演示：

> 用户上传一组内容，系统生成一份结构化审美报告，并允许用户反馈。

这就是后续所有 AI 能力的地基。
