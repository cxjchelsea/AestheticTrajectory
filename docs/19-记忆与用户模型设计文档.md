## 2. 一句话定义

```text
本项目的记忆系统，是把用户输入、报告、反馈组织成可解释、可修正、可治理的审美观察记录；用户模型是其中「带 evidence 的轻量画像层」，不是人格档案，也不是推荐系统用户画像。
```

用户模型只描述：

```text
系统基于历史输入、报告洞察和用户反馈观察到的审美倾向。
```

用户模型不描述：

```text
人格、心理、能力、命运、消费偏好或诊断式结论。
```

## 3. 记忆分层

系统按职责把「记忆相关对象」分成以下层。**下层是上层的基础；上层不得绕开下层编造事实。**

```text
L0 原始输入层
  inputs / input_features / embeddings metadata

L1 分析产物层
  reports / insights / possible_interpretations / analysis_logs

L2 用户反馈层
  insight_feedback

L3 用户模型层（User Model）
  user_profiles / profile_items / profile_evidence

L4 解释上下文层（Supplementary Context，不进 profile 正向证据）
  historyContext / knowledgeContext（persisted in report_json）

L5 对比与轨迹层
  report comparison（只读，复用 report_json）
  aesthetic_timeline_events（表结构已占位，V4-B 实现）

L6 向量检索层
  ChromaDB collections（架构占位，V4-A 前未 runtime）

L7 外部上下文层（V4 占位）
  external_context / MCP import batches / agent_action_logs
```

### 3.1 各层职责

| 层 | 存什么 | 是否 User Model | 当前状态 |
| --- | --- | --- | --- |
| L0–L2 | 单次分析事实与用户态度 | 否（是 evidence 来源） | V1/V2 已实现 |
| L3 | 跨报告聚合的轻量画像 | **是** | V2 已实现 |
| L4 | 报告生成时的历史/知识参考 | **否** | V3 已实现 |
| L5 | 跨报告变化与时间轴 | 部分（comparison 只读；timeline 占位） | V2-D comparison 已实现 |
| L6 | 向量相似度检索 | 否 | 未 runtime |
| L7 | 外部导入与 Agent 行为 | 否（默认不进 profile 正向证据） | V4 占位 |

### 3.2 核心原则

```text
先 evidence，后 profile。
先用户反馈，后模型推断。
先当前输入 evidence，后 history / knowledge / external context。
先可解释和可撤回，后自动更新。
只描述审美倾向，不做人格诊断。
```

## 4. User Model 结构

User Model 由三表组成（DDL 见 `07` §5.10–5.12）：

```text
user_profiles     → 画像摘要（summary、version）
profile_items     → 可解释倾向条目（key、label、status、weight）
profile_evidence  → 每条倾向的证据链（evidence_type、direction、weight_delta）
```

聚合顺序：

```text
收集 evidence → 生成 / 更新 profile_items → 生成 profile summary
```

**禁止**把画像只塞进 `report_json`、前端 state 或 ChromaDB。

### 4.1 profile_item.status 语义

| status | 含义 | 典型来源 |
| --- | --- | --- |
| `stable` | 多次正向 evidence 或强反馈支持 | 重复 feature、very_me |
| `recent` | 近期出现但尚未足够稳定 | 单次 feature、弱正向 feedback |
| `rejected` | 用户明确否定 | not_me |
| `uncertain` | 不确定信号，不强化正向 summary | unsure |
| `inactive` / `hidden` / `deleted` | 预留用户治理状态 | 尚未完整 runtime |

当前实现（`profile_builder.py`）规则摘要：

- `not_me` 或净权重 ≤ 0 且存在负向 evidence → `rejected`
- 仅 uncertain → `uncertain`
- 正负并存 → `recent` 或 `uncertain`（视净权重）
- 正向 evidence ≥ 2 或存在强正向 feedback → `stable`
- 否则 → `recent`

### 4.2 profile_evidence 语义

| evidence_type | 来源 | 是否进入 builder |
| --- | --- | --- |
| `feature` | 报告底层特征 | 是 |
| `report` | 报告摘要 / 报告级观察 | 设计支持；当前 builder 主要从 feature + feedback 构建 |
| `interpretation` | 解释候选 | 设计支持 |
| `insight` | 报告洞察 | 通过 feedback 间接关联 |
| `feedback` | insight_feedback | 是 |

| direction | 含义 |
| --- | --- |
| `positive` | 支持该 profile item |
| `negative` | 否定该倾向 |
| `uncertain` | 不强化 |
| `conflict` | 新旧证据冲突，不直接覆盖（设计规则；builder 可逐步完善） |

| feedback rating | direction | weight_delta（当前实现） |
| --- | --- | --- |
| `very_me` | positive | +0.4 |
| `somewhat_me` | positive | +0.2 |
| `unsure` | uncertain | 0.0 |
| `not_me` | negative | -0.5 |

**feedbackHitRate**（V3-C）只把 `somewhat_me` / `very_me` 计为正向命中；`not_me` → 0% 是设计预期。

## 5. 什么算「记忆」，什么不算

### 5.1 进入 User Model（L3）的对象

可以进入 profile positive evidence 的来源：

- 用户输入-derived 底层特征（重复出现）
- 用户明确认可的 insight / interpretation（via feedback）
- 用户明确否定的解释（作为 `rejected` / negative evidence，**不是**正向偏好）

不可以进入 profile positive evidence：

- V3 `historyContext` 条目
- V3 `knowledgeContext` / 知识 docId
- 外部 RAG / 知识图谱关系（V4 规划，规则同上）
- MCP 导入的外部收藏 / 笔记（V4 规划，规则同上）
- 单次无 feedback 支持的高层 insight 直接升为 `stable`

### 5.2 解释上下文层（L4）——不是 User Model

V3 引入的 `historyContext` 与 `knowledgeContext`：

- 保存在 `aesthetic_reports.report_json`
- 用于报告解释与 UI 展示
- **不写入** `profile_items` / `profile_evidence` 正向证据
- insight 的 `evidenceRefs` **只引用当前 report 的 input ids**

history context 规则（V3-A）：

- 只检索同用户历史 reports / feedback
- 需要 feature overlap gate；无重叠则 abstain
- `not_me` 只作为 negative context，不作为正向偏好
- 必须带 `sourceRefs`、`matchedFeatures`

knowledge context 规则（V3-B）：

- 静态审美知识库 + overlap gate
- out-of-scope 时 abstain，不伪造条目
- 只作 explanation support

### 5.3 对比层（L5）——只读记忆视图

最近两次报告对比（V2-D）：

- 复用 `report_json`，不新增业务表
- 输出 feature / interpretation changes + evidence refs
- 不得写成人格、心理或能力变化

审美时间轴（V4-B 占位）：

- `aesthetic_timeline_events` 表已在 `07` §5.14 占位
- 事件必须带 `evidence_json` / `related_report_ids`
- 不是 User Model 替代品，是长期观察视图

## 6. 写入、更新与冲突

### 6.1 写入路径

```text
用户上传输入
  → workflow 生成 report + insights
  → 用户提交 feedback（可选）
  → GET /api/users/{user_id}/profile 触发 profile rebuild
  → profile_builder.build_profile_from_sources(reports, feedback)
  → 持久化 user_profiles / profile_items / profile_evidence
```

profile builder **只读取**：

- `list[ReportResponse]`（含 low_level_features、insights）
- `list[InsightFeedbackResponse]`

profile builder **不读取**：

- `historyContext`
- `knowledgeContext`
- ChromaDB
- 外部 MCP 内容

### 6.2 更新规则

- 同一 `user_id + insight_id` 再次 feedback → **更新**当前 feedback，不重复累计（V2-C）。
- feedback 更新后重新查询 profile → 反映最新 snapshot（V2-E）。
- 模型推断**不能**覆盖用户 feedback。
- mock / fallback 报告**不得**写入真实 feedback 或 profile evidence。

### 6.3 冲突与遗忘

设计规则（部分已在 builder 启发式中体现，部分为 V4+ 扩展）：

- 新旧 evidence 冲突 → 记录 `conflict` evidence，不 silent 覆盖
- 过时倾向 → 先 `inactive` / weakened，不物理删除 evidence
- V2 不做自动物理删除；`hidden` / `deleted` 为用户治理预留
- 不把单次输入固化为长期偏好

## 7. 读取路径

| 用户 / 开发者需求 | API / 模块 | 读哪一层 |
| --- | --- | --- |
| 查看轻量画像 | `GET /api/users/{user_id}/profile` | L3 |
| 查看历史报告 | `GET /api/users/{user_id}/reports` | L1 |
| 查看报告详情 | `GET /api/reports/{report_id}` | L1 + L4（history/knowledge/evaluation） |
| 查看最近变化 | `GET .../reports/comparison/latest` | L5 只读 |
| 报告中的历史参考 | `ReportResponse.historyContext` | L4 |
| 报告中的知识参考 | `ReportResponse.knowledgeContext` | L4 |
| 开发期 trace | `GET /api/analysis-jobs/{job_id}/debug` | L1 logs + L4 assembly trace |

**ChromaDB 不作为 V2/V3 业务记忆来源。** 业务事实以 PostgreSQL（或 memory repository）为准。

## 8. 治理不变量

以下规则横切 V2/V3，V4 扩展不得破坏：

```text
1. 当前输入 evidence 优先于 history / knowledge / external context。
2. 用户 feedback 优先于模型推断。
3. history / knowledge / 外部源不得写入 profile positive evidence。
4. not_me 不得进入正向 profile summary。
5. unsure 不得强化正向画像。
6. 被否定解释不得复现为正向 profile item。
7. 每条 profile item 至少一条 evidence。
8. 画像与 Agent 输出不做人格、心理、能力、命运判断。
9. 不把画像用于推荐或消费引导。
10. mock / fallback / unavailable 能力必须显性标记。
```

- V2-E：`test_memory_governance_validation.py`
- V3-E：`test_v3_governance_validation.py`
- 指标：`13-验证与评估文档.md` §6.6、§15.1.1–15.1.5

## 9. 与版本路线图的关系

| 版本 | 记忆 / User Model 贡献 |
| --- | --- |
| V1 | 输入、报告、feedback、analysis_logs 闭环 |
| V2 | profile 三表、feedback 权重、comparison、治理验收 |
| V3 | history/knowledge supplementary context；evaluation；debug trace |
| V4（规划） | runtime、多模态、trajectory、知识图谱、Agent、MCP |

一句话：

```text
V1 是地基，V2 是记忆，V3 是可信度，V4 是 Agent 化。
```

User Model 在 V4 的扩展方向是**时间型 profiling 与 observation**，不是另建一套平行记忆。

## 10. V4 扩展占位（未实现）

V4-0 规划扩展时，必须遵守 §5 与 §8。候选扩展：

### 10.1 Temporal Profiling & Trajectory（V4-B）

- 审美时间轴事件：必须链接 report / feedback / comparison evidence
- 周期性摘要：聚合已有 evidence，不生成无来源新偏好
- stable / recent / weakening 语义延续 V2 status
- 实现任务单：`docs/iterations/v4-b-aesthetic-trajectory-temporal-profiling.md`（**已验收**）

### 10.2 Knowledge Graph（V4-C）

- 概念关系边必须有 `sourceEvidence`
- 图谱与外部 RAG **不进入** profile positive evidence
- 实现任务单：`docs/iterations/v4-c-knowledge-graph-external-rag-runtime.md`（**已验收**）

### 10.3 Agent Runtime（V4-D）

- Agent 读取 L1–L5；写入 L3 只能走受 governance 约束的工具
- 每个 action 持久化 reason、toolName、inputRefs、outputRefs
- Agent **不**维护独立黑盒 persona 替代 profile 三表
- 实现任务单：`docs/iterations/v4-d-agent-runtime-mcp-integration.md`（**已验收**）

### 10.4 MCP External Context（V4-D）

- 导入需 user-confirmed；标记 `external_context`
- 默认 supplementary context，不是 preference fact
- 实现任务单：同上（**已验收**）

### 10.5 明确不做

- 无边界自动更新 profile
- 未经确认的 external write
- 无 evidence 的图谱边
- 把 Agent 观察直接当 stable profile 而不经 feedback / feature evidence
