# AI 审美形成系统：文档体系说明

## 1. 文档排序原则

当前 `docs/` 目录按“从想清楚到做出来”的顺序编号：

```text
00 入口导航
01 产品定义
02 版本路线
03 MVP 范围
04-06 AI 认知与输出
07-12 工程实现
13-14 验证与展示
16 开发收口
```

这个顺序不是按文档创建时间排，而是按项目推进顺序排：

```text
先明确项目是什么
↓
再明确分几版做
↓
再锁定第一版范围
↓
再定义 AI 怎么理解和输出
↓
再定义系统怎么落地
↓
最后定义怎么验证、展示和开发收口
```

## 3. 四个文档组

### 3.1 产品组：01-03

这组只负责“做什么”和“为什么做”。

- `01` 定义项目灵魂。
- `02` 定义多版本路线。
- `03` 锁定第一版 MVP。

规则：

- 不在产品组里写具体代码目录。
- 不在 MVP 文档里塞 V3 / V4 能力。
- 如果版本边界冲突，以 `02-版本迭代路线图.md` 为准。
- 如果 MVP 功能冲突，以 `03-MVP功能需求文档.md` 为准。

### 3.2 AI 组：04-06

这组只负责“AI 如何理解、分析、表达”。

- `04` 定义底层表征，不讨论后端架构。
- `05` 定义分析逻辑，不讨论页面布局。
- `06` 定义报告输出，不新增系统功能。

规则：

- 底层特征字段只在 `04` 里做权威定义。
- 分析流程以 `05` 为准。
- 报告语气和禁止表达以 `06` 为准。

### 3.3 工程组：07-12

这组只负责“怎么实现”。

- `07` 是系统架构和数据结构。
- `08` 是代码目录和分层。
- `09` 是 workflow 执行顺序。
- `10` 是 prompt contract。
- `11` 是模块拆分和接口测试。
- `12` 是开发任务和里程碑。

规则：

- 数据库和 API 以 `07` 为准。
- 代码放置以 `08` 为准。
- 分析任务步骤以 `09` 为准。
- LLM 输出 schema 以 `10` 为准。
- 模块验收以 `11` 为准。
- 开发顺序以 `12` 为准。

### 3.4 验证与展示组：13-14

这组只负责“怎么证明、怎么讲”。

- `13` 定义验证方法。
- `14` 定义项目展示和简历包装。

规则：

- `14` 不能反向决定 MVP 范围。
- `13` 可以约束报告质量和测试标准。

### 3.5 开发收口：16

这份文档只负责把 V1 的最终开发范围压成清单。

- `16` 是正式开发 V1 前的最后确认。
- 如果 `11` 的详细模块内容和 `16` 的 V1 清单冲突，V1 以 `16` 为准。
- `16` 不定义长期愿景，只定义 V1 要交付什么。

## 7. 新增文档规则

以后新增文档前，先判断是否能放进现有文档。

只有出现以下情况才新增：

- 已有文档会变得过长。
- 新内容属于新的职责边界。
- 新内容会被频繁单独引用。

新增编号建议：

- 产品路线类放在 `02` 附近。
- MVP 需求类放在 `03` 附近。
- AI 分析类放在 `04-06`。
- 工程实现类放在 `07-12`。
- 验证展示类放在 `13-14`。
协作规范不进入项目设计编号体系；例如 Git 提交规范使用英文文件名 `git-commit-message-guide.md`。

## 8. 当前阶段提醒

当前只应该专注 V0 / V1：

- V0：前端原型 + mock 报告。
- V1：真实输入、底层特征、embedding、相似性分组、报告、反馈。

暂时不要提前实现：

- RAG
- Agent
- MCP
- 知识图谱
- 音乐 / 视频
- 复杂长期画像

一句话：

> 文件编号就是项目推进顺序；文档定位就是每份文档只回答一个层级的问题。
