# AI 审美形成系统：文档体系说明

## 1. 文档体系目标

这套文档用于把 AI 审美形成系统从一个概念想法，推进为可开发、可展示、可写进简历的系统设计。

整体采用双层表达：

- 产品层：审美镜子、审美轨迹、个人风格演化。
- 工程层：多模态用户偏好建模、embedding、结构化生成、RAG、长期记忆、Evaluation、Observability。

核心原则是：

> 不为了热门技术改变项目灵魂，但要让项目的 AI 工程价值被看懂。

## 2. 文档清单

### 00-文档体系说明

说明整套文档的组织方式、阅读顺序和技术分层。

### 01-产品概念说明书

定义系统是什么、为什么做、产品气质是什么，以及如何用产品表达和工程表达同时描述这个项目。

### 02-MVP功能需求文档

定义第一版做什么、不做什么、页面流程、功能优先级和 MVP 成功标准。

重点边界：

- MVP 做结构化分析、embedding、聚类、可解释报告和用户反馈。
- MVP 不强行做完整 Agent、复杂 RAG、MCP 或图数据库。

### 03-AI分析逻辑文档

定义 AI 如何分析用户输入。

包括：

- 单样本特征提取
- embedding 表示
- 跨样本聚类
- 动态解释生成
- Function Calling 设计
- RAG 与历史检索边界
- Agent 与知识图谱边界

### 04-审美表征体系文档

定义系统理解审美时使用的 representation layer，而不是固定标签库。

包括：

- 底层感知特征
- 中层风格结构
- 高层解释主题
- 动态标签生成
- possibleInterpretations
- 去作者中心化测试
- latent aesthetic space

后续知识图谱可以基于这份表征体系扩展，但高层解释不能被当成固定事实。

### 05-数据结构与系统架构文档

定义系统总体架构、数据流、数据表、API、AI 服务分层和扩展架构。

包括：

- 数据层
- 特征层
- 向量层
- 报告层
- 反馈层
- 画像层
- RAG 模块
- 可观测性模块
- 知识图谱模块
- MCP 外部上下文模块

`05` 只保留模块分层和架构关系，不展开每个模块的详细输入输出和测试。

### 06-输出报告模板文档

定义系统最终如何对用户说话。

重点是：

- 先观察，再解释。
- 每条洞察必须有依据。
- RAG 知识只能增强解释，不能替代用户输入证据。
- 避免心理测试、算命和空泛人格判断。

### 07-验证与评估文档

定义如何证明系统不是胡说。

包括：

- 特征层验证
- embedding 聚类验证
- 一致性验证
- 用户主观认可
- 可解释性验证
- RAG 检索相关性
- Agent 行为边界
- Evaluation 与 Observability 指标

### 08-项目展示、简历包装与技术路线文档

定义如何把项目写进简历、作品集和面试讲述，同时说明技术分层、工程包装和长期路线。

重点是把项目讲成：

> 面向长期个性化 AI 的多模态用户偏好建模系统。

而不是：

> AI 分析你的审美人格。

### 09-模块拆分与接口测试文档

定义系统的工程模块拆分、每个模块的职责、输入、输出、依赖关系、测试方式和验收标准。

重点是把系统拆成可开发的模块：

- 输入与存储
- 底层特征提取
- embedding
- 聚类与共性分析
- 动态解释候选
- 报告生成
- 用户反馈
- 基础画像
- 可观测日志
- Prompt 管理与模型调用
- 进阶 RAG / Agent / 知识图谱扩展

`09` 是开发执行文档，负责展开 `05` 中模块的详细接口与测试。

### 10-开发任务拆分与里程碑计划

定义技术选型、开发里程碑、每一步开发任务、验收标准和可交给 AI 执行的任务提示。

重点是把系统拆成可以逐步实现的工程任务：

- 项目初始化
- React 前端与 FastAPI 后端骨架
- Oracle 业务表结构
- ChromaDB 向量库 collection
- 输入上传
- 底层特征提取
- embedding 与聚类
- 动态解释候选
- 报告生成
- 用户反馈
- 历史报告与基础画像
- 测试样本与 Demo 打磨

### 11-Prompt Contract 与结构化输出规范

定义所有 AI prompt 的行为边界、输入 schema、输出 schema、禁止表达、失败处理和测试方式。

重点是把 LLM 输出从“自然语言建议”约束为可校验的工程 contract：

- 图片底层特征提取 prompt
- 文本底层特征提取 prompt
- 动态解释候选 prompt
- 报告生成 prompt
- 用户画像更新 prompt
- evidence binding
- uncertainty
- prompt versioning
- schema validation

`11` 是后续实现 AI 服务和 prompt 调用时的重要约束，避免 JSON 崩坏、解释越界、人格诊断和 developer bias。

### 12-AI Workflow 编排与任务执行文档

定义一次完整分析任务从创建 job 到生成报告、收集反馈、更新画像的执行链路。

重点是明确每个 workflow step 的：

- 输入来源
- 输出去向
- 是否异步
- 是否可重试
- 是否允许部分失败
- timeout
- token / cost 记录
- observability log

`12` 是 FastAPI 后端实现分析任务编排的主要依据，避免把所有逻辑堆在一个接口或一个 service 中。

### 13-项目目录结构与代码分层规范

定义 React 前端、FastAPI 后端、Oracle 数据访问、ChromaDB 向量服务、prompt、schema、workflow、测试文件的放置规则。

重点是明确：

- 前端页面、组件、feature、service 的边界
- FastAPI route、service、repository、workflow 的边界
- Oracle 与 ChromaDB 的职责分离
- prompt 文件和 AI client 的放置位置
- Pydantic schema 与前端类型的对应关系
- 测试目录结构

`13` 是让 AI Coding Agent 稳定协作开发的目录边界文档，避免 route 巨石化、utils 混乱和 schema 分散。

## 4. 技术分层总览

### 4.1 MVP 必须体现

- 多模态输入
- 稳定底层特征提取
- embedding 表示
- 聚类 / 相似度分析
- LLM 结构化报告生成
- evidence binding
- 多个可能解释
- 用户反馈闭环
- 基础评估指标

### 4.2 进阶阶段体现

- Function Calling
- RAG 审美知识库
- personalized memory retrieval
- prompt versioning
- prompt loading / rendering
- Prompt Template 管理
- Prompt Versioning 管理
- insight traceability
- long-term user profile
- evaluation metrics
- observability logging

### 4.3 高级阶段体现

- 审美观察 Agent
- 审美知识图谱
- MCP 外部上下文接入
- 周报 / 月报自动生成
- 风格演化推理
- 外部收藏源导入

## 5. 最终表达原则

不要把项目讲成：

> 我用了很多热门 AI 技术。

而要讲成：

> 为了解决主观审美难以稳定解释、用户偏好需要长期建模、LLM 容易空泛输出的问题，我设计了一个多模态用户偏好建模系统。它通过结构化特征、embedding 聚类、RAG 知识增强、可解释生成、用户反馈、长期记忆和评估体系，让审美洞察变得有依据、可追踪、可迭代。

技术必须服务于系统问题，而不是作为装饰。
