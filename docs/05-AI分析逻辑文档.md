# AI 审美形成系统：AI 分析逻辑文档

## 1. 文档目的

这份文档定义系统如何从用户输入中提取审美特征、形成结构化表示、生成解释型洞察，并避免变成“AI 算命”。

核心原则是：

> 不让 LLM 直接凭感觉写结论，而是先提取结构化特征，再基于特征生成可解释洞察。

更新后的关键原则是：

> 底层特征是 representation，高层主题是 interpretation。系统不能把解释语言当成真实结构。

当前实现边界：

```text
V1 / V2-A 已实现：固定 workflow、mock / heuristic 特征抽取、embedding、相似性分组、报告生成、反馈保存、历史报告回看。
V2-B planned：轻量画像数据模型与 profile evidence，不直接进入复杂权重或自动遗忘。
V2-C / V2-D planned：反馈权重、画像更新、近期变化提示。
V3+ planned：RAG、personalized retrieval、Function Calling、Agent workflow 和知识图谱。
```

## 2. AI 分析总流程

```text
用户输入
↓
输入预处理
↓
单样本特征提取
↓
embedding 表示
↓
跨样本相似性分组
↓
共性与差异分析
↓
动态生成候选解释
↓
可解释洞察生成
↓
用户反馈收集
↓
用户画像更新
```

进阶版本中，这条流程可以通过 Function Calling 拆成可调试工具调用，而不是依赖一个大 prompt 一次性完成。MVP 阶段先实现固定流程；当系统需要根据输入类型、历史记录和中间结果动态选择分析路径时，再升级为 Agent workflow。

## 3. 输入类型

### 3.1 MVP 输入类型

第一版支持：

- 图片
- 文本

图片用于分析视觉审美，文本用于分析语义、情绪、意象和叙事倾向。

### 3.2 后续输入类型

后续可以扩展：

- 音乐
- 视频
- 链接
- 收藏夹
- 歌单
- 社交平台收藏

这些输入最终都应转化为统一的特征表示和 embedding。

## 4. 单样本分析

系统首先对每个输入单独分析，生成结构化特征。

第一版应优先提取少量稳定底层特征，不要一开始做庞大的审美 ontology。风格词和主题词可以作为动态解释生成，而不是固定枚举。

### 4.1 图片特征

MVP 图片分析只提取少量稳定字段。每个字段都必须包含 `value`、`confidence` 和 `evidence`，避免模型只给出抽象标签。

图片底层特征固定为：

- saturation：饱和度
- brightness：明度
- colorTemperature：色温
- colorContrast：色彩对比
- personPresence：人物存在
- spatialDensity：空间密度
- compositionComplexity：构图复杂度
- textureComplexity：纹理复杂度
- moodAtmosphere：情绪氛围

示例结构：

```json
{
  "type": "image",
  "lowLevelFeatures": {
    "saturation": {
      "value": "低",
      "confidence": 0.82,
      "evidence": ["画面整体以灰色和低纯度蓝色为主"]
    },
    "brightness": {
      "value": "中低",
      "confidence": 0.74,
      "evidence": ["主体区域缺少高亮色块"]
    },
    "colorTemperature": {
      "value": "冷",
      "confidence": 0.8,
      "evidence": ["蓝灰色占比较高"]
    },
    "personPresence": {
      "value": "缺席",
      "confidence": 0.95,
      "evidence": ["画面中没有明显人物主体"]
    }
  },
  "candidateStyleLabels": ["冷感空间", "极简倾向"],
  "sampleEvidence": ["画面中大面积灰色墙面", "人物缺席", "空间元素较少"]
}
```

### 4.2 文本特征

MVP 文本分析只提取少量稳定字段。每个字段同样必须包含 `value`、`confidence` 和 `evidence`。

文本底层特征固定为：

- sentimentTone：情绪倾向
- emotionIntensity：情绪强度
- narrativeDensity：叙事密度
- concreteness：具体 / 抽象程度
- imageryDensity：意象密度
- rhythm：语言节奏
- timeOrientation：时间感
- spatialReference：空间感
- subjectDistance：主体距离

示例结构：

```json
{
  "type": "text",
  "lowLevelFeatures": {
    "sentimentTone": {
      "value": "低沉",
      "confidence": 0.78,
      "evidence": ["使用了“空房间”“没有回声”等表达"]
    },
    "emotionIntensity": {
      "value": "弱",
      "confidence": 0.7,
      "evidence": ["情绪表达克制，没有强烈情绪词"]
    },
    "narrativeDensity": {
      "value": "低",
      "confidence": 0.76,
      "evidence": ["文本更像片段观察，而不是完整事件叙述"]
    }
  },
  "candidateStyleLabels": ["低声叙述", "片段化表达"],
  "sampleEvidence": ["反复出现空房间意象", "句子节奏缓慢", "情绪表达克制"]
}
```

## 5. embedding 表示

### 5.1 embedding 的作用

embedding 用来把不同输入映射到可比较的向量空间。

系统不应该只依赖 LLM 的文字判断，而应该让输入在审美空间中形成可计算关系：

- 哪些输入彼此接近
- 哪些输入彼此接近
- 哪些输入是异常点
- 用户偏好是否存在多个中心
- 新输入是否靠近历史偏好

### 5.2 embedding 类型

MVP 可以使用：

- 文本 embedding
- 图片 embedding
- 多模态 embedding

后续可以探索：

- CLIP
- SigLIP
- Qwen VL
- Gemini 多模态
- OpenAI embedding

### 5.3 embedding 输出

每个样本应保存：

- 原始输入
- 结构化特征
- embedding 向量
- 提取时间
- 模型版本

这样后续可以重跑分析，也可以比较不同模型效果。

## 6. 跨样本相似性分组

MVP 阶段不把小样本结果称为严格聚类，而称为“相似性分组”。

原因是用户一次通常只上传 3-10 个样本，样本量不足以支撑严肃统计意义上的聚类。系统可以根据 embedding 距离和底层特征重合度，把样本组织成可解释的临时分组，但不能把分组当成稳定结论。

### 6.1 分组目标

相似性分组的目标是帮助报告解释，而不是证明数学分类正确。

系统需要回答：

- 哪些输入属于同一种审美倾向
- 这些输入的共同特征是什么
- 哪些输入看起来不同但在情绪或结构上接近
- 哪些输入是用户审美中的异常点

### 6.2 分组策略

MVP 可以采用保守策略：

- 样本少于 4 个：不做分组，只输出共同特征。
- 样本 4-7 个：最多输出 2 个相似性组。
- 样本 8-12 个：最多输出 3 个相似性组。
- 无法稳定分组时，输出 `insufficient_structure`。

分组依据可以由两部分组成：

- embedding 相似度
- 底层特征重合度

### 6.3 分组输出

每个相似性组需要包含：

- 分组名称
- 包含样本
- 共同特征
- 代表性样本
- 与其他分组的区别
- 可能对应的审美倾向
- 不确定性说明

示例：

```json
{
  "groupName": "冷感低密度组",
  "samples": ["image_01", "image_03", "text_02"],
  "commonFeatures": ["低饱和", "空旷空间", "结构感", "人物缺席"],
  "differenceFromOthers": "比其他输入更冷、更硬、更强调空间秩序",
  "possibleMeaning": "用户可能被去人化、结构化、安静的空间吸引",
  "uncertainty": "当前样本较少，该分组只表示本次输入中的相似结构"
}
```

## 7. 共性分析

系统需要在所有输入中寻找重复出现的特征。

### 7.1 高频特征

统计反复出现的元素：

- 色彩
- 材质
- 情绪
- 空间
- 意象
- 风格
- 叙事结构

### 7.2 跨模态共性

跨模态共性是项目最有价值的部分。

例如：

- 图片中的空旷空间
- 文本中的孤独叙事
- 歌词中的远距离关系

它们可能共同指向：

> 疏离感。

系统应该能够把不同模态中的相似结构连接起来。

## 8. 差异与矛盾分析

用户审美不一定是单一的，系统应该识别内部矛盾。

常见矛盾包括：

- 秩序感 vs 衰败感
- 温柔感 vs 冷感
- 自然感 vs 工业感
- 叙事性 vs 结构性
- 复古感 vs 未来感
- 亲密感 vs 疏离感
- 完成感 vs 未完成感

矛盾不是错误，而是审美张力。

示例输出：

> 你的输入一方面偏向极简秩序，另一方面又反复出现破损、废墟和未完成状态。这说明你的审美可能不是单纯追求干净，而是在“秩序”和“失控”之间寻找张力。

## 9. 动态解释生成

高层主题是对多个特征的综合解释，不是客观事实。

### 9.1 解释生成原则

解释不能凭空生成，必须来自多个输入证据。

一个解释至少应该由 2-3 类证据支持：

- 视觉证据
- 文本证据
- 情绪证据
- 结构证据
- 历史重复证据

### 9.2 多解释候选

系统不应该只输出一个固定主题，而应该输出多个 possibleInterpretations。

示例：

```json
{
  "observedFeatures": ["低饱和", "人物缺席", "空间密度低"],
  "possibleInterpretations": [
    {
      "name": "结构化疏离",
      "confidence": 0.64,
      "evidence": ["低饱和", "人物缺席", "空间密度低"]
    },
    {
      "name": "冷感空间偏好",
      "confidence": 0.58,
      "evidence": ["冷色调", "大面积空间", "人物缺席"]
    }
  ]
}
```

用户反馈后，系统再判断哪个解释更适合进入长期画像。

## 10. 洞察生成逻辑

LLM 负责把结构化分析转化为用户可读的洞察。

### 10.1 输入给 LLM 的内容

LLM 不应只拿原始图片或文字直接生成报告，而应接收：

- 单样本特征
- 相似性分组结果
- 高频特征
- 风格矛盾
- 动态解释候选
- 用户历史反馈
- 禁止输出规则

### 10.2 洞察结构

每条洞察建议包含：

```text
洞察标题：
系统观察：
输入依据：
可能解释：
不确定性：
用户反馈：
```

### 10.3 输出语气

推荐使用：

- “系统观察到……”
- “这些输入共同指向……”
- “可以推测你可能对……有兴趣”
- “这不一定代表稳定人格，但说明近期输入中……”

避免使用：

- “你就是……”
- “你的灵魂……”
- “命中注定……”
- “你内心深处一定……”

## 11. 防止玄学化的规则

系统必须遵守以下规则：

1. 不输出无法追溯依据的结论。
2. 不直接诊断人格、心理、命运。
3. 不使用过度绝对化语气。
4. 不把单个输入上升为长期人格。
5. 不使用“敏感、孤独、复杂”这类空泛标签作为最终结论。
6. 每条洞察至少绑定 2-3 个证据。
7. 必须区分“观察”和“推测”。

## 12. 用户反馈如何进入系统

用户反馈不是装饰，而是系统长期个性化的关键。

### 12.1 反馈类型

每条洞察可收集：

- 完全不像我
- 有点意思
- 很像我
- 有被看见的感觉

### 12.2 反馈用途

反馈用于：

- 调整用户画像权重
- 识别无效标签
- 优化后续 prompt
- 标记高命中洞察类型
- 形成个人化解释风格

### 12.3 反馈后的系统行为

如果用户多次否定某类洞察，系统应降低相关标签权重。

如果用户多次认可某类洞察，系统应在后续报告中观察它是否持续出现，但不能机械重复。

## 13. 长期演化分析

第一版可以只做即时分析，但数据结构必须支持长期演化。

未来系统应分析：

- 关键词变化
- 相似性中心移动
- 新主题出现
- 旧主题消退
- 风格冲突增强或减弱
- 用户反馈偏好变化

示例：

> 过去三次报告中，你的输入从“叙事性图像”逐渐转向“结构性空间”，低饱和和几何构图出现频率明显增加。系统推测你的审美正在从情节感转向结构感。

## 14. AI 分析质量标准

一条好的洞察应满足：

- 有明确主题
- 有输入依据
- 有解释逻辑
- 不空泛
- 不绝对
- 能让用户产生自我理解
- 可以被用户反馈验证

一条失败洞察通常表现为：

- 像心理测试
- 没有证据
- 谁看都适用
- 只堆形容词
- 直接判断人格
- 和输入关系不明显

## 15. MVP 阶段推荐实现

第一版可以采用简单但清晰的三步方案：

1. 用多模态模型提取每个输入的结构化特征。
2. 用 embedding 和规则分析做相似性分组、共性、矛盾。
3. 用 LLM 基于结构化结果生成审美报告。

第一版不追求模型复杂，而追求：

> 输出有依据、结果有结构、用户有共鸣。

## 16. Function Calling 设计

进阶阶段建议将分析过程拆成函数或工具：

```text
analyze_image_features(input_id)
analyze_text_features(input_id)
generate_embedding(input_id)
cluster_aesthetic_inputs(input_ids)
detect_common_patterns(feature_set)
detect_style_contradictions(feature_set)
retrieve_user_memory(user_id, current_features)
retrieve_aesthetic_knowledge(query_tags)
generate_aesthetic_report(analysis_context)
save_user_feedback(insight_id, rating)
update_user_profile(user_id, feedback)
```

Function Calling 的目标不是炫技，而是解决三个工程问题：

- 让每一步输出可检查。
- 让失败点可定位。
- 让 LLM 的生成建立在结构化上下文上。

## 17. RAG 与历史检索

本系统中需要区分两种检索。

### 17.1 个性化历史检索

personalized memory retrieval 用于检索用户过去的输入、报告、标签和反馈。

它回答：

- 用户过去是否出现过类似风格？
- 当前主题是新出现还是长期稳定？
- 哪些标签曾被用户否定？
- 本次输入和历史哪次报告最相似？

### 17.2 审美知识库 RAG

aesthetic knowledge RAG 用于检索外部或自建审美知识库。

知识库可以包含：

- 设计风格解释
- 摄影与构图知识
- 色彩与材质语言
- 服装风格资料
- 艺术流派资料
- 文学与叙事风格说明
- 系统自建审美表征体系

它回答：

- “低饱和 + 混凝土 + 人物缺席”可以关联哪些风格概念？
- “秩序感 vs 衰败感”在审美解释中如何描述？
- 某个标签应该如何以更专业但不玄学的方式解释？

RAG 的作用是增强解释质量，不是替代用户输入证据。报告仍必须以用户样本为主要依据。

## 18. Agent 边界

MVP 阶段不直接宣称完整 Agent。

更准确的说法是：

> multi-step AI workflow。

当系统具备以下能力后，才适合升级为“审美观察 Agent”：

- 根据输入类型自主选择工具。
- 根据历史记录决定是否做时间对比。
- 根据用户反馈调整后续分析重点。
- 主动发现审美变化并生成周报 / 月报。
- 在证据不足时向用户追问补充输入。

Agent 的定位应该是长期观察者，而不是简单的流程编排器。

## 19. 知识图谱边界

知识图谱适合在高级阶段表达审美概念之间的关系。

例如：

```text
低饱和 → 关联 → 克制感
混凝土 → 关联 → 工业感
人物缺席 → 关联 → 疏离感
工业感 + 疏离感 + 空旷空间 → 组成 → 工业化孤独感
```

第一阶段可以先用关系表或 JSON 表达这些关系，不需要直接上图数据库。等底层特征和中层关系稳定后，再考虑 Neo4j 或其他图数据库。
