# AI 审美形成系统：MVP 功能需求文档

## 0. 文档职责

这份文档只定义 MVP 的产品范围：

- 用户要完成什么。
- 系统第一版提供哪些体验。
- MVP 支持和不支持哪些输入输出。
- 什么样的结果算产品层面成立。

它不负责定义具体数据库表、API 路径、mock schema 或代码目录。V1 的工程验收清单以 `16-V1开发收口清单.md` 为准；当前开发任务顺序以 `12-开发任务拆分与里程碑计划.md` 为准；实际完成状态以 `15-迭代执行记录.md` 和 `archive/` 为准。

## 1. MVP 目标

第一版 MVP 的目标不是做完整平台，而是验证一个最小但有辨识度的核心体验：

> 用户上传一组图片和文字样本，系统生成一份有证据绑定的审美剖析报告，并允许用户反馈每条洞察是否贴近自己。

MVP 要证明的不是“AI 真的懂审美”，而是：

- 系统能从输入中提取稳定、可复用的底层特征。
- 系统能发现一组样本中的相似性和差异。
- 系统能基于证据生成克制的可能解释。
- 用户能判断哪些解释“像我”或“不像我”。

## 2. MVP 产品定位

MVP 的产品形态是：

> AI 审美镜子。

它只回答第一阶段最核心的问题：

> 我最近喜欢的这些图片和文字里，有哪些反复出现的审美倾向？

MVP 不做完整审美成长平台，也不做推荐系统。长期审美轨迹、用户画像、RAG、Agent 和知识图谱都放到后续迭代。

## 3. 核心用户路径

1. 用户进入首页。
2. 用户看到一句清晰说明：上传你最近喜欢的图片和文字，让系统观察其中反复出现的审美倾向。
3. 用户上传 3-10 个样本。
4. 系统创建分析任务。
5. 系统提取底层特征。
6. 系统生成 embedding，并进行小样本相似性分组。
7. 系统生成结构化审美报告。
8. 用户查看报告、证据和不确定性。
9. 用户对每条洞察反馈：像 / 不像 / 不确定。
10. 系统保存输入、特征、报告和反馈。

## 4. MVP 输入范围

### 4.1 支持输入

第一版只支持：

- 图片
- 文字

图片可以包括摄影、穿搭、建筑、空间、设计图、插画、收藏图片。

文字可以包括书摘、歌词、短句、用户自己写的描述、对图片的补充说明。

### 4.2 输入限制

- 最少 3 个样本。
- 建议 5-10 个样本。
- 最多 12 个样本。
- 图片限制大小和格式。
- 单段文字限制长度。

说明：样本数量少时，系统只输出“相似性分组”和“共同特征”，不宣称得到稳定聚类。

### 4.3 MVP 暂不支持

- 音乐音频分析
- 视频分析
- 第三方平台同步
- 复杂登录 / 权限系统
- 社交分享社区
- 自动推荐内容
- 复杂 RAG 审美知识库
- Agent 工作流
- MCP 外部上下文接入
- 图数据库或完整知识图谱
- 训练自有模型

## 5. MVP 输出范围

MVP 报告只保留 5 个核心部分。

### 5.1 总体摘要

用 2-4 句话说明本次输入的整体倾向。

要求：

- 使用倾向性语言。
- 不做人格判断。
- 至少引用 2 类底层特征作为依据。

### 5.2 底层特征摘要

展示统一 schema 下的底层特征。

图片特征优先包括：

- 色彩倾向
- 饱和度
- 明度
- 色温
- 空间密度
- 人物存在
- 构图复杂度
- 材质 / 纹理
- 情绪氛围

文本特征优先包括：

- 情绪倾向
- 抽象程度
- 叙事密度
- 意象类型
- 节奏感
- 时间感
- 空间感
- 主体距离

每个特征必须有来源依据。

### 5.3 相似性分组

系统可以把样本分成 1-3 个“相似性组”。

注意：

- MVP 不承诺严格聚类准确性。
- 分组名是解释性命名，不是客观分类。
- 样本不足时可以不分组，只输出共同特征。
- 每个分组必须说明包含哪些样本、共同特征是什么。

### 5.4 可能解释

系统基于底层特征和相似性分组生成多个可能解释。

要求：

- 至少 2 个解释候选。
- 每个解释必须绑定输入证据。
- 每个解释都要保留不确定性。
- 不能把解释当成用户真实人格或固定审美结论。

### 5.5 重点洞察与反馈

报告生成 3-5 条重点洞察。

每条洞察结构：

```text
洞察标题：
观察依据：
可能解释：
不确定性：
相关输入：
用户反馈：
```

反馈选项：

```text
[ ] 不像我
[ ] 不确定
[ ] 有点像
[ ] 很像我
```

## 6. P0 功能清单

MVP 必做功能：

- 首页说明与上传入口
- 图片上传
- 文字输入
- 样本预览与删除
- 创建分析任务
- 分析状态展示
- 底层特征提取
- embedding 生成
- 小样本相似性分组
- 结构化报告生成
- 证据展示
- 洞察反馈
- 报告保存

## 7. P1 功能清单

MVP 后的第一轮增强：

- 历史报告列表
- 报告详情回看
- 两次报告的简单对比
- 轻量用户画像
- 基础可观测日志
- 报告导出

## 8. P2 功能清单

后续扩展：

- personalized retrieval
- 审美知识库 RAG
- 审美时间轴
- 更完整用户画像
- 音乐 / 视频输入
- 外部收藏源导入
- 审美观察 Agent
- 知识图谱

## 9. 页面范围

### 9.1 首页

目标：10 秒内让用户理解产品。

包含：

- 一句话产品说明
- 示例洞察
- 上传入口

### 9.2 上传页

包含：

- 图片上传
- 文字输入
- 样本数量提示
- 样本预览
- 删除样本
- 开始分析按钮

### 9.3 分析等待页

展示固定步骤：

```text
正在读取样本
正在提取底层特征
正在生成向量表示
正在寻找相似性结构
正在生成审美报告
```

### 9.4 报告页

包含：

- 总体摘要
- 底层特征
- 相似性分组
- 可能解释
- 重点洞察
- 用户反馈

### 9.5 历史页

MVP 可以暂缓。若实现，只需要报告列表和详情入口。

## 10. 数据保存要求

MVP 至少保存：

- 匿名用户 ID
- 输入样本
- 样本类型
- 样本文本或图片路径
- 统一底层特征 JSON
- embedding metadata
- 分析任务状态
- 报告 JSON
- 洞察条目
- 用户反馈
- prompt version
- model name
- 创建时间

业务数据保存到 PostgreSQL。向量和检索 metadata 保存到 ChromaDB。

## 11. AI 输出要求

AI 输出必须遵守：

- 不做人格诊断。
- 不使用玄学表达。
- 不使用绝对判断。
- 不只输出抽象形容词。
- 每个结论都必须关联输入证据。
- 区分事实观察和解释推测。
- 使用“可能”“倾向于”“系统观察到”等表达。

## 12. MVP 成功标准

产品层成功标准：

- 用户能顺利完成一次上传。
- 用户能理解报告在说什么。
- 用户觉得至少 1 条洞察“有点像”或“很像我”。
- 用户能看到每条洞察的依据。
- 输出不像心理测试或算命。

工程层成功标准：

- 底层特征按统一 schema 保存。
- 每条洞察能追溯到输入证据。
- 相似性分组能解释共同特征。
- 用户反馈能保存。
- prompt version 和 model name 可记录。
- 报告生成流程可拆分、可调试。

## 13. MVP 明确不做

第一版不做：

- 长期画像自动推理
- 历史趋势图
- 周报 / 月报
- RAG
- Agent
- 知识图谱
- MCP
- 多用户复杂权限
- 推荐系统

这些不是放弃，而是为了保护第一版核心体验。

## 14. MVP 一句话验收

MVP 完成时，应该能够演示：

> 我上传 5 张图片和 2 段文字，系统提取了统一底层特征，发现其中几组相似倾向，生成了 3-5 条有输入证据的审美洞察，并让我反馈哪些解释真正贴近我。
