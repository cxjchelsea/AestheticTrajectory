# AI 审美形成系统：版本迭代路线图

## 1. 文档目的

这份文档专门定义项目从原型到长期系统的多版本迭代方案。

它回答三个问题：

- 每一次迭代要解决什么核心问题。
- 每一版具体实现哪些功能。
- 哪些能力不应该提前塞进当前版本。

本文件是产品与工程共同使用的版本路线文档。`03-MVP功能需求文档.md` 只负责第一版 MVP，`12-开发任务拆分与里程碑计划.md` 负责把版本目标拆成开发任务。

## 2. 总体迭代原则

项目不要一开始追求完整平台，而要按能力递进：

```text
先证明报告体验成立
↓
再证明数据闭环成立
↓
再证明长期观察成立
↓
再证明检索增强有效
↓
最后扩展为长期个性化 AI 系统
```

每一版只解决一个主要矛盾：

- V0：用户是否喜欢这个体验。
- V1：系统是否能真实跑通最小闭环。
- V2：系统是否能记住历史并形成轻量画像。
- V3：系统是否能借助检索和评估变得更可靠。
- V4：系统是否能扩展为长期、多模态、主动观察系统。

## 3. 版本总览

| 版本 | 名称 | 核心目标 | 用户可感知结果 |
| --- | --- | --- | --- |
| V0 | 可演示原型 | 验证产品感觉 | 上传样本后看到一份 mock 审美报告 |
| V1 | 精简 MVP | 跑通真实闭环 | 真实生成有证据的审美报告并反馈 |
| V2 | 历史与画像 | 建立长期观察雏形 | 用户能看到历史、变化和轻量画像 |
| V3 | 检索增强与评估 | 提高解释质量和可信度 | 报告能参考历史与知识，并能被评估 |
| V4 | 长期个性化系统 | 扩展模态和主动观察 | 系统能长期追踪审美演化 |

## 4. V0：可演示原型

### 4.1 核心问题

先验证这个产品体验有没有吸引力：

> 用户上传一组审美样本后，是否愿意阅读一份“审美剖析报告”？

### 4.2 实现功能

前端：

- 首页
- 上传页
- 分析等待页
- 报告页
- 洞察反馈按钮

数据：

- 使用本地 mock JSON。
- 不接数据库。
- 不接真实模型。

报告：

- 总体摘要
- 底层特征
- 相似性分组
- 可能解释
- 重点洞察
- 反馈入口

### 4.3 不做

- PostgreSQL
- ChromaDB
- 真实 AI 调用
- 用户画像
- 历史报告
- RAG
- Agent

### 4.4 验收标准

- 可以完整演示一次用户路径。
- 报告结构清楚。
- 用户能理解产品不是心理测试。
- 至少有 1-2 条示例洞察让人觉得“这个方向有意思”。

## 5. V1：精简 MVP

### 5.1 核心问题

验证真实系统闭环是否成立：

> 系统能否从真实输入中提取底层特征，生成 embedding，做相似性分组，并输出有证据绑定的报告？

### 5.2 实现功能

输入：

- 图片上传
- 文字输入
- 样本预览
- 删除样本
- 输入数量限制

后端：

- FastAPI 项目骨架
- PostgreSQL 连接
- ChromaDB 连接
- 文件存储
- 分析任务状态

AI 分析：

- 图片底层特征提取
- 文本底层特征提取
- 统一底层特征 schema
- embedding 生成
- 小样本相似性分组
- possible interpretations 生成
- 结构化报告生成

报告：

- 总体摘要
- 底层特征摘要
- 相似性分组
- 可能解释
- 重点洞察
- 证据展示
- 用户反馈

数据保存：

- 输入样本
- 底层特征
- embedding metadata
- 分析任务
- 报告
- 洞察
- 反馈
- 基础日志

### 5.3 不做

- 完整登录系统
- 历史趋势
- 长期画像自动推理
- RAG
- Agent
- 知识图谱
- 音乐 / 视频输入

### 5.4 验收标准

- 用户能上传 3-10 个样本。
- 系统能真实生成报告。
- 每条洞察都有输入证据。
- 相似性分组不被包装成绝对聚类结论。
- 用户反馈能保存。
- PostgreSQL 是业务事实来源。
- ChromaDB 只保存向量和 metadata。

## 6. V2：历史报告与轻量画像

### 6.1 核心问题

让系统从一次性报告进入长期观察：

> 系统能不能记住用户过去的输入，并开始描述审美变化？

### 6.2 实现功能

历史：

- 历史报告列表
- 报告详情回看
- 按时间查看输入批次

对比：

- 最近两次报告对比
- 新增特征
- 减弱特征
- 重复出现的特征
- 可能的风格变化提示

轻量画像：

- 稳定底层特征统计
- 用户认可的解释
- 用户否定的解释
- 反馈权重
- 画像更新时间

前端：

- 历史页
- 报告对比页
- 轻量画像摘要

### 6.3 不做

- 自动推荐内容
- 复杂用户画像推理
- 大规模知识库 RAG
- 主动 Agent
- 周报 / 月报

### 6.4 验收标准

- 用户能看到过往报告。
- 系统能比较最近两次输入的共同点和差异。
- 用户反馈能影响轻量画像。
- 被否定的解释不会作为正向偏好进入画像。
- 画像只描述“系统观察到的倾向”，不做人格判断。

## 7. V3：检索增强与评估

### 7.1 核心问题

提高系统解释质量和工程可信度：

> 报告是否能参考历史和审美知识，同时仍然保持证据可追踪？

### 7.2 实现功能

个性化历史检索：

- 检索相似历史输入
- 检索历史报告摘要
- 检索用户曾经认可或否定的解释
- 将历史检索结果作为报告上下文

审美知识库 RAG：

- 小型审美知识文档
- 风格概念解释
- 设计 / 视觉 / 文学相关知识片段
- 检索来源记录

评估：

- evidence coverage
- feedback hit rate
- grouping stability
- prompt output schema pass rate
- hallucination check

可观测性：

- prompt version
- model name
- latency
- token / cost
- retrieval trace
- insight trace

### 7.3 不做

- 把 RAG 知识当成用户偏好证据。
- 把历史检索结果强行写成审美结论。
- 多 Agent 编排。
- 大而全知识图谱。

### 7.4 验收标准

- 报告能引用历史记录，但当前输入证据仍然优先。
- 外部知识有来源记录。
- 每条洞察能追踪到输入证据、历史证据或知识证据。
- 能输出基础评估结果。
- RAG 增强的是解释质量，而不是制造高级词。

## 8. V4：长期个性化系统

### 8.1 核心问题

把项目从分析工具扩展为长期个性化 AI：

> 系统能否长期观察用户审美如何变化，并在多模态输入中持续更新理解？

### 8.2 实现功能

多模态扩展：

- 音乐输入
- 视频输入
- 外部收藏源导入
- 用户手动补充上下文

审美轨迹：

- 审美时间轴
- 周期性变化总结
- 长期主题复现
- 风格迁移提示

知识结构：

- 审美概念关系表
- 轻量知识图谱
- 风格、情绪、材质、构图、主题之间的关系

Agent：

- 定期生成观察摘要
- 根据历史变化提出观察问题
- 调用检索、报告、画像更新等工具
- 所有行动必须有 reason 和 evidence

MCP / 外部上下文：

- 接入外部收藏源
- 接入笔记或资料库
- 接入未来可扩展的数据源

### 8.3 不做

- 无边界自动行动。
- 未经用户确认的外部数据导入。
- 没有证据来源的知识图谱关系。
- 把 Agent 当成营销包装词。

### 8.4 验收标准

- 新模态能进入统一表征体系。
- 长期轨迹能展示真实历史变化。
- Agent 的每个行为有明确触发原因和证据。
- 外部上下文不会覆盖用户输入证据。
- 系统仍然保持克制、可解释、不玄学。

## 9. 推荐实现顺序

最推荐的实际开发顺序：

1. V0 前端原型。
2. V1 后端 mock AI 闭环。
3. V1 接真实 AI 特征提取与 embedding。
4. V1 打磨报告体验和反馈。
5. V2 增加历史报告。
6. V2 增加轻量画像。
7. V3 加 personalized retrieval。
8. V3 加小型 RAG 和评估。
9. V4 再考虑 Agent、知识图谱和 MCP。

## 10. 当前最小行动建议

现在不要直接做 V3 / V4。

当前最合理的下一步是：

> 先实现 V0，再以 V1 的目录和数据结构为目标搭后端骨架。

也就是说：

- 前端先让体验跑起来。
- 后端先用 mock AI client。
- PostgreSQL 表结构先稳定。
- ChromaDB 可以在 V1 中后段接入。
- 真实模型调用等 mock 结构稳定后再替换。
