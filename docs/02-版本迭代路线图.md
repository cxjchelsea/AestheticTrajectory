# AI 审美形成系统：版本迭代路线图

## 1. 文档目的

这份文档专门定义项目从原型到长期系统的多版本迭代方案。

它回答三个问题：

- 每一次迭代要解决什么核心问题。
- 每一版具体实现哪些功能。
- 哪些能力不应该提前塞进当前版本。

本文件是产品与工程共同使用的版本路线文档，只定义“为什么分这些版本、每个版本解决什么核心问题、哪些能力不能提前做”。

职责边界：

- `03-MVP功能需求文档.md` 只负责第一版 MVP 的产品范围和用户路径。
- `12-开发任务拆分与里程碑计划.md` 只负责当前版本的开发任务顺序。
- `15-迭代执行记录.md` 记录每个版本实际完成了什么。
- `archive/` 保存已完成版本的事实快照、测试记录和遗留问题。

因此，本文档不记录具体开发进度，不作为 V1 验收清单，也不归档实际完成状态。

## 2. 总体迭代原则

项目不要一开始追求完整平台，而要按能力递进：

```text
先证明报告体验成立
↓
再证明数据闭环成立
↓
再证明长期观察成立
↓
再证明检索增强有效
↓
最后扩展为长期个性化 AI 系统
```

每一版只解决一个主要矛盾：

- V0：用户是否喜欢这个体验。
- V1：系统是否能真实跑通最小闭环。
- V2：系统是否能记住历史并形成轻量画像。
- V3：系统是否能借助检索和评估变得更可靠。
- V4：系统是否能扩展为长期、多模态、主动观察系统。
- V5：系统是否能在真实 runtime 与信任边界下可部署、可运维。

## 4. 版本与 Agent 前沿方向

每个版本都只引入少量前沿能力，避免把长期个性化 Agent 一次性做成不可控的大系统。

说明：

- Governance 从 V1 起横切所有版本，不等到 V4 才出现。
- Skill / Capability 在 V1 / V2 先通过 workflow step、prompt contract 和测试用例形成可沉淀材料，V4 再正式升级为可复用 Skill。
- Evaluation / Observability 从 V1 起做基础记录，V3 才扩展为系统化评估和失败回放。

| 版本 | 主要前沿方向 | 当前阶段使用方式 |
| --- | --- | --- |
| V0 | Product Prototype | 验证审美报告体验是否成立 |
| V1 | Multimodal Preference Modeling、Preference Explanation、Prompt Contract、Evidence Binding、Basic Governance | 用图片 / 文字特征、相似性分组、证据绑定报告和反馈闭环建立地基，同时控制人格诊断、玄学化和审美规训风险 |
| V2 | Memory / User Model、Temporal User Profiling、Preference Evolution、Memory Governance | 基于历史报告和用户反馈形成轻量画像与变化观察，并允许用户反馈修正偏好记录 |
| V3 | Personalized Retrieval、RAG for Explanation、Evaluation、Observability | 让报告参考历史与知识，并能通过 evidence coverage、feedback hit rate、grouping stability 和失败回放被评估 |
| V4 | Skill / Capability、Agent Runtime、Long-term Personalized Agent、Governance | 将固定 workflow 扩展为长期审美观察能力，并把成熟 workflow step 沉淀为可复用 Skill |
| V5 | Multimodal Runtime、Identity & Trust Boundary、Production MCP、Resilience | 真实 LLM runtime、用户身份与对象级 scope、OAuth 只读外部源、降级与运维 |
| V6 | Multimodal Preference Modeling、Evaluation / Observability、Governance | image/audio/video runtime adapter、metadata-only/placeholder 边界、默认 CI hardening 和横切治理 |
| V7 | Evaluation / Observability、Governance、Skill / Capability | 真实 runtime smoke、golden dataset、manual evaluation rubric 和 V7-V10 成型版路线 |
| V8 | Product Experience、Preference Explanation、Multimodal Preference Modeling | 上传、报告、反馈、画像、轨迹和 debug 展示路径产品化 |
| V9 | Evaluation / Observability、Governance | representative sample set、评估记录、trace summary 和回归复核 |
| V10 | Skill / Capability、Agent Runtime、Long-term Personalized Agent | 将成熟 workflow step 沉淀为可复用能力，完成作品级 Agent baseline |

## 5. 为什么 V1 不直接做完整 Agent

虽然本项目长期目标是长期个性化 Agent，但 V1 不应该直接做完整 Agent。

原因是长期个性化 Agent 依赖一系列更底层的工程能力。如果这些地基没有建立，直接做 Agent 会变成一个不可控的大 prompt 系统。

V1 阶段要先解决：

```text
输入能否稳定进入系统
图片和文字能否被结构化表征
每个特征是否有 evidence
报告是否能区分观察和解释
用户反馈是否能被保存
workflow 是否可复现
prompt 输出是否可校验
```

只有这些能力稳定后，后续的长期记忆、时间型用户画像、Skill、Agent Runtime、MCP 才有可靠基础。

因此，V1 的定位不是完整 Agent，而是：

> 长期个性化 Agent 的多模态表征与可解释分析底座。

## 6. V0：可演示原型

### 6.1 核心问题

先验证这个产品体验有没有吸引力：

> 用户上传一组审美样本后，是否愿意阅读一份“审美剖析报告”？

### 6.2 实现功能

前端：

- 首页
- 上传页
- 分析等待页
- 报告页
- 洞察反馈按钮

数据：

- 使用本地 mock JSON。
- 不接数据库。
- 不接真实模型。

报告：

- 总体摘要
- 底层特征
- 相似性分组
- 可能解释
- 重点洞察
- 反馈入口

### 6.3 不做

- PostgreSQL
- ChromaDB
- 真实 AI 调用
- 用户画像
- 历史报告
- RAG
- Agent

### 6.4 验收标准

- 可以完整演示一次用户路径。
- 报告结构清楚。
- 用户能理解产品不是心理测试。
- 至少有 1-2 条示例洞察让人觉得“这个方向有意思”。

## 7. V1：精简 MVP

### 7.1 核心问题

验证真实系统闭环是否成立：

> 系统能否从真实输入中提取底层特征，生成 embedding，做相似性分组，并输出有证据绑定的报告？

### 7.2 实现功能

输入：

- 图片上传
- 文字输入
- 样本预览
- 删除样本
- 输入数量限制

后端：

- FastAPI 项目骨架
- PostgreSQL 连接
- ChromaDB 连接
- 文件存储
- 分析任务状态

AI 分析：

- 图片底层特征提取
- 文本底层特征提取
- 统一底层特征 schema
- embedding 生成
- 小样本相似性分组
- possible interpretations 生成
- 结构化报告生成

报告：

- 总体摘要
- 底层特征摘要
- 相似性分组
- 可能解释
- 重点洞察
- 证据展示
- 用户反馈

数据保存：

- 输入样本
- 底层特征
- embedding metadata
- 分析任务
- 报告
- 洞察
- 反馈
- 基础日志

### 7.3 不做

- 完整登录系统
- 历史趋势
- 长期画像自动推理
- RAG
- Agent
- 知识图谱
- 音乐 / 视频输入

### 7.4 验收标准

- 用户能上传 3-10 个样本。
- 系统能真实生成报告。
- 每条洞察都有输入证据。
- 相似性分组不被包装成绝对聚类结论。
- 用户反馈能保存。
- PostgreSQL 是业务事实来源。
- ChromaDB 只保存向量和 metadata。

## 8. V2：历史报告与轻量画像

### 8.1 核心问题

让系统从一次性报告进入长期观察：

> 系统能不能记住用户过去的输入，并开始描述审美变化？

### 8.2 实现功能

历史：

- 历史报告列表
- 报告详情回看
- 按时间查看输入批次

对比：

- 最近两次报告对比
- 新增特征
- 减弱特征
- 重复出现的特征
- 可能的风格变化提示

轻量画像：

- 稳定底层特征统计
- 用户认可的解释
- 用户否定的解释
- 反馈权重
- 画像更新时间

记忆体系：

- 记忆写入：哪些输入、特征、解释和反馈应该进入轻量画像。
- 记忆更新：新的反馈如何改变旧的偏好权重。
- 记忆遗忘：被用户否定或过时的解释不继续强化。
- 记忆冲突：新输入和旧偏好不一致时，只记录变化，不强行下结论。
- 记忆可解释：画像中的每个倾向都能追溯到输入、报告或反馈。
- 记忆治理：用户反馈优先于模型推断，避免固化偏见。

前端：

- 历史页
- 报告对比页
- 轻量画像摘要

### 8.3 不做

- 自动推荐内容
- 复杂用户画像推理
- 大规模知识库 RAG
- 主动 Agent
- 周报 / 月报

### 8.4 验收标准

- 用户能看到过往报告。
- 系统能比较最近两次输入的共同点和差异。
- 用户反馈能影响轻量画像。
- 被否定的解释不会作为正向偏好进入画像。
- 画像只描述“系统观察到的倾向”，不做人格判断。

## 9. V3：检索增强与评估

### 9.1 核心问题

提高系统解释质量和工程可信度：

> 报告是否能参考历史和审美知识，同时仍然保持证据可追踪？

### 9.2 实现功能

个性化历史检索：

- 检索相似历史输入
- 检索历史报告摘要
- 检索用户曾经认可或否定的解释
- 将历史检索结果作为报告上下文

审美知识库 RAG：

- 小型审美知识文档
- 风格概念解释
- 设计 / 视觉 / 文学相关知识片段
- 检索来源记录

评估：

- evidence coverage
- feedback hit rate
- grouping stability
- prompt output schema pass rate
- hallucination check

可观测性：

- prompt version
- model name
- latency
- token / cost
- retrieval trace
- insight trace

### 9.3 不做

- 把 RAG 知识当成用户偏好证据。
- 把历史检索结果强行写成审美结论。
- 多 Agent 编排。
- 大而全知识图谱。

### 9.4 验收标准

- 报告能引用历史记录，但当前输入证据仍然优先。
- 外部知识有来源记录。
- 每条洞察能追踪到输入证据、历史证据或知识证据。
- 能输出基础评估结果。
- RAG 增强的是解释质量，而不是制造高级词。

## 10. V4：长期个性化系统

### 10.1 核心问题

把项目从分析工具扩展为长期个性化 AI：

> 系统能否长期观察用户审美如何变化，并在多模态输入中持续更新理解？

### 10.2 实现功能

多模态扩展：

- 音乐输入
- 视频输入
- 外部收藏源导入
- 用户手动补充上下文

审美轨迹：

- 审美时间轴
- 周期性变化总结
- 长期主题复现
- 风格迁移提示

知识结构：

- 审美概念关系表
- 轻量知识图谱
- 风格、情绪、材质、构图、主题之间的关系

Agent：

- 定期生成观察摘要
- 根据历史变化提出观察问题
- 调用检索、报告、画像更新等工具
- 所有行动必须有 reason 和 evidence

MCP / 外部上下文：

- 接入外部收藏源
- 接入笔记或资料库
- 接入未来可扩展的数据源

### 10.3 不做

- 无边界自动行动。
- 未经用户确认的外部数据导入。
- 没有证据来源的知识图谱关系。
- 把 Agent 当成营销包装词。

### 10.4 验收标准

- 新模态能进入统一表征体系。
- 长期轨迹能展示真实历史变化。
- Agent 的每个行为有明确触发原因和证据。
- 外部上下文不会覆盖用户输入证据。
- 系统仍然保持克制、可解释、不玄学。

## 11. V5：可部署运行时与信任边界

> 详细子阶段与调研见 `docs/iterations/v5-0-production-runtime-trust-boundary-research.md`。V5-0 待用户确认 §12 后，才进入 V5-A 实现。

### 11.1 核心问题

V4 已建立 Agent baseline，但核心 workflow 仍为 mock/heuristic，用户身份与外部 MCP 仍为 dev 模式。V5 要回答：

> 系统能否在真实 LLM runtime 与用户/数据信任边界就绪的前提下，成为可部署、可接真实外部源、可运维降级的系统？

### 11.2 实现功能（候选）

身份与访问：

- 持久用户 ID（登录或持久匿名 ID）
- API 对象级 user scope
- dev 环境 bypass

真实分析 runtime：

- 真实 LLM 生成报告（schema + evidence 契约）
- 可选 vision 路径（子阶段内定）

生产外部上下文：

- OAuth MCP 只读接入（1–2 个外部源）
- 继承 V4-D 用户 confirm 治理

韧性与运维：

- Chroma / LLM 不可达时的 graceful degrade 一致性
- 可选 OpenTelemetry / LangSmith（非硬门槛）
- V4 tech-debt 批次清理

### 11.3 不做

- V5 级 multi-agent 协作。
- LLM-as-judge evaluation dashboard。
- 企业级 IAM / SSO。
- 无 schema 的自由文本报告。
- 静默 external sync 或未经确认的 profile 写入。

### 11.4 验收标准（版本级）

- 真实 LLM 路径下 insight 仍有 evidenceRefs 且治理测试通过。
- 跨 user 数据隔离。
- 至少 1 个真实 OAuth MCP 只读源可 confirm 导入。
- 非核心路径降级可追踪、不伪造业务事实。
- V5 archive gate 与 legacy audit 完成。

### 11.5 子阶段（候选）

```text
V5-A Identity & Access
→ V5-B Real Report Runtime
→ V5-C Production MCP (OAuth)
→ V5-D Resilience & Observability
→ V5-E Governance Validation
→ V5 final closure
```

## 12. V6-V10：成型版路线与毕业线

V6 已归档为：

```text
Multimodal Runtime & Production Hardening baseline
```

V7 起不再以“继续扩功能”为默认方向，而是进入作品级完整系统的成型路线：

```text
V7 -> V8 -> V9 -> V10 -> 作品级毕业
```

### 12.1 V6：多模态运行时与生产硬化（已归档）

核心问题：

```text
系统能否让 image / audio / video 多模态输入进入可信 runtime 边界，并保持 evidence-first、profile governance 和 identity scope？
```

归档结论：

- image adapter 支持 mock / disabled / ollama_vision。
- music/video 支持 metadata_only / text_notes / mock / disabled。
- 默认 CI baseline 不依赖外部多模态模型。
- V6-A 真实 vision 模型人工验收后置。
- 真实 audio/video runtime 继续 carry_over，不阻塞作品级路线。

### 12.2 V7：Production Validation & Graduation Roadmap

核心问题：

```text
系统如何证明自己已经足够可信，并明确后续版本何时收束？
```

实现范围：

- Graduation roadmap 与 acceptance bar。
- Real runtime smoke pack 或手动 smoke checklist。
- Golden dataset / representative sample set。
- Manual evaluation rubric。
- Product demo acceptance planning。

不做：

- 不默认实现真实 audio/video runtime。
- 不接企业 SaaS 能力。
- 不做复杂 LLM-as-judge dashboard。

验收标准：

- V7-V10 路线明确。
- 作品级 graduation bar 明确。
- V6 carry-over 已重分类。
- 真实 runtime smoke 与评估包有可执行入口。

### 12.3 V8：Product Experience & Portfolio Demo

核心问题：

```text
用户是否能顺畅完成一条可展示的端到端审美形成路径？
```

实现范围：

- 上传 / 登记输入体验打磨。
- 报告、反馈、画像、轨迹页面体验打磨。
- Debug 信息与普通用户页面边界清楚。
- 作品集 demo script、截图/录屏、展示说明。

不做：

- 不把产品体验打磨变成推荐系统。
- 不新增无验证的模型能力。
- 不做企业账号、计费、多租户。

验收标准：

- 用户可以完成 demo 路径。
- 报告、反馈、画像、轨迹的价值能被清楚理解。
- 展示材料能说明系统架构、AI 能力边界和验证方式。

### 12.4 V9：Evaluation / Observability System

核心问题：

```text
系统质量是否能被持续复核，而不是只依赖一次性人工感觉？
```

实现范围：

- Representative sample set versioning。
- Evidence / governance / usefulness 评估记录。
- Evaluation summary 与 debug trace 对齐。
- 可选轻量 LLM-as-judge，但不作为作品级硬门槛。

不做：

- 不做复杂 SaaS dashboard。
- 不把 judge 结果当绝对真理。
- 不牺牲 evidence-first 和人工复核边界。

验收标准：

- 样本集、评估 rubric、评估记录可复现。
- 核心质量指标能解释失败原因。
- 回归复核不依赖单次主观判断。

### 12.5 V10：Capability / Agent Graduation

核心问题：

```text
系统是否能作为长期个性化 AI 的能力样板完成作品级收口？
```

实现范围：

- 将成熟 workflow step 归纳为可复用 capability。
- 明确哪些能力可迁移到墨核或其他个性化 AI 场景。
- Agent 行为、观察问题、报告生成、profile 更新具备证据链。
- 最终 archive / portfolio packaging。

不做：

- 不做无边界自主 Agent。
- 不做企业级 Agent 平台。
- 不做未验证能力的营销式包装。

验收标准：

- 能清楚解释系统从多模态输入到长期偏好建模的完整链路。
- 可复用能力边界清楚。
- 项目具备作品级 README、架构说明、验证记录和演示材料。

### 12.6 作品级 vs SaaS 级边界

作品级毕业线要求：

```text
用户路径完整，工程证据完整，表达材料完整。
```

生产 SaaS 后置能力：

- 企业账号 / SSO / RBAC。
- 计费、订阅、多租户。
- 生产级 OAuth provider 扩展。
- 大规模 LangSmith / OTel / Sentry 运维平台。
- 自动化成本治理、告警、on-call runbook。

这些能力可进入 V11+，但不阻塞 V10 作品级毕业。

## 13. 版本之间的依赖关系

版本推进必须遵守能力依赖：

```text
V1 单次分析闭环
是 V2 历史报告、轻量画像和记忆写入的基础。

V2 历史与画像
是 V3 personalized retrieval、历史证据引用和偏好变化评估的基础。

V3 检索增强、评估与可观测性
是 V4 Skill 沉淀、长期观察和 Agent Runtime 的基础。

V4 长期个性化 Agent baseline
是 V5 真实 runtime、identity 与生产 MCP 的基础。

V4 长期个性化系统
才进入更完整的 Agent 化能力，不反向扩大 V1 / V2 范围。
```

一句话总结：

```text
V1 是地基
V2 是记忆
V3 是可信度
V4 是 Agent 化
V5 是可部署与信任边界
V6 是多模态边界
V7 是验证与毕业路线
V8 是产品体验
V9 是质量评估
V10 是能力毕业
```
