# 多模态偏好建模设计文档

## 1. 文档职责与权威边界

本文档是 **Multimodal Preference Modeling**（`docs/01-产品概念说明书.md` §3.2）的语义权威入口。

它定义：

- 多模态输入类型与 metadata-only 边界
- V6 起真实内容解析层（image / audio / video）的语义边界
- embedding text 构建规则
- 文件存储与 `file_url` 约定
- 向量 runtime 与 Chroma collection 隔离规则
- 多模态解析结果如何进入 `InputFeature` 与 evidence governance

它不替代：

- 表结构与 API 路径细节：`docs/07-数据结构与系统架构文档.md`
- 模块契约与测试：`docs/11-模块拆分与接口测试文档.md`
- workflow step 顺序：`docs/09-AI Workflow 编排与任务执行文档.md`

## 2. 一句话定义

多模态偏好建模指：在用户上传或登记的多种审美输入上，统一生成可比较的 embedding 与底层特征，为相似性分组、个性化检索和后续审美轨迹提供输入层语义，而不把未解析的媒体内容写成已验证偏好。

## 3. 输入 taxonomy（V4-A → V6）

| type | 内容形态 | V4-A/V5 处理 | V6 目标 |
| --- | --- | --- | --- |
| `text` | 用户文本 | 直接参与 feature + embedding | 继续作为基准模态 |
| `image` | 图片文件或 URL | 真实文件经 upload API；feature 仍 mock/heuristic | V6-A 接入真实视觉内容解析 |
| `music` | 曲名、链接、备注 | **metadata-only**，不解析音频 | V6-B 定义 audio/music 解析最小路径 |
| `video` | 标题、链接、备注 | **metadata-only**，不解析视频 | V6-C 定义 keyframe/subtitle/metadata 边界 |

校验不变量：

- `music` / `video` 至少提供 `title` 或 `fileUrl` 之一。
- 报告、UI、debug 不得声称已解析未实际解析的媒体内容。
- 新模态输入不绕过 feedback 直接写入 profile positive evidence。

## 3.1 V6 真实解析层

V6 将输入处理分为三层：

```text
Input Record
→ Modality Content Extraction
→ Structured InputFeature
→ Embedding / grouping / report
```

语义要求：

- `Input Record` 保存用户提交的事实：`type`、`title`、`contentText`、`fileUrl`、`description`。
- `Modality Content Extraction` 负责读取真实媒体内容或明确标记 metadata-only。
- `Structured InputFeature` 才能进入相似性分组、报告解释和 profile 间接证据链。
- 任何没有经过真实解析的媒体内容，不得在报告中写成“系统看见/听见/识别到”。

V6 不要求所有模态同时完成。版本推进顺序是：

```text
image first → audio/music boundary → video boundary → hardening → governance
```

## 3.2 解析状态

每个多模态输入在 debug / feature metadata 中应能区分：

| 状态 | 含义 | 是否可作为内容证据 |
| --- | --- | --- |
| `parsed` | 已读取媒体内容并由真实 parser/model 生成结构化特征 | 是 |
| `metadata_only` | 只使用 title / description / URL metadata | 仅可作为 metadata 证据 |
| `placeholder` | mock/heuristic 占位，不代表真实内容理解 | 否，必须 dev-only 标记 |
| `failed` | 用户期待内容解析但 runtime 失败 | 不可伪装成功；按子阶段 fail-fast 或 partial_failed |

## 3.3 Modality Extractor Adapter

V6 推荐按模态拆 extractor adapter：

```text
ImageFeatureExtractor
AudioFeatureExtractor
VideoFeatureExtractor
```

每个 adapter 必须输出或抛错：

```text
InputFeature
├── inputId
├── featureType
├── lowLevelFeatures
├── sampleEvidence
├── promptVersion
└── modelName
```

禁止：

- 直接把原始 LLM / vision response 入库。
- 用空 feature 或默认 feature 掩盖 runtime 失败。
- 把 metadata-only 结果标记成真实视觉/音频/视频解析。

## 3.4 失败语义

V6 的默认失败语义：

| 场景 | 处理方式 |
| --- | --- |
| 用户上传本地图片并进入 image analysis | 真实 image parser 失败应 fail-fast 或明确 `partial_failed`，不 silent fallback mock |
| 用户只提供图片 URL 且服务无法读取内容 | 可 metadata-only，但报告/debug 必须标记 |
| music/video 只有 title 或描述 | metadata-only 是合法路径 |
| music/video 用户上传文件且 V6 子阶段承诺解析 | parser 失败不得伪装成功 |
| embedding / Chroma 增强失败 | 仍按 V5-D 非核心增强降级规则 |
| database / schema validation / user scope 失败 | fail-fast |

## 3.5 Evidence Governance

多模态解析结果可以成为 report insight 的 evidence，但必须满足：

- evidence 能追溯到当前 report 的 `inputId`。
- `sampleEvidence` 是从解析结果或用户 metadata 明确生成的片段，不是无来源高级词。
- report `evidenceRefs` 仍只引用当前 inputs，不引用 external source、profile item 或模型内部临时对象。
- 多模态 feature 可以间接进入 profile，但仍必须经过 report / feedback / profile builder 的既有治理链路。
- 低置信度或 metadata-only 结果不得形成 stable profile item。

## 4. Embedding runtime 与 collection 隔离

环境变量（`backend/.env.example`）：

```text
EMBEDDING_RUNTIME=mock|openai|ollama
EMBEDDING_MODEL=...
EMBEDDING_DIMENSIONS=...
CHROMA_ENABLED=false|true
```

规则：

- 默认 `mock`（8 维），保证 CI 与 memory backend 无外部依赖。
- `openai` / `ollama` 为可选 real path；无 key 或 runtime 错误时 **fail-fast**，不静默回退 mock。
- 不同 runtime / 维度 **不得** 共用同一 Chroma collection。

Collection 命名：

```text
inputs_{runtime}_{dimension}
例：inputs_mock_8、inputs_openai_512、inputs_ollama_768
```

## 5. 文件存储

- 图片走 `POST /api/files/upload` → 本地 `UPLOAD_DIR`。
- `inputs.file_url` 存服务 URL（如 `/api/files/{file_id}`），不新增 `input_files` 表。
- `GET /api/files/{file_id}` 用于读取已上传文件。

## 6. Chroma 写入边界

- PostgreSQL `embedding_records` 保存业务事实；Chroma 保存向量与检索 metadata。
- `CHROMA_ENABLED=false`：跳过远程 upsert，仍写 `EmbeddingRecord`；debug 记录 `not_used` / skipped。
- `CHROMA_ENABLED=true` 且 upsert 失败：记录 `fallback_events`，job 可完成但 debug 明示失败原因。
- 测试默认使用 fake vector store，不依赖外部 Chroma 进程。

Chroma 本地启动（Windows）：`chroma run --host 127.0.0.1 --path ... --port 8001`。

## 7. 治理不变量

1. metadata-only 模态不得伪装成内容理解。
2. mock / heuristic feature 必须在 debug `mockUsage` / `boundaryWarnings` 中可见。
3. 向量空间变更必须换 collection，不迁移历史 mock 向量。
4. 多模态输入只进入输入层与 embedding 层，不直接改写 profile。
5. 真实解析 runtime 失败不得 silent fallback mock。
6. 多模态解析不得做人脸身份识别、人格诊断、心理评估、能力判断或命运式表达。
7. 对人物、身体、身份等敏感内容，只能描述画面/声音结构，不得做价值评判。

## 10. 文档维护

- 表结构、env 默认值变更时同步 `07` 与 `backend/.env.example`。
- 新增模态或 runtime 时先更新本文档 §3–§6，再改代码。
