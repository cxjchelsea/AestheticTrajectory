# AI 审美形成系统：验证与评估文档

## 1. 文档目的

这份文档回答一个核心问题：

> 如何证明这个系统不是在胡说？

这个系统不是搜索引擎、OCR 或传统推荐系统，不能只用客观准确率衡量。它更接近解释型系统，核心不是证明“绝对正确”，而是证明：

> 系统的解释有依据，并且用户觉得被理解。

## 2. 系统类型判断

这个系统不是客观正确系统，而是：

> 解释型系统（Interpretive System）。

传统系统的验证方式：

| 系统 | 常见验证方式 |
| --- | --- |
| 搜索引擎 | 是否搜到相关结果 |
| OCR | 字符识别准确率 |
| 推荐系统 | 点击率、转化率 |
| 分类器 | 分类准确率 |

本系统更接近：

- 艺术评论
- 风格分析
- 人格洞察
- 审美理解
- 心理测验中的解释机制

它不存在唯一正确答案。

真正要验证的是：

- 系统是否能从输入中找到真实结构
- 系统是否能稳定提取风格特征
- 系统是否能发现跨输入一致性
- 用户是否认可系统生成的洞察

## 3. 验证总框架

系统验证分为三层：

1. 特征层验证：AI 是否稳定提取输入特征。
2. 结构层验证：系统是否发现跨输入模式。
3. 体验层验证：用户是否觉得洞察有解释力。

对应关系：

| 验证层级 | 核心问题 | 方法 |
| --- | --- | --- |
| 特征层 | 系统看见了什么 | 人工抽检、标签一致性 |
| 结构层 | 系统发现了什么关系 | embedding 聚类、跨次一致性 |
| 体验层 | 用户是否认可 | 用户反馈、访谈、留存 |
| 生成层 | 输出是否可控 | JSON schema、证据覆盖率、跨次稳定性 |
| 检索层 | 检索是否有用 | RAG 命中率、历史检索相关性 |
| 可观测层 | 过程是否可追踪 | prompt versioning、insight traceability |

## 4. 第一层：特征层验证

### 4.1 验证目标

验证系统是否能稳定识别输入中的基础审美特征。

例如：

- 低饱和
- 冷色调
- 空旷空间
- 人物缺席
- 工业材质
- 克制叙事
- 未完成感

### 4.2 验证方法

选取一组测试样本，由人工先标注主要特征，再对比 AI 输出。

对比项目：

- AI 是否提取到主要特征
- AI 是否漏掉明显特征
- AI 是否生成无依据特征
- AI 证据是否对应输入

### 4.3 评分标准

每个样本可以按 0-3 分评分：

| 分数 | 标准 |
| --- | --- |
| 0 | 大部分特征错误，或输出与输入无关 |
| 1 | 提到少量相关特征，但较泛 |
| 2 | 识别到主要特征，有一定依据 |
| 3 | 识别准确，证据清晰，表述稳定 |

### 4.4 合格标准

MVP 阶段不要求完美，但应该做到：

- 明显视觉特征识别正确
- 明显情绪氛围识别正确
- 每个标签有依据
- 不生成过多虚假标签

## 5. 第二层：embedding 聚类验证

### 5.1 验证目标

验证系统是否能把相似审美输入聚在一起。

例如，以下内容应该在审美空间中相对接近：

- 工业废墟
- 混凝土建筑
- 黑白摄影
- 极简服装
- 《1984》相关文本

它们可能共同指向：

> 工业化孤独感 / 结构化冷感。

### 5.2 测试方法

准备几组具有明显风格的样本：

1. 工业冷感组
2. 温柔日常组
3. 自然松弛组
4. 复古怀旧组
5. 未来科技组

将所有样本混合输入系统，观察聚类结果。

### 5.3 观察指标

需要观察：

- 同组样本是否靠近
- 不同组样本是否分离
- 聚类名称是否合理
- 聚类解释是否有依据
- 跨模态样本是否能聚到一起

### 5.4 合格标准

MVP 阶段的合格标准：

- 明显风格组能大致聚合
- 聚类解释不违背样本内容
- 异常样本能被识别
- 聚类不是随机结果

## 6. 第三层：一致性验证

### 6.1 验证目标

验证系统是否在不同时间、不同输入下保持相对稳定，而不是每次随机编造。

### 6.2 同组重复测试

对同一组输入多次生成报告，观察：

- 底层特征是否基本一致
- 可能解释是否在合理范围内相近
- 洞察是否有稳定方向
- 是否每次都换一套说法

### 6.3 相似组测试

让用户上传两组相似但不完全相同的内容。

观察系统是否仍然识别出共同风格，例如：

- 冷色调
- 结构感
- 空旷空间
- 去人化

### 6.4 长期一致性

如果用户多次上传内容，系统应能识别：

- 稳定偏好
- 新出现主题
- 正在减弱的倾向
- 被用户反馈否定的标签

### 6.5 合格标准

系统应该满足：

- 同一输入不会产生完全相反结论
- 相似输入会产生相似洞察
- 用户否定过的标签不会反复强推
- 长期报告中能看到连续性

## 7. 第四层：用户主观认可

### 7.1 验证目标

这个系统最关键的指标是：

> 用户是否觉得“这真的很像我”。

### 7.2 洞察反馈

每条洞察后收集：

```text
这条洞察：
[ ] 完全不像我
[ ] 有点意思
[ ] 很像我
[ ] 有被看见的感觉
```

### 7.3 指标定义

可以统计：

- 洞察认可率：选择“很像我”或“有被看见的感觉”的比例。
- 有趣率：选择“有点意思”及以上的比例。
- 否定率：选择“完全不像我”的比例。
- 高命中洞察数：一份报告中被高度认可的洞察数量。

### 7.4 MVP 合格标准

第一版可以设定：

- 每份报告至少有 1 条洞察被用户认为“很像我”。
- 否定率不能过高。
- 用户愿意读完整份报告。
- 用户愿意再次上传新样本。

## 8. 第五层：可解释性验证

### 8.1 验证目标

验证系统的每个结论是否能追溯到输入。

### 8.2 检查方式

对每条洞察检查：

- 是否有证据
- 证据是否真实存在
- 证据是否足以支持结论
- 结论是否过度推断
- 是否区分观察和解释

### 8.3 失败示例

不合格：

```text
你是一个内心孤独但渴望自由的人。
```

问题：

- 没有输入依据
- 直接判断人格
- 谁看都适用

### 8.4 合格示例

合格：

```text
你的输入中反复出现人物缺席、低饱和色和空旷空间，因此系统观察到一种“疏离感”的审美倾向。
```

优点：

- 有证据
- 说的是输入
- 没有诊断人格

## 9. 第六层：产品体验验证

### 9.1 验证目标

验证用户是否愿意完成整个流程。

### 9.2 行为指标

可以观察：

- 上传完成率
- 分析等待完成率
- 报告阅读完成率
- 洞察反馈率
- 再次上传率
- 分享 / 保存率

### 9.3 体验访谈问题

可以问用户：

- 你觉得这个系统在做什么？
- 哪一条洞察最像你？
- 哪一条最不像你？
- 你觉得它像工具、测试，还是观察者？
- 你愿意过一周再用一次吗？
- 你希望它长期记录什么？

## 10. 测试样本设计

### 10.1 标准测试集

建议建立一个小型标准测试集。

每组包含：

- 5 张图片
- 3 段文字
- 人工预期底层特征
- 可接受的解释候选
- 不应出现的错误解释
- 风格覆盖说明

### 10.2 示例测试组

#### 工业冷感组

预期底层特征：

- 低饱和
- 冷色调
- 空间密度低
- 人物存在弱或缺席
- 构图复杂度低到中

可接受解释候选：

- 冷感空间偏好
- 结构化疏离
- 工业感视觉

#### 温柔日常组

预期底层特征：

- 暖色调
- 中低对比
- 人物或生活物件存在
- 空间密度中等
- 叙事密度低到中

可接受解释候选：

- 未完成的温柔
- 日常诗性
- 生活化低刺激偏好

#### 自然松弛组

预期底层特征：

- 自然光
- 开放空间
- 绿色或自然色系
- 空间密度低到中
- 构图复杂度低到中

可接受解释候选：

- 自然中的安静感
- 非控制感
- 松弛型视觉偏好

### 10.3 去作者中心化测试集

为了避免系统过拟合开发者个人审美，必须加入非文艺低饱和风格测试。

必测风格包括：

- 高饱和二次元
- Y2K
- 朋克
- hyperpop
- meme collage
- 婚礼摄影
- 美式 suburban
- 甜美元气风
- 赛博霓虹
- 土味 / 网感美学

观察重点：

- 系统是否仍能提取稳定底层特征。
- 系统是否强行使用“疏离、克制、留白、未完成”等开发者偏好的解释语言。
- 系统是否能生成更贴近该风格自身语境的解释。
- 用户是否认可这些动态解释。

## 11. 失败类型清单

需要重点监控以下失败类型：

1. 空泛化：输出谁都能套用。
2. 玄学化：像算命、灵魂分析。
3. 过度人格化：从输入直接推断人格。
4. 无依据：结论找不到输入证据。
5. 不一致：同一输入多次输出相反结论。
6. 标签堆砌：只有关键词，没有解释。
7. 过度确定：把可能性说成绝对事实。
8. 审美粗糙：用词低级，缺少产品气质。
9. 检索污染：RAG 检索到的知识与用户输入无关，却被强行写进报告。
10. Agent 过度行动：系统在证据不足时主动生成过多推断。
11. 反馈失效：用户否定过的标签仍反复出现。
12. 可追溯性缺失：无法知道某条洞察由哪些特征、prompt 或检索结果生成。
13. 作者中心化：系统把不同审美都翻译成开发者偏好的文艺语言。
14. 解释固化：系统把“工业化孤独感”等高层解释当成事实标签。
15. 替代解释缺失：面对模糊特征时只给一个解释，不提供其他可能。

## 13. MVP 阶段成功标准

第一版系统可以认为初步成立，如果满足：

- 基础特征提取基本稳定
- embedding 聚类能大致分组
- 报告中每条洞察有依据
- 用户至少认可一条核心洞察
- 输出不像心理测试或算命
- 用户愿意再次上传
- 系统能保存反馈并影响后续分析

## 14. 简历中的验证表达

这个项目写进简历时，可以强调：

> 设计了面向解释型 AI 系统的多层验证方法，包括特征提取一致性、embedding 聚类有效性、跨次分析稳定性、用户主观认可和洞察可解释性评估。

这会比单纯写“接入大模型生成审美报告”更有含金量。

## 15. 工程评估与可观测性

为了让项目更像真实 AI 工程系统，需要加入 Evaluation 与 Observability。

### 15.1 Evaluation 指标

建议记录：

- insight hit rate：用户认可洞察的比例。
- evidence coverage：每条洞察是否绑定足够证据。
- cluster stability：相同或相似输入的聚类是否稳定。
- cross-run consistency：同一输入多次生成是否一致。
- historical consistency：系统对用户长期偏好的判断是否连续。
- rejected tag recurrence rate：被用户否定的标签是否仍然反复出现。
- retrieval relevance：RAG 或历史检索结果是否与当前输入相关。

### 15.2 Observability 记录

每次分析应尽量记录：

- prompt version
- model version
- function calling trace
- feature extraction result
- embedding model
- cluster result
- retrieved user memories
- retrieved knowledge documents
- generated insight
- user feedback

这些记录可以回答：

> 系统为什么生成这条洞察？

也可以支持后续调试和面试展示。

### 15.3 Agent / RAG / 知识图谱的评估边界

如果后续加入 RAG，需要评估检索结果是否真的增强了解释，而不是堆砌概念。

如果后续加入 Agent，需要评估 Agent 是否做出了有效工具选择，而不是把固定流程包装成 Agent。

如果后续加入知识图谱，需要评估图谱关系是否有证据来源，而不是主观编造概念关系。

## 16. 结论

这个系统不需要证明 AI 绝对懂审美。

它需要证明：

1. AI 能从输入中稳定提取风格特征。
2. AI 能发现跨输入的一致结构。
3. AI 的解释有证据支持。
4. 用户觉得某些洞察确实说中了自己。

只要这四点成立，它就不是玩具，而是一个有验证逻辑的解释型 AI 系统。
